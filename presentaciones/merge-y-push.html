Estrategias de merge y política de push

Cómo entra el trabajo en la rama base y qué sale al remoto: las cuatro estrategias de merge, la política de push que trae cada estrategia de rama, el hook que bloquea lo irreversible y las reglas que aplica el servidor.

Dos decisiones, dos sitios

  • Merge: cómo se integra una rama en la base. Es un dato del proyecto, configuracion.branching.mergeStrategy en _hilo/ESTADO_PROYECTO.json.
  • Push: qué sale al remoto y con qué garantías. Se decide en tres capas: la configuración (pushFeatures), el hook local (bash-guard.js) y las reglas del servidor (rulesets o branch policies).

Elegir la estrategia de rama fija las dos a la vez: cada una trae su mergeStrategy y su pushFeatures por defecto.

La estrategia no es una preferencia de estilo: es la fila de una tabla que rellena seis campos del Hilo. Quien la aplica es references/workflow-branching.md.

Squash o no-ff: el desempate

Con Pull Requests, squash: un commit limpio por feature, fácil de leer y de revertir.

Rebase: la regla de las tres noes

git fetch origin
git rebase origin/main
git push --force-with-lease
  • Nunca rebase de main ni de develop.
  • Nunca git push --force: --force-with-lease comprueba el remoto antes de sobrescribir.
  • Solo en ramas propias que nadie más esté usando.

Rebase aquí sirve para actualizar tu rama con la base, no para integrarla. Integrar es lo que hace la mergeStrategy del proyecto.

Conflictos: el flujo, no el pánico

  1. git fetch origin
  2. git rebase origin/main
  3. Git marca los ficheros en conflicto
  4. Resolver entre los marcadores <<<<<<<, ======= y >>>>>>>
  5. git add <fichero-resuelto>
  6. git rebase --continue

Herramienta visual, si hace falta:

git config --global merge.tool vscode
git config --global mergetool.vscode.cmd 'code --wait --merge $REMOTE $LOCAL $BASE $MERGED'

Los pasos completos, con un conflicto resuelto de ejemplo, en strategies/merge-strategies.md.

Push de features: un dato, no una costumbre

configuracion.branching.pushFeatures dice si las ramas de trabajo salen al remoto.

  • false en developer-branch: las features son locales y lo único que se empuja es la rama base personal dev.{usuario}.
  • false en github-flow-simplificado: se mergea en local con --no-ff y se empuja la rama base.
  • true en el resto: la rama sale al remoto y el Pull Request es el gate.

Aviso: pushFeatures vive en _hilo/ESTADO_PROYECTO.json, no en ecosystem.config.schema.json. Es una clave del proyecto, no de la organización.

La regla .claude/rules/developer-branch.md se autogatea leyendo configuracion.branching.estrategia; si no vale developer-branch, no aplica nada.

Lo que el hook bloquea, y por qué

bash-guard.js corre en PreToolUse[Bash] y sale con exit 2: bloqueo intrínseco, no configurable.

OrdenMotivo
git push --force, y -f o -fudestruye el historial de otros
--no-verify en commit, push, merge o rebasesaltea los hooks defensivos
git reset --harddescarta lo no commiteado
git branch -Dborra una rama sin garantía de merge
git stash drop y git stash clearsin recuperación posible
git checkout . y git restore .descarta lo no preparado

--force-with-lease no se bloquea, y -d en minúscula tampoco: el hook distingue mayúsculas.

Los flags cortos se tokenizan, así que -fu y -r -f cuentan igual que la forma canónica. git clean -f también está bloqueado.

Lo que protege el remoto: GitHub

templates/branch-ruleset.json.template, sobre ~DEFAULT_BRANCH:

  • deletion y non_fast_forward: ni se borra ni se fuerza.
  • required_linear_history: sin commits de merge.
  • required_signatures: firmado SSH o GPG.
  • pull_request: una aprobación, code owner, aprobación del último push, hilos resueltos y allowed_merge_methods: ["squash"].
  • required_status_checks: Build y Security, en modo estricto.
  • merge_queue: cada PR se prueba contra la base más los que van por delante.

Se versiona en .github/rulesets/ y se aplica por API con gh (tools/github-rulesets.md).

El context de un check es el name: del job, no su id. Si no coincide, el check nunca aparece y el PR se queda bloqueado para siempre.

En repositorios privados los rulesets exigen plan de pago, y merge_queue exige Team o Enterprise.

Tags: el push que no se deshace

templates/tag-ruleset.json.template, sobre refs/tags/v*:

  • creation: solo los bypass_actors crean tags v*.
  • deletion y update: un tag publicado ni se borra ni se mueve a otro commit.
  • required_signatures: git tag -s.

Es lo que sostiene el flujo de release: lo que se empuja como versión se queda quieto.

El hotfix no es una excepción

La tentación, con producción caída, es mergear en local y empujar:

git checkout main
git merge --no-ff hotfix/...   # el ruleset lo rechaza tres veces

templates/branch-ruleset.json.template lo impide por tres sitios a la vez: required_linear_history no admite commits de merge, la regla pull_request no admite push directo, y allowed_merge_methods solo deja squash.

Lo que cambia en un hotfix es la prioridad de la revisión, no el mecanismo: rama, PR, squash y tag.

El merge commit para integrar sigue siendo correcto donde el historial lineal no se exige, que es lo que hacen gitflow y oneflow a propósito; en esos proyectos el ruleset se despliega sin required_linear_history. Lo decide mergeStrategy del Hilo, no la urgencia del arreglo.
