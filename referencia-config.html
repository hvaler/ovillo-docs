Referencia de configuración

La identidad de la organización y las decisiones de plataforma (cloud, identidad, base de datos, VCS, CI/CD, Hub, hooks) viven en un solo fichero. Esta página se genera del schema: cada clave con su tipo, sus valores permitidos, su default y su descripción.

14objetos raíz
89claves documentadas
1configVersion

Jerarquía

Tres capas, la más específica gana: proyecto (ecosystem.config.json en la raíz) › organización (el mismo fichero distribuido con el plugin o el zip) › defaults del schema. Los hooks lo leen con hooks/lib/config.js; las skills, con la referencia de hub-client y cicd-init.

ecosystem.config.json (proyecto)      ← manda
  └─ ecosystem.config.json (organización, plugin/zip)
       └─ defaults (schema, "default" de cada clave)

configVersion integer

Version del esquema de configuracion. El validador falla si no es la que entiende: una version MAYOR exige actualizar el plugin (el ecosistema avisa en sesion y sigue con las claves conocidas); una MENOR exige migrar el fichero. La lee hooks/lib/config.js (CONFIG_VERSION_SOPORTADA) y la comprueba validate-config.js.

Validar

El schema es JSON Schema draft-07; en el editor basta con "$schema": ".claude/schemas/ecosystem.config.schema.json" para autocompletar y validar al escribir. Las claves desconocidas se detectan comparando con properties del schema; /hv:init avisa si el fichero no valida.

Configuración personal

Precedencia de configuración: .claude/user-config.json (personal, solo preferencias.*) › _hilo/ESTADO_PROYECTO.json (proyecto) › ecosystem.config.json (organización) › defaults neutrales. Resuelve hooks/lib/config.js → resolve(); alias y claves deprecadas en .claude/CONFIGURACION.md.

Tres ficheros, cada uno con su papel. Ninguna skill ni hook debe leer dos de ellos a mano para decidir un valor: la función resolve() aplica la precedencia y los alias por todos.

FicheroPapelSe commiteaQuién lo escribe
.claude/user-config.jsonPersonal: solo el bloque preferencias.* (nivel de integración Git, confirmar push, formato de commit…)no (.gitignore)cada desarrollador (/hv:mi-config)
_hilo/ESTADO_PROYECTO.jsonProyecto: estado y decisiones del equipo (ramas, plataforma CI/CD, entornos, tipos de tarea, evolutivos, equipo, mcpSync)sí/hv:onboarding, /hv:cicd-init, las skills que actualizan el Hilo
ecosystem.config.jsonOrganización: identidad y defaults compartidos por todos los proyectos (namespace, IdP, cloud, base de datos, VCS, CI/CD, Hub, hooks)síla organización; schema en .claude/schemas/ecosystem.config.schema.json
defaults neutraleslo que aplica cuando nadie ha dicho nada—hooks/lib/config.js → DEFAULTS

Quién manda en cada familia de claves

El proyecto gana; la organización es el default. Lo que solo es estado del proyecto no tiene equivalente en la organización, y lo que solo es identidad de la organización no tiene equivalente en el Hilo.

Plataforma CI/CDinfraestructura.cicd.plataformacicd.platform → none
Branching: estrategia, rama base, convenciónconfiguracion.branching.{estrategia, ramaBase, convencionRamas} (solo dentro de branching)vcs.{branchingStrategy, defaultBranch, branchNamingConvention}

Las 13 estrategias de branching reconocidas son el enum vcs.branchingStrategy del schema; la lista _estrategias_disponibles del Hilo es una copia informativa de ese enum.

Resolución

En un hook (Node):

const configLib = require(path.join(__dirname, 'lib', 'config'));
const plataforma = configLib.resolve('cicd.platform', { fallback: 'none' });          // proyecto > organización > default
const { value, source } = configLib.resolve('vcs.defaultBranch', { detail: true });   // source: proyecto | organizacion | default

En una skill o desde la terminal (modo plugin o en-repo):

node "${CLAUDE_PLUGIN_ROOT:-.claude}/hooks/config-check.js" --resolve cicd.platform
node "${CLAUDE_PLUGIN_ROOT:-.claude}/hooks/config-check.js" --resolve vcs.branchNamingConvention --json

En PowerShell, dentro de una skill:

$plataforma = (node "$env:CLAUDE_PLUGIN_ROOT/hooks/config-check.js" --resolve cicd.platform --json | ConvertFrom-Json).value

resolve() devuelve las convenciones de rama en el dialecto del Hilo ({codigo}, {descripcion}, {tipo}), que es el que consumen commit, git-sync y la regla developer-branch; la organización puede escribirlas con {code}, {description}, {type} y se traducen.

Comprobar y migrar

node "${CLAUDE_PLUGIN_ROOT:-.claude}/hooks/config-check.js" --validate           # hallazgos de coherencia del Hilo
node "${CLAUDE_PLUGIN_ROOT:-.claude}/hooks/config-check.js" --migrate --dry-run  # qué cambiaría
node "${CLAUDE_PLUGIN_ROOT:-.claude}/hooks/config-check.js" --migrate            # quita las planas si coinciden con branching.*
node .claude/scripts/validate-config.js                                         # ecosystem.config.json contra su schema

Hallazgos: DUP_DIVERGENTE (plana y anidada con valores distintos: gana branching.*), CLAVE_DEPRECADA, ENUM_DESCONOCIDO, LISTA_ESTRATEGIAS_DESFASADA. El hook banner los muestra al empezar la sesión (aviso, una vez) y hilo-json-guard avisa al commitear un ESTADO_PROYECTO.json con una divergencia (exit 1; bloquea solo si la organización pone config-guard en hooks.blockList). /hv:init nunca reescribe el Hilo: la migración es siempre una acción explícita.
