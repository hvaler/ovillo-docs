FASE 2.5 — Registro pipeline en Azure DevOps — SOLO Fase ≥ 1

Si Fase = 0, saltar a FASE 3. GitHub Actions: no hay definición que registrar (el workflow existe por estar en .github/workflows/). En su lugar, FASE 2.5-gh (más abajo): environments, reviewers y secretos con gh.

Tras escribir los ficheros, registrar build definition en Azure DevOps vía API REST.

Por entrypoint (R25): con >1 entrypoint hay >1 azure-pipelines.<slug>.yml → una definición Azure DevOps por cada uno (<PROYECTO>-<slug>, con su yamlFilename y trigger.paths propios). Repetir FASE 2.5 (y 2.6) por cada pipeline generado; cada entrada se persiste en su cicd[] (FASE 4). Console/Worker = definición CI-only (sin stages de deploy).

R20 — si $DEPLOY_MODE = on-demand: el JSON de la definición DEBE incluir la sección variables con DeployEnv y allowOverride: true (= settable at queue time). Sin esto, /hv:cicd-deploy --env <env> falla al encolar con DeployEnv is not a valid queue-time variable. Si $DEPLOY_MODE = auto, omitir esa variable (el YAML no la usa).

Descubrimiento

# 1. RepositoryId
$repos = Invoke-RestMethod -Uri "$tfsUrl/$proj/_apis/git/repositories?api-version=5.0" -UseDefaultCredentials
$repoId = ($repos.value | Where-Object { $_.name -eq $repoName }).id

# 2. QueueId de el pool configurado (per-proyecto)
$queues = Invoke-RestMethod -Uri "$tfsUrl/$proj/_apis/distributedtask/queues?api-version=5.0-preview" -UseDefaultCredentials
$queueId = ($queues.value | Where-Object { $_.pool.name -eq 'el pool configurado' }).id

# 3. Default branch
$defaultBranch = "refs/heads/$ramaBase"

POST build definition

{
  "name": "<PIPELINE_NAME>",
  "path": "\\",
  "type": "build",
  "process": {
    "yamlFilename": "azure-pipelines.yml",
    "type": 2
  },
  "queue": { "id": <queueId> },
  "repository": {
    "id": "<repoId>",
    "name": "<repoName>",
    "type": "TfsGit",
    "defaultBranch": "<defaultBranch>"
  },
  "variables": {
    "DeployEnv": { "value": "", "allowOverride": true }
  },
  "triggers": [{
    "branchFilters": [],
    "pathFilters": [],
    "settingsSourceType": 2,
    "batchChanges": false,
    "maxConcurrentBuildsPerBranch": 1,
    "triggerType": "continuousIntegration"
  }],
  "retentionRules": [
    {
      "branches": ["+refs/heads/<RAMA_BASE>"],
      "daysToKeep": 30,
      "minimumToKeep": 5,
      "artifacts": ["drop"]
    },
    {
      "branches": ["+refs/heads/*", "-refs/heads/<RAMA_BASE>"],
      "daysToKeep": 7,
      "minimumToKeep": 1,
      "artifacts": ["drop"]
    }
  ]
}

Validar tras POST: que retentionRules quedó aplicado (algunas versiones Azure DevOps Server 2020 lo ignoran silenciosamente — warning si así).

Manejo de respuestas

  • HTTP 200: ✅ pipeline registrado. Mostrar URL: https://devops.example.org/<COL>/<PROJ>/_build?definitionId=<id>
  • HTTP 400/409 con "already exists": en modo edición es esperado. En modo creación inicial, ofrecer 4 opciones (vincular existente / nombre v2 / cancelar / borrar y recrear).
  • HTTP 401/403 (típico: <usuario> needs Use permissions for pool configurado (cicd.buildPool)): el usuario no tiene permiso Use sobre el pool configurado (cicd.buildPool). Es un gate de el equipo de infraestructura, no es verificable vía API antes del POST (por eso aflora aquí y no en FASE 0.4). NO reintentar — el script ya descubrió repoId + queueId, así que al reanudar el registro es inmediato. Acción a comunicar al usuario:
    • Pedir al equipo de infraestructura que conceda rol User (permiso Use) sobre Agent pools → el pool configurado → Security PARA EL GRUPO DEL PROYECTO ([<Proyecto>]\Contributors o Project Valid Users), NO para la identidad individual. Razón: si se concede solo al usuario actual, el siguiente dev del mismo proyecto que registre vuelve a bloquearse. Concedido al grupo, todo el equipo queda autorizado. Alternativa equivalente: activar "Grant access permission to all pipelines" del pool para el proyecto.
    • Quién paga el permiso: solo el primer dev que registra la definición, una vez por proyecto. Los demás devs que clonan un repo ya registrado NO necesitan el permiso — el azure-pipelines.yml ya está commiteado y la definición ya existe; solo hacen git push.
    • Tras conceder: re-ejecutar /hv:cicd-init (modo idempotente FASE 0.5 → opción "registrar definición") o el script standalone ops/cicd/registrar-pipeline-azure-devops.ps1 si se generó. El POST ahora pasa.
    • Si el usuario no puede esperar al equipo de infraestructura: documentar el bloqueador en _hilo/ESTADO_PROYECTO.json.infraestructura.cicd[] con repoId/queueId resueltos y continuar con las instrucciones manuales de UI de Azure DevOps.
  • HTTP 5xx / network: mostrar response + sugerir reintento o manual.

NO encolar el primer build vía API — dejar que git push lo dispare (memoria feedback_no_manual_queue).

Autorización canalización → pool (TEC-003, intento auto-servicio)

Tras crear la definición, el primer build puede quedar en notStarted con Checkpoint.Authorization: inProgress (agentes de build libres) — la canalización no está autorizada a usar el recurso pool configurado (cicd.buildPool). Distinto del permiso Use del USUARIO (que sirve para registrar/encolar, no para despachar). /hv:cicd-init debe intentar autorizar por API (auto-servicio si el dev es pool admin, validado en piloto Griddo Fase 2 def 13):

# R2 TLS 1.2+. $defId = id de FASE 2.5; $queueId = queue de el pool configurado.
$body = @{ pipelines = @(@{ id = $defId; authorized = $true }) } | ConvertTo-Json -Depth 5
$uri  = "$tfsUrl/$proj/_apis/pipelines/pipelinePermissions/queue/$queueId?api-version=5.1-preview.1"
try {
    Invoke-RestMethod -Uri $uri -Method Patch -Body $body -ContentType 'application/json' -UseDefaultCredentials | Out-Null
    Write-Host "OK: canalizacion autorizada al pool configurado (`cicd.buildPool`) por API (eres pool admin). Build desbloqueado."
} catch {
    $code = if ($_.Exception.Response) { [int]$_.Exception.Response.StatusCode } else { 0 }
    Write-Host "Autorizacion por API no permitida (HTTP $code) -> derivar a el equipo de infraestructura (banner 'Permit' o 'grant access to all pipelines')."
}
  • HTTP 200 → autorizado automáticamente, build desbloqueado sin pasar por el equipo de infraestructura (caso pool admin; frecuente en líder técnico / pilotos).
  • HTTP 401/403 → derivar al banner "Permit" del build o al equipo de infraestructura (Agent pools → el pool configurado → Security → grant access to all pipelines).

NO confundir con el Use del usuario (401/403 en el POST de FASE 2.5): son dos gates distintos.

Cola por defecto de la definición — queue NULL → "No pool was specified" (TEC-007)

Síntoma: TODO build (push, manual o API) falla instantáneo (startTime == finishTime, ~0s), con timeline vacío (ningún job arranca) y build.validationResults[].message = "No pool was specified.". Da igual dónde esté el pool: en el YAML (raíz, stage o job): el error persiste.

Causa: la definición de build tiene queue = NULL (sin pool por defecto). En Azure DevOps Server 2020 la definición necesita una queue por defecto además del pool: del YAML. El POST de esta FASE 2.5 ya incluye "queue": { "id": <queueId> }, pero un pipeline creado por el wizard de la UI (New pipeline → Existing YAML) se queda con queue=NULL → de ahí el fallo. Validado en piloto MyCompany.WebCorporativa (def 15: TODOS los builds instant-fail hasta asignar la cola por API).

Verificación OBLIGATORIA tras registrar — y también en FASE 0.5 si el pipeline ya existía (típico: creado por UI antes de /hv:cicd-init):

# $defId de FASE 2.5; $queueId = queue de el pool configurado en el proyecto; $poolId = 6
$d = Invoke-RestMethod -Uri "$tfsUrl/$proj/_apis/build/definitions/$defId`?api-version=5.0" -UseDefaultCredentials
if (-not ($d.PSObject.Properties.Name -contains 'queue') -or -not $d.queue) {
    $q = [pscustomobject]@{ id = $queueId; name = 'el pool configurado'; pool = [pscustomobject]@{ id = $poolId; name = 'el pool configurado' } }
    $d | Add-Member -NotePropertyName queue -NotePropertyValue $q -Force   # la propiedad puede NO existir
    $json = $d | ConvertTo-Json -Depth 40
    Invoke-RestMethod -Method Put -Uri "$tfsUrl/$proj/_apis/build/definitions/$defId`?api-version=5.0" -Body $json -ContentType 'application/json' -UseDefaultCredentials | Out-Null
    Write-Host "Cola por defecto (el pool configurado) asignada a la definicion $defId."
}

TRAMPA: el objeto de la definición puede venir sin la propiedad queue (ausente, no null) → $d.queue = ... lanza "The property 'queue' cannot be found on this object". Usar Add-Member -Force (añade o reemplaza).

Pre-requisito del PATCH de autorización (rol de la COLA, no del pool): para que el PATCH pipelinePermissions funcione en auto-servicio, el grupo del proyecto (Project Valid Users) debe tener rol User sobre la cola del proyecto — un proyecto nuevo suele crearla con Reader → el PATCH da AccessDenied aunque seas admin del pool de colección. Mismo gate de el equipo de infraestructura que el Use, pero a nivel de la cola. Validado: Griddo queue 3 = Project Valid Users → User (funciona); WebCorporativa queue 13 = Reader (bloqueaba) hasta cambiarlo a User. Comprobar con GET .../securityroles/scopes/distributedtask.agentqueuerole/roleassignments/resources/{projectId}_{queueId}.

FASE 2.5-gh — Environments y secretos en GitHub — SOLO github-actions, Fase ≥ 1

Idempotente: PUT crea o actualiza. Los ids de usuarios y equipos salen de gh api users/<login> --jq .id y gh api orgs/{{ORG}}/teams/<slug> --jq .id.

gh api -X PUT repos/{{ORG}}/{{REPO}}/environments/dev
gh api -X PUT repos/{{ORG}}/{{REPO}}/environments/pre --input - <<'JSON'
{"reviewers":[{"type":"User","id":<id>}],"deployment_branch_policy":{"protected_branches":false,"custom_branch_policies":true}}
JSON
gh api -X PUT repos/{{ORG}}/{{REPO}}/environments/pro --input - <<'JSON'
{"reviewers":[{"type":"Team","id":<team_id>}],"deployment_branch_policy":{"protected_branches":true,"custom_branch_policies":false}}
JSON

# secretos (P4-gh): el valor entra por stdin, nunca en la linea de comandos
gh secret set <CLAVE> --env pre < clave.txt
gh secret set HUB_SERVICE_KEY < hub-key.txt          # QR de calidad (FASE 2.7), secret de repositorio
gh variable set HUB_PROJECT_ID --body "<GUID>"       # no secreto

# verificar
gh api repos/{{ORG}}/{{REPO}}/environments --jq '.environments[] | {name, protection_rules}'

Reviewers de environment y ramas restringidas requieren repositorio público o plan Team/Enterprise: en Free privado, avisar y dejar pre/pro sin reviewers (el gate queda en el workflow_dispatch manual, G1). Si gh no está autenticado (pre-flight 0.4-gh), imprimir los comandos para que el usuario los ejecute.

Seguridad del repositorio (opt-in, con degradación)

Preguntar una vez (default [S] para lo gratuito, [n] para lo que exige licencia):

REPO=$(gh repo view --json nameWithOwner --jq .nameWithOwner)
# Gratis en todos los planes
gh api -X PUT "repos/$REPO/vulnerability-alerts"            # Dependabot alerts
gh api -X PUT "repos/$REPO/automated-security-fixes"        # Dependabot security updates (PRs automáticas)
# .github/dependabot.yml (version updates): git-best-practices/templates/dependabot.yml.template

# Gratis en repos PÚBLICOS; en privados exige GitHub Advanced Security (403/422 -> anotar y seguir)
gh api -X PATCH "repos/$REPO" --input - <<'JSON'
{"security_and_analysis":{"secret_scanning":{"status":"enabled"},"secret_scanning_push_protection":{"status":"enabled"}}}
JSON
# Code scanning: (a) default setup por API, o (b) el workflow security.yml (CodeQL + dependency review, SHA-pinned)
gh api -X PATCH "repos/$REPO/code-scanning/default-setup" -f state=configured -f query_suite=extended

Regla: ante 403/422 («Advanced Security must be enabled») no materializar security.yml, anotarlo en ops/cicd/SEGURIDAD_PIPELINE.md («cobertura: gate G8 + Dependabot alerts») y continuar. Si el usuario acepta el workflow y la licencia lo permite, materializar templates/github/security.yml.template → .github/workflows/security.yml (sello github-security; stack Vue/mixto añade javascript-typescript a la matriz). Nunca bloquear la adopción por licencia.

FASE 2.6 NUEVO Ovillo — Registro Hub MCP — SOLO Fase ≥ 1

Si .mcp.json referencia ovillo-hub y la Fase elegida ≥ 1:

🔗 Invocando tool MCP `register_pipeline` para registrar el pipeline
   en el Hub central Ovillo (ProjectId={projectId}, PipelineId={pipelineIdTfs}).

   Esto permitirá:
   - Dashboard tab CI/CD muestre el estado de tu pipeline
   - `/hv:cicd-status` local pueda consultar el Hub
   - Telemetría agregada cross-proyecto

Claude invoca el tool MCP con payload:

{
  "projectId": "<projectId from _hilo/.mcp-project.json>",
  "pipelineId": "<id devuelto por FASE 2.5>",
  "nombre": "<PIPELINE_NAME>",
  "url": "https://devops.example.org/<COL>/<PROJ>/_build?definitionId=<id>",
  "fase": <0|1|2>,
  "stages": ["Build", "DeployDev", "DeployDemo", "DeployProd"],  // según fase
  "stack": ".NET ASP.NET Core" | "Vue+Vite+TS"
}

GitHub Actions: pipelineId = nombre del fichero del workflow (cd-<slug>.yml, lo que aceptan gh workflow run y gh run list --workflow), url = https://github.com/{{ORG}}/{{REPO}}/actions/workflows/cd-<slug>.yml, stages = nombres de los jobs (build, quality, deploy-dev, deploy-pre, deploy-pro).

Best-effort: si el Hub no responde o el tool falla, mostrar warning + sugerir re-ejecutar mcp-sync luego. NO bloquear /hv:cicd-init.

FASE 2.7 — Publicar el Registro de Calidad (QR) al dashboard — Fase 2 + .NET con tests

Materialización: el workflow o pipeline ejecuta ops/cicd/scripts/Sync-QualityRecord.ps1, que /hv:cicd-init copia desde la skill calidad-codigo-sync (el plugin no vive en el repo del proyecto, así que CI no puede leer .claude/skills/). En GitHub Actions lo envuelve la composite action .github/actions/quality-sync con el secret HUB_SERVICE_KEY y la variable HUB_PROJECT_ID.

Para que cada build publique su Registro de Calidad (QR) en el dashboard de calidad del portfolio (hub v1.3.0+, vivo en 1.7.0), el stage Build incluye el step productor quality-sync (skill calidad-codigo-sync, mismo motor que el comando local /calidad-codigo-sync). Best-effort: NO gatea el build (el gate de cobertura sigue siendo coverage-gate.ps1, G7/R18) y no rompe nada sin la service-key (si HUB_SERVICE_KEY falta en el VG, el step loguea un warning y sale 0). Por eso se incluye por defecto en Fase 2 .NET con tests. Detalle: skills/calidad-codigo-sync/references/ci-wiring.md.

Preguntar al usuario (default SÍ — es inocuo sin la key): ¿Publicar el QR de calidad al dashboard en cada build? (best-effort; tendras que anadir HUB_SERVICE_KEY al Variable Group cuando quieras que empiece a publicar) [S/n]

Si SÍ (rellenar los marcadores del template fase2.dotnet):

  1. Step: sustituir el marcador # {{QUALITY_SYNC_STEP}} por - template: steps/quality-sync.yml y materializar steps/quality-sync.yml desde skills/cicd-architect/templates/steps/ a la carpeta steps/ del repo (junto a azure-pipelines.yml). Va en el stage Build, tras el reporte HTML de cobertura.
  2. Variables (no secretas): sustituir el marcador # {{QUALITY_SYNC_VARS}} por dos vars: qualityProjectId = projectId del hub (mcpSync.projectId de ESTADO_PROYECTO.json / _hilo/.mcp-project.json) y codeSearchBase = https://devops.example.org/<COL>/<PROJ>/_search?type=code&text=.
  3. OpenCover ya emitido: el dotnet test del template ya pasa Format=cobertura,opencover (desde h12) → el productor encuentra el *.opencover.xml en $(Agent.TempDirectory) sin el coverage.runsettings de la skill (ese runsettings solo hace falta en pipelines hand-rolled o netfx que no emitan opencover). El cobertura sigue alimentando el gate de cobertura (G7/R18) sin cambios.
  4. Service-key del Variable Group. Es lo único que el step necesita para publicar de verdad. Sub-pregunta (default Auto):

¿Configuro la service-key del dashboard automaticamente (zero-touch)? Usare tu apiKey per-dev para que el Hub emita la key y la dejare en el Variable Group (nunca se muestra). [1] Auto (recomendado) [2] Manual

  • [1] Auto — requiere _hilo/.mcp-credentials.json (apiKey per-dev) + Hub ≥ 1.7.0 + PipelineId (de FASE 2.5). Materializar Provision-QualityCiKey.ps1.template → ops/cicd/provision-quality-ci-key.ps1 sustituyendo {{ADO_COLLECTION_URL}}, {{ADO_PROJECT}}, {{PIPELINE_ID}} (def de FASE 2.5) y {{VG_NAME}} (<PIPELINE_NAME>-secrets o el VG elegido); los {{HUB_*}} el script los resuelve de las credenciales. Ejecutarlo en la máquina del dev (Windows auth a Azure DevOps, igual que registrar-pipeline-azure-devops.ps1 — NO en el sandbox del comando):
     pwsh ops/cicd/provision-quality-ci-key.ps1

Emite/rota la key vía Hub (POST /v2/sync/emit-service-key) y la deja isSecret en el VG + autoriza VG→canalización. La key NUNCA se imprime ni la maneja el agente — no la pidas ni la eco; solo lee el [OK]/[WARN] del script. Fallback automático a Manual si el script sale con exit ≠ 0: 3 (sin apiKey → irm|iex primero), 4 (apiKey rotada), 5 (Hub < 1.7.0), 6 (REST de Azure DevOps / el VG tiene otros secretos). El exit 0 con autorizada=manual significa que la key quedó puesta pero hay que autorizar el VG en la UI de Azure DevOps (no eres admin de Library).

  • [2] Manual — el admin emite la key una vez y la pega en el VG (vía clásica, sigue válida): EXEC mcp.EmitirServiceKey @ProyectoId='<GUID>', @Label='ci-quality', @ServiceKey=@k OUTPUT, @Id=@id OUTPUT (o mcp.EmitirServiceKeyRotando si quieres rotación limpia). Marcar la variable isSecret en el VG.

Mientras no haya key, el step no publica (warning, build verde). Tras configurarla (auto o manual), empieza a publicar sin re-/hv:cicd-init.

GitHub Actions (FASE 2.7): el job quality (composite .github/actions/quality-sync) ya viene en cd.fase2.dotnet.yml.template; sin Hub se elimina (rama condicional c). Variables: HUB_PROJECT_ID como variable de repositorio y code-search-base = https://github.com/<owner>/<repo>/search?q= (ya en el template). Service-key: [1] Auto materializa Provision-QualityCiKey.github.ps1.template → ops/cicd/provision-quality-ci-key.ps1 sustituyendo {{HUB_PROJECT_ID}}, {{HUB_SERVER_URL}} y {{GITHUB_REPO}} (owner/repo), y lo ejecuta en la máquina del dev (gh con admin del repo): emite la key vía Hub y la guarda con gh secret set por stdin, nunca la imprime; exit 6 = gh sin sesión o sin permiso → manual. [2] Manual: el admin emite por SQL y gh secret set HUB_SERVICE_KEY < key.txt

  • gh variable set HUB_PROJECT_ID --body <GUID>. Detalle: skills/calidad-codigo-sync/references/ci-wiring.md § 4-gh.

Si NO (al QR): eliminar del YAML generado los marcadores # {{QUALITY_SYNC_STEP}} y # {{QUALITY_SYNC_VARS}} (y no materializar steps/quality-sync.yml ni provision-quality-ci-key.ps1).

Tests de integración WebApplicationFactory (coverlet cuelga el testhost) → medir con dotnet-coverage por-proyecto (FB-008); ver ci-wiring.md §1-bis. El productor no necesita ReportGenerator (parsea el opencover directo, sin internet ni tool install). Si el hub es < v1.3.0 el step loguea [SKIP] y no falla.

netfx/Vue: N/A — netfx emite .coverage binario (no opencover) y Vue no tiene cobertura .NET. El QR es solo Fase 2 .NET SDK-style (coverlet). El marcador {{QUALITY_SYNC_STEP}} solo existe en el template fase2.dotnet.
