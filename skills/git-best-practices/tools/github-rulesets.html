Skill: git-best-practices Como se versionan y aplican los rulesets del repositorio con gh, en vez de configurarlos a mano en la UI.

Por que por API

  • El ruleset queda versionado en .github/rulesets/ y se revisa por PR como cualquier otro cambio.
  • Se aplica igual en todos los repositorios de la organizacion (o una vez a nivel de organizacion).
  • gh usa la sesion ya autenticada; no hay tokens que guardar.

Plantillas de esta skill: templates/branch-ruleset.json.template (rama por defecto) y templates/tag-ruleset.json.template (tags v*).

Requisitos

  • gh auth status con una cuenta admin del repositorio (o owner de la organizacion para rulesets de org).
  • Plan: los rulesets existen en todos los planes para repos publicos; en repos privados necesitan GitHub Pro, Team o Enterprise. La regla merge_queue necesita Team o Enterprise.
  • require_code_owner_review necesita un CODEOWNERS valido (templates/CODEOWNERS.template).
  • required_signatures necesita que todo el equipo firme (patterns/ssh-signing.md); si no, quitar la regla.

Aplicar el ruleset de la rama por defecto

Las plantillas llevan claves _description, _usage... para documentarse. La API no las admite: se eliminan antes del POST.

# 1. Copiar la plantilla al repo y ajustar (equipo, numero de revisores, checks)
mkdir -p .github/rulesets
cp "${CLAUDE_PLUGIN_ROOT}/skills/git-best-practices/templates/branch-ruleset.json.template" .github/rulesets/branch-main.json

# 2. Quitar las claves _ y crear el ruleset
node -e "const w=x=>Array.isArray(x)?x.map(w):(x&&typeof x==='object')?Object.fromEntries(Object.entries(x).filter(([k])=>!k.startsWith('_')).map(([k,v])=>[k,w(v)])):x;process.stdout.write(JSON.stringify(w(JSON.parse(require('fs').readFileSync(process.argv[1],'utf8')))))" .github/rulesets/branch-main.json > /tmp/ruleset.json
gh api -X POST repos/{{ORG}}/{{REPO}}/rulesets --input /tmp/ruleset.json --jq '{id, name, enforcement}'

Con jq disponible, el paso 2 es:

jq 'walk(if type == "object" then with_entries(select(.key | startswith("_") | not)) else . end)' .github/rulesets/branch-main.json > /tmp/ruleset.json

En PowerShell 7 el filtrado es el mismo script de Node (viene con Ovillo) o ConvertFrom-Json -AsHashtable recorriendo el objeto.

Aplicar el ruleset de tags

cp "${CLAUDE_PLUGIN_ROOT}/skills/git-best-practices/templates/tag-ruleset.json.template" .github/rulesets/tags-release.json
# mismo filtrado de claves _ que arriba
gh api -X POST repos/{{ORG}}/{{REPO}}/rulesets --input /tmp/ruleset.json --jq '{id, name, enforcement}'

Actualizar, listar, borrar

gh api repos/{{ORG}}/{{REPO}}/rulesets --jq '.[] | {id, name, target, enforcement}'   # listar
gh api -X PUT repos/{{ORG}}/{{REPO}}/rulesets/{{ID}} --input /tmp/ruleset.json            # actualizar
gh api -X DELETE repos/{{ORG}}/{{REPO}}/rulesets/{{ID}}                                   # borrar

Verificar lo que realmente aplica a una rama

Los rulesets se suman a las branch protection rules antiguas. Lo que ve una rama concreta:

gh api repos/{{ORG}}/{{REPO}}/rules/branches/main --jq '.[] | {type, ruleset_id}'
gh api repos/{{ORG}}/{{REPO}}/codeowners/errors --jq '.errors'    # [] si CODEOWNERS es valido

Detalles que rompen si no se cuidan

DetalleQue pasa si se ignora
required_status_checks.context es el name: del job, no su idEl check "no aparece" y el PR queda bloqueado para siempre. El template CI usa Build y Security
merge_queue sin merge_group: en el workflowLa cola espera checks que nunca corren; los PRs se quedan en la cola hasta el timeout
strict_required_status_checks_policy: trueCada PR debe estar al dia con main; con merge queue es lo que se quiere, sin ella genera re-runs
bypass_mode: "always" en la rama por defectoUn admin puede hacer push directo saltandose todo. En main usar "pull_request"; "always" solo en el ruleset de tags
~DEFAULT_BRANCHSigue a la rama por defecto aunque cambie de nombre; preferir a refs/heads/main
enforcement: "evaluate"Modo simulacion (solo Enterprise): registra que habria bloqueado sin bloquear. Util una semana antes de activar
Branch protection rules antiguas + rulesetsSe aplican las dos. Migrar y borrar las antiguas para tener una sola fuente

Rulesets a nivel de organizacion

El mismo JSON, con conditions.repository_name para elegir a que repositorios aplica:

# anadir a conditions:  "repository_name": { "include": ["~ALL"], "exclude": ["sandbox-*"], "protected": true }
gh api -X POST orgs/{{ORG}}/rulesets --input /tmp/ruleset.json

Un ruleset de organizacion no lo puede relajar el admin de un repositorio: es la forma de que la politica de la organizacion (ecosystem.config.json -> vcs) sea la que manda.

Relacion con el resto del ecosistema

  • /hv:cicd-release empuja tags v*: el ruleset de tags evita que se borren o se muevan.
  • El workflow de templates/github-workflow.yml.template publica los checks Build y Security que el ruleset exige, y se dispara con merge_group.
  • patterns/azure-devops-branching.md describe el equivalente en Azure DevOps (branch policies), que no tiene merge queue nativa.
