Contenido

Solo usuario: lleva disable-model-invocation: true, asi que el modelo no puede lanzarla por su cuenta ni su descripcion entra en contexto. Se ejecuta solo con /hv:cicd-deploy.

Despliega un proyecto a Dev / Pre / Pro bajo demanda. NO despliega en cada push: el deploy lo decides tú con este comando.

  • Azure DevOps (Server o Services): encola el pipeline vía REST con la variable DeployEnv=<env>.
  • GitHub Actions: despacha el workflow con gh workflow run cd-<slug>.yml -f environment=<env>.

Audiencia: desarrolladores con un pipeline en Fase 2 (CD) ya generado por /hv:cicd-init. Plataforma: resolve('cicd.platform') (Hilo infraestructura.cicd.plataforma › ecosystem.config.json → cicd.platform; .claude/CONFIGURACION.md §Resolución): azure-pipelines | github-actions.

Extended Thinking Mode

think hard

El deploy lo ejecuta el agente o runner de deploy (MSDeploy al IIS destino, azure/webapps-deploy, contenedor…), NO la máquina del desarrollador. Este comando solo pide el deploy: en Azure encola el pipeline con DeployEnv=<env> y el stage corre en el agente con capability DeployTarget=<env>; en GitHub despacha el workflow con inputs.environment=<env> y solo corre el job deploy-<env> (los demás tienen if: que no matchea). NUNCA hagas MSDeploy ni copia de archivos directa desde el cliente.

Sintaxis

/cicd-deploy --env <dev|pre|pro> [--entrypoint <slug>] [--tag vX.Y.Z | --commit <sha>] [--watch] [--dry-run] [--yes]
FlagDescripción
--envObligatorio. Entorno destino: dev, pre o pro.
--entrypointOpcional. Slug del entrypoint a desplegar (R25). Si la solución tiene >1 pipeline y se omite → listar y preguntar. Con 1 solo, se infiere. Cada entrypoint = su propia definición (<PROYECTO>-<slug>) o su propio workflow (cd-<slug>.yml); su destino (`DeployTarget=<env>-<app\svc> · environment: <env>`) ya va horneado en su YAML.
--tagOpcional. Despliega la versión de ese tag. Por defecto, HEAD de la rama base.
--commitOpcional. Despliega ese commit SHA. Mutuamente excluyente con --tag. Solo Azure DevOps (sourceVersion): GitHub solo despacha sobre una rama o un tag → crear un tag sobre ese commit y usar --tag.
--watchOpcional. Sigue el estado de la run hasta que termine (polling 30s · gh run watch).
--dry-runOpcional. Muestra qué encolaría/despacharía (URL, body o comando, entorno) sin ejecutarlo.
--yesOpcional. Salta la confirmación (deploy directo) en el entorno pedido, aunque su deployConfirm esté activo. No salta los reviewers de un environment de GitHub: esos aprueban en la plataforma.

CUÁNDO USAR

  • Tras un /hv:cicd-release (o un push que generó un Build verde) cuando quieras promover ese artefacto a un entorno.
  • Para re-desplegar una versión anterior (--tag vX.Y.Z): es la capa 2 del rollback (G9).

NO usar para:

  • Generar o promocionar el pipeline → /hv:cicd-init.
  • Versionar/disparar el build → /hv:cicd-release.
  • Ver el estado de builds → /hv:cicd-status.
  • Proyectos en Fase 0 o Fase 1 (no tienen stages/jobs de CD): este comando ABORTA con mensaje accionable.

FASE 0 — Validaciones previas

0.1 Leer estado CI/CD del proyecto

Leer _hilo/ESTADO_PROYECTO.json.infraestructura.cicd (objeto { plataforma, pipelines[] }; R25: N entradas, una por entrypoint). Seleccionar la del entrypoint a desplegar:

  • Si --entrypoint <slug> → esa entrada. Si se omite y hay 1 entrypoint → esa. Si hay >1 → listar (entrypoint, tipo, serverType) y preguntar cuál.
  • De la entrada elegida: pipelineId (id de definición · fichero del workflow), yamlFile, fase, nombre, url, stages, stack, tipo, serverType, publico, deployConfirm, modeloDeploy.
  • Plataforma: resolve('cicd.platform') (equivale a cicd.plataforma del Hilo y, si falta, ecosystem.config.json → cicd.platform).
  • Azure DevOps: datos de conexión (infraestructura.azureDevOps.url, cicd.serverUrl del ecosystem.config, o derivar de la url del pipeline).
  • GitHub: repo=$(gh repo view --json nameWithOwner --jq .nameWithOwner) y wf=<pipelineId> (ej. cd-web.yml).
  • El destino (serverType app/svc en Azure · environment: en GitHub) ya está horneado en el YAML de ese entrypoint: /hv:cicd-deploy NO lo decide, solo pide el deploy con <env>.

0.2 Gate de fase (BLOQUEANTE)

SI fase < 2:
  ❌ "El pipeline '<nombre>' está en Fase <fase> (sin stages/jobs de CD).
      /cicd-deploy requiere Fase 2 (pipeline completo).
      Promociona con: /cicd-init  → opción 'promocionar a Fase 2'."
  exit 0

0.3 Validar entorno solicitado

  • --env ∈ {dev, pre, pro}. Si no, error.
  • Azure: verificar que el stage de deploy de ese entorno existe en stages (DeployDev, DeployPre/DeployDemo, DeployProd).
  • GitHub: verificar que el job deploy-<env> existe en stages (o en el YAML: ^\s*deploy-<env>:) y que workflow_dispatch.inputs.environment.options incluye <env>.
  • Si el entorno no tiene stage/job generado, sugerir /hv:cicd-init → "añadir stage".

0.4 Pre-flight de conectividad

Azure DevOps — R2, forzar TLS 1.2+ antes de cualquier HTTPS:

try {
    [Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12 -bor [Net.SecurityProtocolType]::Tls13
} catch { [Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12 }

Verificar GET {col}/_apis/connectionData?api-version=6.0 → 200. Si 401/403, avisar que faltan credenciales o permiso de cola sobre el pipeline.

GitHub Actions — sesión de gh y workflow despachable:

gh auth status                                                  # sin sesión: gh auth login (el pre-flight de /cicd-init ya avisa)
gh api "repos/$repo/actions/workflows/$wf" --jq '.state'        # active · disabled_manually · 404 = el fichero NO está en la rama por defecto
gh api "repos/$repo/environments/<env>" --jq '[.protection_rules[]?.type] | join(",")'   # required_reviewers => la run esperará aprobación

workflow_dispatch solo ve los workflows que existen en la rama por defecto. Un cd-<slug>.yml recién creado en una rama feature no se puede despachar hasta que llega a main (--ref elige después qué versión del fichero se ejecuta).

FASE 1 — Confirmación por entorno (configurable)

Política por defecto: Dev y Pre = deploy directo; Prod = confirmación. Configurable por proyecto en _hilo/ESTADO_PROYECTO.json.infraestructura.cicd.pipelines[].deployConfirm: { dev:false, pre:false, pro:true } (override por entrypoint). --yes fuerza directo en cualquier entorno; si deployConfirm[env]=true, pedir confirmación.

EntornoConfirmación (default)
devDirecto (no pregunta): mostrar destino/versión informativo
preDirecto por defecto (configurable a confirmar): mostrar entorno, URL destino, versión/commit
proConfirmación por defecto + doble check: mostrar aprobadores, balanceo, estrategia rolling

Ejemplo de confirmación para pre:

⚠️  DEPLOY A PRE — confirmar
    Proyecto:   MyCompany.Griddo
    Pipeline:   MyCompany.Griddo-CI (id=10)          | Workflow: cd-web.yml
    Entorno:    pre  (servidor: <server>, URL: <url>)
    Versión:    vX.Y.Z (o HEAD <sha7>)
    Gate:       el stage DeployPre / job deploy-pre aplicará security-gate + smoke test + rollback (G8/G14/G9)
    GitHub:     el environment `pre` tiene reviewers → la run quedará en espera hasta que aprueben en GitHub

    ¿Continuar? (escribe 'pre' para confirmar)

NUNCA desplegar a un entorno con deployConfirm[env]=true (por defecto Prod) sin confirmación explícita del usuario. En GitHub, la confirmación de este comando es el primer gate y los required reviewers del environment el segundo: este comando nunca aprueba un environment por API.

FASE 2 — Pedir el deploy

Derivación de <ref> (depende del modelo de deploy elegido en P2-bis de /hv:cicd-init; igual en ambas plataformas):

ModelosourceBranch (Azure) · --ref (GitHub)
on-demand / autorefs/heads/<ramaBase> · <ramaBase> (de configuracion.branching.ramaBase); con --tag, el tag
branch-gated (R24)derivar del entorno pedido: dev/pre → <ramaDevelop>, pro → <ramaBase> (mapeo R24, leer configuracion.branching)

En branch-gated, pedir --env pro sobre la rama de develop produce una run cuyo stage DeployProd / job deploy-pro no matchea su condition / if: por rama → el deploy se salta (a propósito). Si el usuario lo intenta, avisar ANTES de encolar.

2-ado — Azure DevOps: encolar vía REST

R3: usar PowerShell + REST (no tasks Node). Encolar el build con DeployEnv=<env>:

# [bloque TLS 1.2+ R2 ya aplicado en FASE 0.4]
$headers = @{ Authorization = "Bearer $env:SYSTEM_ACCESSTOKEN" }   # o -UseDefaultCredentials con credenciales Windows
$col  = '<System.CollectionUri>'
$proj = '<TeamProject>'
$body = @{
    definition  = @{ id = <pipelineId> }
    sourceBranch = 'refs/heads/<rama>'          # ver derivacion arriba; o refs/tags/<tag> si --tag
    # sourceVersion = '<sha>'                    # si --commit
    parameters  = (@{ DeployEnv = '<env>' } | ConvertTo-Json -Compress)
} | ConvertTo-Json -Depth 6

# --dry-run: imprimir $body y la URL, NO ejecutar
Invoke-RestMethod -Uri "$col$proj/_apis/build/builds?api-version=6.0" -Method POST -Headers $headers -Body $body -ContentType 'application/json'

DeployEnv debe estar declarada como variable settable at queue time en la definición (lo configura /hv:cicd-init en Fase 2). El stage Deploy<Env> lleva condition: eq(variables['DeployEnv'], '<env>'), así que SOLO corre cuando se encola con ese valor. Un push normal (sin DeployEnv) construye pero NO despliega.

Manejo de respuestas (Azure)

  • HTTP 200: ✅ build encolado. Mostrar buildNumber + URL de la run.
  • HTTP 400 DeployEnv is not a valid ... queue time variable: la definición no tiene DeployEnv como queue-time. Causa: pipeline generado antes del modelo on-demand. Fix: /hv:cicd-init → "actualizar YAML" para regenerar con el modelo DeployEnv.
  • HTTP 403: falta permiso de cola sobre el pipeline. Escalar al equipo de infraestructura (rol Queue builds).

2-gh — GitHub Actions: despachar el workflow

# --dry-run: imprimir el comando y salir
gh workflow run "$wf" --ref "<ref>" -f environment=<env>

# El dispatch es asíncrono y NO devuelve el id de la run: localizarla (hasta 5 intentos, 3 s).
# Aceptar solo una run creada DESPUÉS del dispatch (comparar createdAt con la hora del comando).
for i in 1 2 3 4 5; do
  run=$(gh run list --workflow "$wf" --event workflow_dispatch --branch "<ref>" --limit 1 \
        --json databaseId,url,status,createdAt,headSha --jq '.[0]')
  [ -n "$run" ] && break
  sleep 3
done

El push a la rama base ejecuta solo build (G1); los jobs deploy-* llevan if: github.event_name == 'workflow_dispatch' && inputs.environment == '<env>'. Con --ref vX.Y.Z, gh run list --branch filtra por el nombre del tag (GitHub lo expone como headBranch).

Manejo de respuestas (GitHub)

  • exit 0: ✅ workflow despachado. Mostrar databaseId + URL de la run (y el headSha que se despliega).
  • HTTP 422 Workflow does not have 'workflow_dispatch' trigger: el fichero de la rama por defecto no tiene el trigger (modelo auto antiguo o YAML editado). Fix: /hv:cicd-init → Opción 4 (re-render) y merge a la rama por defecto.
  • HTTP 422 Required input 'environment' not provided / Unexpected inputs provided: el workflow no espera environment (o espera otro nombre). Mismo fix: re-render con el modelo on-demand.
  • HTTP 404 Not Found: $wf mal escrito, o el workflow no está en la rama por defecto (ver 0.4). Hacer merge primero.
  • HTTP 403 Resource not accessible by integration / Must have admin rights: el token de gh no tiene el scope workflow → gh auth refresh -h github.com -s workflow; o Actions deshabilitadas en Settings → Actions.
  • This workflow is disabled: gh workflow enable "$wf" y reintentar.

FASE 3 — Seguimiento (--watch) y registro

Azure: con --watch, poll GET {col}{proj}/_apis/build/builds/{buildId}?api-version=6.0 cada 30s hasta status=completed. Mostrar result (succeeded / failed / canceled).

GitHub: con --watch:

gh run watch <databaseId> --interval 30 --exit-status     # exit != 0 si la run falla
gh run view  <databaseId> --json conclusion,jobs --jq '{conclusion, jobs: [.jobs[] | {name, conclusion}]}'

Si la run queda en status=waiting, el environment tiene required reviewers: mostrar quién debe aprobar y la URL, y no aprobar desde aquí.

gh api "repos/$repo/actions/runs/<databaseId>/pending_deployments" \
  --jq '.[] | "environment=\(.environment.name) reviewers=\([.reviewers[].reviewer.login] | join(","))"'

Tras una run con resultado succeeded / success:

  1. Actualizar _hilo/ESTADO_PROYECTO.json: metricas.ultimo_deploy + infraestructura.cicd.pipelines[].ultimoBuildStatus.
  2. Registrar en el Hub (si .mcp.json referencia ovillo-hub): /hv:mcp-sync envía cicd-batch con el último build y el historial de deploys por entorno (los recoge de la plataforma: REST de Azure DevOps o gh). Best-effort: no fallar el comando si el Hub no responde.

Si el deploy falla en pre/pro, el rollback tiene tres capas (G9): backup previo del step Deploy (Azure: steps/rollback-*; GitHub: el step Deploy del template), re-desplegar la versión anterior con este mismo comando (--tag <anterior> · gh workflow run "$wf" --ref <sha_o_tag_anterior> -f environment=<env>), y el manual de ops/cicd/RUNBOOK.md.

REGLAS CRÍTICAS

  • NUNCA desplegar a un entorno con deployConfirm=true (default Prod) sin confirmación explícita.
  • NUNCA hacer MSDeploy/copia directa desde el cliente: el agente o runner de deploy lo hace.
  • NUNCA encolar/despachar si fase < 2.
  • NUNCA aprobar un environment de GitHub por API desde este comando: los reviewers aprueban en la plataforma.
  • Azure: SIEMPRE TLS 1.2+ (R2) antes de tocar Azure DevOps Server; SIEMPRE encolar vía REST + PowerShell (R3), no tasks Node.
  • GitHub: SIEMPRE gh workflow run (o POST /repos/{o}/{r}/actions/workflows/{wf}/dispatches); el environment va como input, nunca hardcodeado en el YAML.
  • El push NO despliega; el deploy es on-demand vía este comando (Azure: modelo DeployEnv, R20 · GitHub: workflow_dispatch + environment:, G1).
