Ficheros del pack 0

Solo SKILL.md.

Contenido

Solo usuario: lleva disable-model-invocation: true, asi que el modelo no puede lanzarla por su cuenta ni su descripcion entra en contexto. Se ejecuta solo con /hv:verify.

USE FOR: verificar el CÓDIGO antes de commit/PR (build, format, lint, tests, cobertura, docs, clean — 7 fases con short-circuit). DO NOT USE FOR: verificar/corregir el archivo CLAUDE.md del proyecto → usar /hv:verificar-claude.

REGLAS CRITICAS

  • Si la Fase 1 (Build) falla: DETENER el pipeline inmediatamente (short-circuit): sin binarios no hay nada que medir.
  • Si la Fase 4 (Tests) falla con tests en rojo: DETENER. No tener proyecto de tests NO es un fallo (es WARN) y no detiene nada: la Fase 5 (Seguridad) es la unica cuyo hallazgo siempre es FAIL, y tiene que ejecutarse igual.
  • Si alguna fase tiene FAIL: el resultado global es FAIL
  • Si solo hay WARN: el resultado global es WARN (se puede proceder con precaucion)
  • Si todo es PASS: el resultado global es PASS (listo para commit/PR)
  • Mostrar SIEMPRE la tabla resumen al final

1. Detectar el objetivo de compilacion

El objetivo lo resuelve una sola funcion del ecosistema (ADR-037), no esta skill. No buscar .sln a mano:

node "${CLAUDE_PLUGIN_ROOT}/hooks/build-target.js" --json

En instalacion por zip (sin plugin), la ruta es node .claude/hooks/build-target.js --json.

Devuelve { objetivo, tipo, candidatos, tests, motivo } y su codigo de salida dice el caso:

ExitSituacionQue hacer
0objetivo resuelto (tipo: solucion o proyecto)guardar objetivo en $TARGET y continuar
3varios candidatosmostrar candidatos numerados y preguntar cual usar; no continuar sin respuesta
4no hay nada compilableinformar con motivo y abortar: no hay codigo .NET que verificar

Un repositorio de un solo .csproj y sin solucion es un caso normal, no un problema: el SDK acepta proyecto, solucion o directorio. Guardar tambien la lista tests para la Fase 4.

2. Fase 1: Build

Ejecutar:

dotnet build "$TARGET" --no-incremental 2>&1
  • Si el exit code es distinto de 0: registrar FAIL, contar errores, y DETENER el pipeline.
  • Si hay 0 errores: registrar PASS.
  • Guardar el numero de warnings para la Fase 2.

3. Fase 2: Diagnosticos

Intentar primero usar MCP get_diagnostics si esta disponible. Si no:

dotnet build "$TARGET" -warnaserror 2>&1

Contar el numero de warnings/diagnosticos.

  • 0 warnings: PASS
  • 1+ warnings: WARN con el conteo

4. Fase 3: Anti-patrones

Intentar primero usar MCP detect_antipatterns si esta disponible. Si no, buscar manualmente en archivos .cs (excluyendo obj/, bin/, Migrations/):

PatronBuscarSeveridad
DateTime.NowDateTime.Now (usar DateTime.UtcNow o TimeProvider)WARN
new HttpClientnew HttpClient( (usar IHttpClientFactory)WARN
async voidasync void (excepto event handlers)WARN
.Result.Result o .Wait() en codigo asyncWARN
Console.WriteConsole.Write en proyectos no-consolaWARN
Thread.SleepThread.Sleep (usar Task.Delay)WARN
  • 0 violaciones: PASS
  • 1+ violaciones: WARN con el conteo y detalle

5. Fase 4: Tests

Primero comprobar si hay proyectos de test, con la lista tests del paso 1 (o --tests):

node "${CLAUDE_PLUGIN_ROOT}/hooks/build-target.js" --tests

Un proyecto es de test si declara <IsTestProject>true</IsTestProject> o referencia Microsoft.NET.Test.Sdk.

  • Lista vacia: registrar WARN "Sin proyecto de tests" y continuar con la Fase 5. Nunca FAIL: no tener tests es una carencia del proyecto, no un fallo de la verificacion. Y nunca lanzar dotnet test en ese caso, porque sale con exit 0 sin ejecutar nada y se registraria un PASS falso con cero tests.

Con al menos un proyecto de test, ejecutar:

dotnet test "$TARGET" --no-build --verbosity normal 2>&1
  • Si el exit code es distinto de 0: registrar FAIL con el numero de tests fallidos, y DETENER el pipeline.
  • Si todos pasan: PASS con el conteo total de tests.

6. Fase 5: Escaneo de seguridad

Buscar en archivos .cs, .json, .xml, .config (excluyendo obj/, bin/):

PatronBuscar
Connection strings hardcodedServer=.*Password= o Data Source=.*pwd= en .cs
API keysapikey, api_key, secret, password asignados a string literal
Certificados en repoarchivos .pfx, .key, .pem en el repositorio
Tokens hardcodedBearer seguido de string literal
  • 0 hallazgos: PASS
  • 1+ hallazgos: FAIL con detalle (seguridad siempre es FAIL, no WARN)

7. Fase 6: Formato

Ejecutar:

dotnet format "$TARGET" --verify-no-changes --verbosity diagnostic 2>&1
  • Exit code 0: PASS (formato correcto)
  • Exit code distinto de 0: WARN "Se requieren cambios de formato. Ejecutar dotnet format"
  • Si dotnet format no esta disponible: WARN "dotnet format no disponible"

8. Fase 7: Revision del diff

Ejecutar:

git diff --stat
git diff --cached --stat

Analizar:

  • Archivos con >500 lineas cambiadas: listarlos como WARN
  • Archivos .cs nuevos sin test correspondiente (buscar *Tests.cs): listar como WARN
  • Si no hay cambios: PASS "Sin cambios pendientes"
  • Si hay cambios normales: PASS con resumen

9. Generar tabla resumen

Construir la tabla con los resultados de todas las fases ejecutadas:

## Resultado Verificacion

| Fase | Estado | Detalle |
|------|--------|---------|
| 1. Build | {estado} | {detalle} |
| 2. Diagnosticos | {estado} | {detalle} |
| 3. Anti-patrones | {estado} | {detalle} |
| 4. Tests | {estado} | {detalle} |
| 5. Seguridad | {estado} | {detalle} |
| 6. Formato | {estado} | {detalle} |
| 7. Diff review | {estado} | {detalle} |

### Resultado global: {PASS|WARN|FAIL}

Iconos de estado:

  • PASS: ✅ PASS
  • WARN: ⚠️ WARN
  • FAIL: ❌ FAIL
  • SKIP: ⏭️ SKIP (si se detuvo por short-circuit)

Si el resultado global es PASS: "Listo para commit/PR" Si el resultado global es WARN: "Proceder con precaucion. Revisar los avisos." Si el resultado global es FAIL: "NO proceder. Corregir los errores antes de commit/PR."

Skill verify · kind: workflow

DELEGACION EN AGENTS

Estos agents trabajan en su propio contexto: devuelven un resumen y no gastan el de la sesion (ADR-028). Se invocan con la herramienta Task.

test-runner

Cuando hay que ejecutar y analizar los tests, no solo comprobar que compilan:

Task tool con:
  subagent_type: test-runner
  prompt: "Ejecutar los tests de {objetivo}, analizar los fallos y evaluar la cobertura.
              Devolver los tests que faltan para los metodos sin cubrir."
