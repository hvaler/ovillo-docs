Contenido

Este skill genera código CRUD completo siguiendo los estándares de la organización. Las plantillas son una sola familia (ADR-031): un vocabulario de placeholders, un fichero generado por plantilla, un namespace de fichero por fichero con los using al principio, y el conjunto compila junto (lo comprueba scripts/check-crud-templates.js en cada release del ecosistema).

PRIMERO: qué estilo arquitectónico

Antes de generar nada, leer configuracion.arquitectura.estilo de _hilo/ESTADO_PROYECTO.json (precedencia completa en .claude/CONFIGURACION.md) y usar el subdirectorio que le corresponda:

EstiloPlantillasQué emite
clean (default)templates/clean/27 plantillas en cuatro capas: Domain · Application · Infrastructure · Api
vertical-slicestemplates/vertical-slices/13: un fichero por caso de uso (petición, validación, handler y endpoint juntos) más lo compartido
n-layertemplates/n-layer/7: Api → Services → Repository → BD. Es el perfil BÁSICO del wizard, y su entidad es un POCO: las reglas viven en el servicio
hexagonaltemplates/hexagonal/9: núcleo con sus puertos (entrada y salida) y adaptadores alrededor. EF Core solo existe dentro del adaptador de salida
minimaltemplates/minimal/3: entidad, contexto con el mapeo dentro, y los endpoints hablando con él directamente

No mezclar los dos juegos. Cada uno es coherente consigo mismo y con las reglas de arquitectura de su estilo; combinarlos produce código que ninguna de las dos las cumple.

templates/vertical-slices/compartidas.json declara las plantillas de clean/ que ese estilo reutiliza tal cual —el modelo de dominio— en vez de copiarlas. No es economía de ficheros: un modelo compartido es lo que hace posible la independencia entre slices, porque si cada feature tuviera su entidad, la que necesitara la de otra tendría que referenciar esa feature.

SEGUNDO: con qué se llega a la base

El estilo decide dónde vive el acceso a datos; esto decide con qué. Son dos dimensiones aparte, y por eso las plantillas que tocan la base viven en templates/<estilo>/datos/<modo>/ y las demás están fuera: cambiar de modo no cambia el resto del estilo.

Leer configuracion.arquitectura.accesoDatos de _hilo/ESTADO_PROYECTO.json (precedencia completa en .claude/CONFIGURACION.md; default de organización en ecosystem.config.json → database.accessMode):

ModoQué emiteEstilos que lo tienen hoy
efcore (default)DbContext, IEntityTypeConfiguration y LINQlos cinco
dapper-spDapper invocando procedimientos, más el .sql que los crealos cinco
dapperDapper con el SQL en el códigolos cinco
ado-spSqlCommand a pelo contra procedimientos, sin ORM ni micro-ORMn-layer, minimal

Cuántas plantillas cuesta el modo dice lo que cada estilo aísla, y es la misma medida de antes vista desde el otro lado:

Estiloefcoredapper-spdapperQué cambia
hexagonal311solo el adaptador de salida — el núcleo no se toca
minimal211no hay contexto que declarar
n-layer321 (+1 reutilizada)
clean643 (+1 reutilizada)sin contexto, mapeo ni interceptores
vertical-slices755el fichero entero se duplica aunque solo cambie el handler: la unidad es la feature

dapper y dapper-sp comparten lo que no depende de dónde viva el SQL — abrir la conexión en n-layer, la unidad de trabajo en clean —, y se declara en templates/<estilo>/datos/<modo>/compartidas.json en vez de copiarse: dos copias idénticas divergen a la tercera corrección.

ado-sp solo existe para los dos estilos con entidad POCO, y no por falta de trabajo. ADO.NET puro materializa asignando propiedades, así que solo puede construir entidades con setters públicos. La entidad de clean —y la de hexagonal, y la que vertical-slices reutiliza— tiene private set y constructor privado: EF Core y Dapper la rellenan por reflexión, ADO.NET no. La encapsulación del dominio decide qué modos son posibles, que es lo contrario de lo que uno esperaría.

Si el modo configurado no existe para el estilo del proyecto, decirlo y parar: no hay que traducir a mano el juego de otro estilo. Qué combinaciones existen lo dice el árbol de templates/, y la tabla de x-support del schema no puede prometer más que él — hay un caso de test-config que lo comprueba.

Con procedimientos, el .sql se genera también

templates/sql/<motor>/Procedimientos.sql.template emite los seis procedimientos que el C# invoca, con la nomenclatura {schema}.{Accion}{Entidad} que ya exige sql-nomenclatura-guard. Generar solo el C# dejaría los procedimientos a mano, y los nombres se irían del convenio a la tercera entidad. Los nombres del .sql y los que el C# invoca se cruzan en la puerta de release: un procedimiento declarado y no usado, usado y no declarado, o con prefijo usp_/sp_, es un fallo.

Lo que el modo cambia en el contrato

El repositorio de n-layer no tiene SaveAsync: con procedimientos no hay change tracker que confirmar, así que un SaveAsync que no hace nada dejaría al servicio creyendo que ha persistido. El contrato es Task<bool> UpdateAsync(id, entidad, ct), que vale igual en los dos modos — EF Core guarda y devuelve si encontró la fila; el procedimiento devuelve su @@ROWCOUNT.

En clean el mismo defecto era mayor y está en Domain: Add y Update marcaban sin escribir, y GetByIdAsync prometía una entidad rastreada, así que el handler que la mutaba y llamaba a SaveChangesAsync no escribía nada con procedimientos — 204 sin tocar la base. Ahora son AddAsync y UpdateAsync, y mutar un agregado no lo persiste: hay que llamar a UpdateAsync. Bajo EF Core sobre una entidad ya rastreada no cuesta nada; con procedimientos es la escritura.

IUnitOfWork se queda, y no es un residuo de EF Core: «unidad de trabajo» significa que el caso de uso se aplica entero o no se aplica — la definición de Fowler, anterior a los dos motores. EF Core la implementa volcando el change tracker; dapper-sp la implementa con el commit de una transacción que se abre perezosamente en la primera escritura. El handler es el mismo.

Es el criterio general: si una operación del contrato solo tiene sentido con un motor detrás, el contrato está describiendo el motor y no la intención.

  1. Nueva entidad - Crear todas las capas para una nueva entidad
  2. API endpoints - Generar Controller (o Minimal API) + CQRS + Repository

Uso Rápido

Solicitar un CRUD

"Crea un CRUD completo para la entidad Scholarship con los campos:
- Id (int, PK)
- Name (string, 200 chars, requerido)
- Description (string, opcional)
- Amount (decimal, requerido, > 0)
- Status (enum: Draft, Published, Closed)"

Claude generará

  1. Entidad con factoría y validaciones de dominio (DomainException)
  2. DTOs y mapper Mapperly (RequiredMappingStrategy.Target: todo campo del DTO viene de la entidad)
  3. Commands / Queries y sus handlers (Mediator, ValueTask)
  4. Validadores FluentValidation sobre los commands
  5. Repositorio (puerto en Application, implementación EF Core en Infrastructure)
  6. Configuración EF Core (tabla, auditoría, soft delete con query filter)
  7. Controller versionado o Minimal API versionada, a elección
  8. Las plantillas de una vez que falten en el proyecto, y el DbSet en ApplicationDbContext

Paquetes: Mediator.Abstractions + Mediator.SourceGenerator (MIT; MediatR es comercial desde v13), Riok.Mapperly, FluentValidation, Asp.Versioning.Mvc (controllers) o Asp.Versioning.Http (Minimal API).

Handler

public async ValueTask<ScholarshipDto> Handle(CreateScholarshipCommand request, CancellationToken ct)
{
    var entity = Scholarship.Create(request.Name, request.Description);   // reglas de dominio
    _repository.Add(entity);
    await _unitOfWork.SaveChangesAsync(ct);
    return _mapper.ToDto(entity);
}

UnicidadMustAsync + repository check

Los mensajes van en inglés siempre (ADR-001 D3, ADR-027, ADR-073): validación, ProblemDetails, excepciones y log viajan al cliente y a repositorios ajenos, así que no dependen de organization.language — esa clave gobierna la UX (comandos, hooks, docs), no el código. Un ProblemDetails es un contrato: el texto que lee una persona lo localiza el cliente a partir de su código, no la API en un idioma fijo.

Checklist Post-Generación

  • Revisar entidad de dominio y sus reglas en Create/Update
  • Registrar en DI: AddMediator, AddSingleton<{Entity}Mapper>, AddValidatorsFromAssemblyContaining, AddScoped<I{Entity}Repository, {Entity}Repository>
  • Añadir el DbSet en ApplicationDbContext (si no lo hizo la generación)
  • Crear migración si es necesario
  • Añadir tests unitarios (skill testing-patterns)
