Se ejecuta solo bajo petición explícita: invocación de la skill issue-tracker-sync con intención de aplicar, o una petición de acción clara, en un proyecto cuya plataforma es GitHub (ecosystem.config.json → vcs.platform = github, o infraestructura.github en el Hilo). El disparo semántico de la skill NUNCA llega hasta aquí: responde con el conocimiento del SKILL.md y para. Para Azure DevOps, el workflow es workflow-devops-sync.md; la API de GitHub está en github-playbook.md.

Analiza el código fuente y sincroniza con GitHub: Epic, Features y PBIs como issues con sub-issues, labels type:/area:/priority:, milestones por sprint, un Project v2 con Kanban por Status, y la documentación en docs/ (o la Wiki). DRY-RUN por defecto: muestra todo antes de ejecutar cambios reales.

REGLAS CRÍTICAS

  • DRY-RUN obligatorio en primera ejecución (mostrar, no ejecutar)
  • NO crear issues sin confirmación explícita del usuario
  • NO sobrescribir documentación existente en docs/ sin preguntar (opciones: sobrescribir/versionar/omitir)
  • Verificar duplicados SIEMPRE antes de crear (buscar Epic/Feature existentes por título y label)
  • Trazabilidad obligatoria en cada PBI: endpoint + archivo + commit + tipo
  • Assignee solo por login (equipo.miembros[].githubLogin); sin match → sin asignar + warning
  • Nunca aprobar, mergear ni cerrar PRs desde aquí: esto es Issues, no Git

Fase 0: Verificar pre-requisitos

================================================================
         VERIFICANDO PRE-REQUISITOS (GitHub)
================================================================

  gh autenticado            [gh auth status: OK · scopes: repo, project]
  Repositorio               [owner/repo, Issues habilitadas]
  ESTADO_PROYECTO.json      [infraestructura.github]
  Código fuente             [src/ detectado]
  Git log accesible         [git log disponible]
================================================================
gh auth status                                                     # sin sesión: gh auth login
gh auth status 2>&1 | grep -q "project" || echo "[!] falta scope project: gh auth refresh -h github.com -s project (solo si vas a usar Projects v2)"
REPO=$(gh repo view --json nameWithOwner --jq .nameWithOwner)      # infiere owner/repo del remoto
gh repo view --json hasIssuesEnabled,isPrivate,owner --jq '{hasIssuesEnabled, isPrivate, ownerType: .owner.type}'

Verificar:

  1. Que _hilo/ESTADO_PROYECTO.json tiene sección infraestructura
  2. Que existe código en src/ (o ruta detectada) y git log es accesible
  3. Que hasIssuesEnabled = true (si no: gh repo edit --enable-issues)

Si es primera vez (no hay github en ESTADO_PROYECTO.json), preguntar (defaults entre corchetes):

Primera sincronización con GitHub detectada.

1. Repositorio: <owner/repo inferido>                              [Enter = correcto]
2. ¿Jerarquía con Features (Epic → Feature → PBI) o plano (Epic → PBIs por área)?   [Features si ≥ 3 áreas]
3. ¿Project v2? [1] crear uno nuevo (owner: <org|@me>)  [2] enlazar uno existente (número)  [3] sin Project
4. ¿Documentación en docs/ (recomendado, viaja con el código) o en la GitHub Wiki?  [docs/]
5. Logins de GitHub del equipo: <usuario> → <login>  (se guardan en equipo.miembros[].githubLogin)

Guardar en ESTADO_PROYECTO.json → infraestructura.github (estructura en github-playbook.md).

Fase 1: Análisis automático del código

Idéntica a la Fase 1 de workflow-devops-sync.md (framework, arquitectura, endpoints, seguridad, tests, integraciones, ORM, observabilidad, resiliencia; git log de 200 commits clasificado por Conventional Commits). No duplicar: el mismo análisis alimenta las dos plataformas. Mapeo del tipo de commit al label: feat: → type:task · fix: → type:bug · refactor: → type:debt · docs: → type:docs.

Fase 2: Generar estructura (DRY-RUN)

Con Features:

Epic: <Proyecto>                                          type:epic
├── Feature: Seguridad                                    type:feature area:seguridad
│   ├── Configurar SSO con el IdP            [Done]        type:task area:seguridad priority:P1  @login
│   ├── Implementar CORS policy              [Done]        type:task area:seguridad priority:P1
│   └── Añadir rate limiting                 [Todo]        type:task area:seguridad priority:P2
├── Feature: API Endpoints                                type:feature area:api
│   ├── GET /api/scholarships                [Done]        type:task area:api priority:P2
│   └── POST /api/scholarships               [In Progress] type:task area:api priority:P2  @login
└── Feature: Calidad                                      type:feature area:calidad
    └── Tests unitarios                      [Todo]        type:task area:calidad priority:P4

Modo plano:

Epic: <Proyecto>                                          type:epic
├── Configurar SSO con el IdP                [Done]        type:task area:seguridad priority:P1
├── GET /api/scholarships                    [Done]        type:task area:api priority:P2
└── Tests unitarios                          [Todo]        type:task area:calidad priority:P4

[Done] = issue closed (completed); [In Progress]/[Todo] = open con ese Status en el Project.

Priorización automática (misma tabla que Azure): Seguridad y Bugs → priority:P1 · Endpoints → P2 · Observabilidad → P3 · Refactor / Deuda técnica → P4.

================================================================
Total: 1 Epic, 5 Features, 11 PBIs (6 Done, 1 In Progress, 4 Todo)
Labels: 6 type:* · 9 area:* · 4 priority:*      Milestones: 4      Project: crear "<Proyecto>" (owner myorg)
================================================================

Trazabilidad en cada PBI (bloque Origen: en el cuerpo, ver github-playbook.md).

Fase 2.5: Validación obligatoria

¿Confirmas esta estructura? [S/N]
¿Quieres modificar algo? (añadir/eliminar Features o PBIs, cambiar modo plano/Features)

NO continuar sin confirmación.

Fase 2.6: Control de duplicados

Si el proyecto ya tiene github.epicIssue, o existen issues type:epic/type:feature:

gh issue list --label type:epic --state all --json number,title
gh issue list --label type:feature --state all --json number,title
gh issue list --state all --search "in:title \"<título del PBI>\"" --json number,title      # por PBI propuesto
Se ha detectado contenido existente en GitHub:

Epic: #12 "Epic: LicenseManager" (existente)
Features: 3 de 5 ya existen
PBIs: 7 de 11 ya existen

Opciones:
1. Reutilizar existentes + crear solo los nuevos (y re-enlazar sub-issues que falten)
2. Crear todo como nuevos (duplicados)
3. Cancelar

Fase 3: Ejecutar (solo si --live)

DRY-RUN (default)

  • Mostrar TODO en pantalla con formato visual
  • NO ejecutar nada en GitHub
  • Guardar propuesta en _hilo/devops_sync_proposal.json ("plataforma": "github")

LIVE (--live)

3a. About (descripción del repositorio + README)

gh repo edit --description "<1 frase, ≤ 350 chars: qué hace, stack>"

La versión larga (qué hace, stack, endpoints principales, seguridad, equipo, enlaces a docs/) va en una sección ## Estado del README.md (PR normal). Es el equivalente del About + del widget «Estado».

3b. Labels

Crear el juego canónico con gh label create … -f (idempotente): type:*, area:*, priority:*. Receta completa en github-playbook.md.

3c. Issues (Epic → Features → PBIs con sub-issues)

Orden: Epic → Features → PBIs; tras cada creación, POST …/sub_issues con el id numérico (no el número). Cada PBI: labels type:/area:/priority:, -a <login> si hay assignee (3e), -m "<milestone>" si hay sprints (3h). Los PBIs [Done] se crean y se cierran a continuación (gh issue close <n> --reason completed) para que el histórico quede en GitHub. Guardar epicIssue y features.<area> para la Fase 4.

3d. Documentación (docs/ por defecto)

Escribir las 9 páginas en docs/ según la tabla de github-playbook.md (Home → README, Arquitectura, Endpoints, Seguridad, Resiliencia, Observabilidad, Configuración, Desarrollo, Equipo). Si el fichero existe: preguntar sobrescribir/versionar/omitir por fichero. Commit en rama y PR (/hv:commit), nunca push directo a la rama base. Si el usuario eligió Wiki: comprobar hasWikiEnabled, que la Wiki esté inicializada, clonar <repo>.wiki.git y escribir las páginas ahí (sin PR).

3e. Asignaciones (assignees)

Mismo algoritmo que Azure (3e.1-3e.4 de workflow-devops-sync.md: developers por roles, tabla área → carpetas, top contributor de git log por paths candidatos, empate → más commits en el área). Cambia solo la identidad:

resolver developer:
  - buscar m en developers donde m.git_author_name == top_contributor o m.nombre == top_contributor
  - si match y m.githubLogin → assignee = m.githubLogin
  - si match sin githubLogin → intentar m.usuario si es colaborador del repo
      (gh api repos/$REPO/collaborators/<usuario> devuelve 204); si no, assignee = null + warning
  - si NO match → assignee = null (sin asignar + warning)
gh issue edit <n> --add-assignee <login>

3f. Áreas: son las labels area:* de 3b/3c (no hay Area Paths ni fix de Team). Vista Table del Project agrupada por area:* para el equivalente del backlog por área.

3g. Recetas de consulta

Escribir docs/management/ISSUE_QUERIES.md con las recetas gh issue list (Mi trabajo, Bugs abiertos, Deuda técnica, Completados esta semana, Sprint actual) e indicar qué vistas del Project crear (3i).

3h. Milestones (sprints)

Según calendario.release_cycle (tabla en github-playbook.md): gh api -X POST repos/$REPO/milestones -f title= -f due_on=; asignar los PBIs abiertos del sprint en curso con gh issue edit <n> -m "<milestone>".

3i. Project v2

Si se eligió crear o enlazar: gh project create / gh project link, gh project field-list para los ids de Status y sus opciones, gh project item-add por cada issue y gh project item-edit para el Status inicial (Todo abiertos sin actividad · In Progress con commits recientes · Done cerrados). Imprimir la receta de vistas (Board por Status, Table por area:*, Roadmap por milestone) y de los workflows integrados («Item closed → Done»), que solo se configuran en la UI. Guardar project.{owner,number,id,statusFieldId,statusOptions}.

3j. Rulesets y notificaciones

Las branch policies son rulesets (skill git-best-practices, tools/github-rulesets.md): si no existen, sugerirlo, no aplicarlo desde aquí. Notificaciones: recordar CODEOWNERS (auto-request de review), watch del repo y Discussions (gh repo edit --enable-discussions) si el equipo las quiere.

Fase 4: Persistencia Hilo

Guardar en _hilo/ESTADO_PROYECTO.json → infraestructura.github (estructura completa en github-playbook.md): owner, repo, epicIssue, features{}, modoPlano, milestones{}, project{}, docsEnLugarDeWiki, ultimaSync, syncMode. Y los logins en equipo.miembros[].githubLogin.

Guardar log en _hilo/devops_execution_log.json:

{ "fecha": "2026-09-07", "usuario": "HV", "plataforma": "github", "modo": "DRY-RUN", "cambios": [], "errores": [] }

Fase Opcional: --verify (Tests de regresión)

# Check 1: labels canónicas presentes
gh label list --json name --jq '[.[] | select(.name | test("^(type|area|priority):"))] | length'      # esperado ≥ 19
# Check 2: el Epic tiene sub-issues
gh api "repos/$REPO/issues/<epicIssue>/sub_issues" --jq length                                          # esperado > 0
# Check 3: los PBIs están en el Project
gh project item-list <number> --owner <owner> --format json --jq '.items | length'                     # esperado ≥ nº de PBIs
# Check 4: milestones abiertos
gh api "repos/$REPO/milestones?state=open" --jq length                                                  # esperado > 0 si release_cycle != continuo
