Referencia técnica del camino GitHub de issue-tracker-sync: la API (gh CLI, REST y GraphQL) que usan el workflow references/workflow-github-sync.md y el modo activo de la regla devops-awareness (infraestructura.github.autoSync = true). Es el homólogo de azure-devops-rest-playbook.md. Se lee bajo demanda: la regla siempre-cargada solo lleva el resumen.

Prerrequisitos

  • gh autenticado (gh auth status). Scopes: repo cubre issues, labels, milestones y sub-issues; Projects v2 exige project (gh auth refresh -h github.com -s project; read:project basta para consultar).
  • Issues habilitadas en el repo (gh repo view --json hasIssuesEnabled --jq .hasIssuesEnabled; si no, gh repo edit --enable-issues).
  • Un Project v2 vive en la organización o el usuario, no en el repo: se crea allí y se enlaza al repo (gh project link). En una organización, el owner del proyecto es la organización.
  • infraestructura.github en _hilo/ESTADO_PROYECTO.json (lo escribe la primera sincronización, Fase 4).

Modelo de trabajo en GitHub

  • Jerarquía por sub-issues: el Epic es un issue type:epic; cada Feature un issue type:feature sub-issue del Epic; cada PBI un issue type:task (o bug/debt/docs) sub-issue de su Feature, con area:<x> y priority:Pn. Modo plano (repos pequeños): sin Features, los PBIs cuelgan del Epic y se agrupan por area:*.
  • Estados: open/closed con state_reason (completed | not_planned). Si hay Project, el campo Status (Todo / In Progress / Done por defecto) da el Kanban. Mapeo desde Azure: New → Todo, Committed → In Progress, Done → closed + Done.
  • Identidad: assignee por login (equipo.miembros[].githubLogin; si falta y usuario coincide con un login del repo, usarlo; si no, omitir y avisar). Nunca email.
  • Trazabilidad: mismo bloque Origen: (endpoint, archivo:línea, commit, tipo) en el cuerpo del issue. Los commits y PRs que digan Closes #<n> cierran el issue al llegar a la rama por defecto.

Organizaciones con Issue Types habilitados pueden además fijar el tipo nativo (Epic, Feature, Task, Bug) desde la UI o la REST (-f type=Epic). Para Ovillo la fuente de verdad siguen siendo las labels type:*, que funcionan en cualquier plan.

Crear la jerarquía (Epic → Feature → PBI)

# Epic
EPIC_URL=$(gh issue create -t "Epic: <Proyecto>" -F epic.md -l type:epic)
EPIC_N=${EPIC_URL##*/}

# Feature = sub-issue del Epic. sub_issue_id es el ID NUMÉRICO del issue (campo .id), NO su número (#n).
F_URL=$(gh issue create -t "Feature: Seguridad" -b "Agrupa los PBIs de autenticación, CORS y cabeceras" -l type:feature -l area:seguridad)
F_N=${F_URL##*/}
F_ID=$(gh api "repos/$REPO/issues/$F_N" --jq .id)
gh api -X POST "repos/$REPO/issues/$EPIC_N/sub_issues" -F sub_issue_id=$F_ID      # -F: parámetro tipado (entero)

# PBI = sub-issue de la Feature, con área, prioridad, asignado y milestone
P_URL=$(gh issue create -t "Configurar SSO con el IdP" -F pbi.md -l type:task -l area:seguridad -l priority:P1 -a <login> -m "Sprint 1")
P_ID=$(gh api "repos/$REPO/issues/${P_URL##*/}" --jq .id)
gh api -X POST "repos/$REPO/issues/$F_N/sub_issues" -F sub_issue_id=$P_ID

# Ver / reordenar / mover de padre
gh api "repos/$REPO/issues/$EPIC_N/sub_issues" --jq '.[] | "\(.number)\t\(.title)\t\(.state)"'
gh api -X POST "repos/$REPO/issues/<nuevo_padre>/sub_issues" -F sub_issue_id=$P_ID -F replace_parent=true
gh api "repos/$REPO/issues/${P_URL##*/}/parent" --jq .number

Cuerpo del PBI (pbi.md), con la trazabilidad obligatoria:

Origen:
- Endpoint: POST /api/scholarships
- Archivo: src/MyCompany.Scholarships.Web/Controllers/ScholarshipsController.cs:45

Projects v2

OWNER=<org|@me>
NUM=$(gh project create --owner $OWNER --title "<Proyecto>" --format json --jq .number)
gh project link $NUM --owner <login-u-org> --repo $REPO      # con el LOGIN literal: `link --owner @me` falla ("has different owner from '@me'")
PROJECT_ID=$(gh project view $NUM --owner $OWNER --format json --jq .id)                       # PVT_...
gh project field-list $NUM --owner $OWNER --format json --jq '.fields[] | {id, name, options}'    # Status y sus opciones (PVTSSF_... / PVTSSFO... ids)

# Añadir un issue y fijar Status
ITEM_ID=$(gh project item-add $NUM --owner $OWNER --url $P_URL --format json --jq .id)          # PVTI_...
gh project item-edit --project-id $PROJECT_ID --id $ITEM_ID --field-id <statusFieldId> --single-select-option-id <optionId>

# Campos propios (TEXT | SINGLE_SELECT | DATE | NUMBER; Iteration solo desde la UI)
gh project field-create $NUM --owner $OWNER --name "Área" --data-type SINGLE_SELECT --single-select-options "api,seguridad,integraciones,observabilidad,calidad"

ISSUE_NODE_ID = gh api repos/$REPO/issues/<n> --jq .node_id. Con gh api graphql -f query='...'.

Vistas = dashboard: Board agrupado por Status (Kanban), Table agrupada por label area:*, Roadmap por milestone. Se crean desde la UI (la API no crea vistas); el workflow imprime la receta. Los workflows integrados del Project («Item closed → Status Done», «Item added → Todo») evitan actualizar Status a mano: activarlos desde la UI del Project.

docs/ en vez de Wiki

El layout Ovillo ya tiene docs/ (management/, architecture/, api/, manuals/, testing/, support/): las 9 páginas de la Wiki de Azure se escriben ahí y viajan con el código (PR, CODEOWNERS, historia). La GitHub Wiki es opcional (gh repo edit --enable-wiki): es un repo git aparte (https://github.com/<o>/<r>.wiki.git) que hay que inicializar desde la UI con una primera página antes de poder clonarlo, y no pasa por PR.

Recetas de consulta (sustituyen a las Shared Queries)

Guardar en docs/management/ISSUE_QUERIES.md; las vistas del Project las persisten en la UI.

gh issue list --assignee @me --state open                                    # Mi trabajo
gh issue list --label type:bug --state open                                  # Bugs abiertos
gh issue list --label type:debt --state all                                  # Deuda técnica
gh issue list --state closed --search "closed:>=$(date -d '-7 days' +%F)"    # Completados esta semana (pwsh: (Get-Date).AddDays(-7).ToString('yyyy-MM-dd'))
gh issue list --milestone "Sprint 1" --json number,title,state,assignees     # Sprint actual
gh issue list --search "HV-19 in:title" --json number --jq '.[0].number'     # Localizar un evolutivo por código

Modo activo (autoSync)

Prerrequisitos: github.autoSync = true y github.epicIssue != null. Si falta alguno, modo pasivo.

# Localizar el issue de un evolutivo por su código
N=$(gh issue list --search "{CODIGO} in:title" --state all --json number --jq '.[0].number')
gh issue edit $N --add-assignee <login> --add-label priority:P1
gh issue close $N --reason completed

Coherencia de Features: Feature con sub-issues abiertos → sigue open; todos cerrados → puede cerrarse (gh api repos/$REPO/issues/<f>/sub_issues --jq '[.[] | select(.state=="open")] | length').

Gotchas

  • sub_issue_id es el id de base de datos del issue (.id), no su número: gh api repos/{o}/{r}/issues/{n} --jq .id. Con gh api, pasar el entero con -F (tipado), no con -f (string).
  • Projects v2: scope project (gh auth refresh -s project); --owner obligatorio en todos los gh project; el proyecto es de la organización o del usuario y se enlaza al repo. En gh project link el --owner debe ser el login literal (@me da «has different owner»); create, view, item-add sí aceptan @me.
  • Iteration no se crea por API ni por gh project field-create: usar milestones para los sprints; si el Project ya tiene un campo Iteration (UI), asignar con --iteration-id.
  • Wiki: inicializar desde la UI antes de clonar <repo>.wiki.git; por eso el default es docs/.
  • gh label create -f es idempotente (actualiza color/descripción); los nombres con : son válidos.
  • due_on en ISO 8601 YYYY-MM-DDTHH:MM:SSZ; GitHub lo muestra en la zona del usuario (poner la fecha del día siguiente a 00:00Z si el sprint acaba a final de día).
  • Rate limit: 5.000 peticiones/h REST por token; una sincronización de 50 issues con sub-issues y Project consume ~200. Reintentar con backoff ante 403 rate limit.
  • Un repo Free privado tiene issues, sub-issues, labels, milestones y Projects; lo que no tiene son reviewers de environments (eso es CI/CD, no Issues).
