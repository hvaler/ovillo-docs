Contenido

Solo usuario: lleva disable-model-invocation: true, asi que el modelo no puede lanzarla por su cuenta ni su descripcion entra en contexto. Se ejecuta solo con /hv:cicd-release.

Crea un tag semver, lo empuja y dispara el Build del pipeline de esa versión. En GitHub crea además la GitHub Release del tag (notas generadas). NO despliega: el deploy es un paso aparte on-demand (/hv:cicd-deploy).

Audiencia: desarrolladores con pipeline (Fase 1 o 2) generado por /hv:cicd-init. Plataforma: resolve('cicd.platform') (Hilo infraestructura.cicd.plataforma › ecosystem.config.json → cicd.platform; .claude/CONFIGURACION.md §Resolución): azure-pipelines | github-actions.

Extended Thinking Mode

think hard

release ≠ deploy. Liberar una versión = marcar un punto semver y construirlo (artefacto reproducible). Desplegarlo a un entorno es una decisión posterior y on-demand. Este comando NUNCA despliega por defecto: solo versiona + dispara el Build (+ la GitHub Release, que es una ficha del tag, no un deploy). Así "liberar" no acopla con "distribuir".

en un proyecto consumidor, "publicar el artefacto" lo hace el propio pipeline (Build → dotnet publish / ArchiveFiles@2 → artefacto drop · upload-artifact). Excepción: en el stack .NET-tool / librería NuGet, el tag v* SÍ dispara la publicación del .nupkg al feed (publish job / stage único): ahí liberar = publicar el paquete. Avisarlo antes de empujar el tag.

Sintaxis

/cicd-release [--major | --minor | --patch | --version X.Y.Z] [--deploy <dev|pre|pro>] [--no-push] [--no-gh-release] [--dry-run]
FlagDescripción
--patchDefault. Incrementa Z (vX.Y.Z → vX.Y.Z+1).
--minorIncrementa Y, resetea Z.
--majorIncrementa X, resetea Y.Z.
--version X.Y.ZFuerza una versión concreta.
--deploy <env>Opcional. Atajo: tras el release, encola /hv:cicd-deploy --env <env> --tag vX.Y.Z. NUNCA es el comportamiento por defecto.
--no-pushCrea el tag local pero NO lo empuja (no dispara el build). Para revisar antes.
--no-gh-releaseSolo GitHub. No crear la GitHub Release del tag (por defecto se crea con --generate-notes).
--dry-runMuestra el tag/commit (y la release) que crearía sin ejecutar.

CUÁNDO USAR

  • Cuando una funcionalidad/fix está lista en la rama base y quieres marcar una versión y construirla.
  • Como paso previo a un deploy on-demand (/hv:cicd-release → luego /hv:cicd-deploy).

NO usar para:

  • Desplegar a un entorno → /hv:cicd-deploy (release NO despliega).
  • Generar el pipeline → /hv:cicd-init.
  • Publicar la plantilla Ovillo (eso es /publicar, comando del Constructor, no de consumidor).

FASE 0 — Validaciones previas

0.1 Leer config

_hilo/ESTADO_PROYECTO.json: configuracion.branching.ramaBase, infraestructura.cicd (objeto { plataforma, pipelines[] }; pipeline activo), estado.version_actual. Plataforma: cicd.plataforma o ecosystem.config.json → cicd.platform.

0.2 Estado del repo (BLOQUEANTE)

  • Working tree limpio (git status --short vacío). Si hay cambios sin commitear → abortar con mensaje.
  • Estar en la rama base (ramaBase, típicamente main). Si no, avisar y pedir confirmación.
  • GitHub: gh auth status OK (sin sesión, el tag se empuja igual pero no se crea la Release ni se resuelve el enlace a la run).

0.3 Calcular siguiente semver

  • Leer el último tag: git describe --tags --abbrev=0 --match 'v*' (o v0.0.0 si no hay ninguno).
  • Aplicar el bump (--patch por defecto). Validar formato vX.Y.Z.
  • Si --version, validar que es estrictamente mayor que el último tag.

0.4 (Opcional, recomendado) verificar build verde

Si el pipeline está registrado, consultar el último Build de la rama base. Si está rojo, advertir: "El último build de <rama> está en failed. ¿Liberar de todas formas? (S/N)". No bloquea, pero avisa.

# Azure DevOps (R2 TLS 1.2+): GET $adoUrl/$proj/_apis/build/builds?definitions=$pipelineId&branchName=refs/heads/<ramaBase>&$top=1&api-version=6.0 -> .value[0].result
# GitHub Actions: la última run del workflow de CI en la rama base
gh run list --workflow ci.yml --branch <ramaBase> --limit 1 --json conclusion,url,displayTitle

FASE 1 — Crear tag y (opcional) commit de versión

  1. Si el proyecto tiene archivos de versión (*.csproj con <Version>, package.json, _hilo/VERSION.json), bumpearlos a X.Y.Z y crear un commit chore(release): vX.Y.Z.
  2. Crear tag anotado:
git tag -a vX.Y.Z -m "Release vX.Y.Z"

Con --dry-run: mostrar el tag y el commit que se crearían (y, en GitHub, el comando de la Release), sin ejecutar.

FASE 2 — Push (dispara el Build)

Salvo --no-push.

git push origin <ramaBase>           # si hubo commit de versión
git push origin vX.Y.Z               # el tag

Azure DevOps: el push a la rama base dispara el trigger CI → stage Build (compila + test + publica artefacto drop). Los stages de deploy NO corren (la variable DeployEnv está vacía en un push normal, modelo on-demand R20).

GitHub Actions: el push a la rama base ejecuta el job build de ci.yml / cd-<slug>.yml (y quality, si hay Hub). Los jobs deploy-* NO corren: solo se activan con workflow_dispatch (G1). En el stack .NET-tool el push del tag v* ejecuta el job publish de publish-nuget.yml: el paquete se publica en el feed; con --no-push se puede revisar antes.

Confirmar al usuario que el build se disparó, con enlace a la run:

# Azure DevOps: GET .../_apis/build/builds?definitions=$pipelineId&$top=1&api-version=6.0 -> _links.web.href
# GitHub Actions (la run tarda unos segundos en aparecer)
gh run list --branch <ramaBase> --limit 1 --json url,status,workflowName,displayTitle

2-gh — GitHub Release (solo github-actions, salvo --no-gh-release)

gh release create vX.Y.Z --verify-tag --title "vX.Y.Z" --generate-notes
# --verify-tag: aborta si el tag no está en el remoto (garantiza que el push anterior llegó)
# --generate-notes: notas desde PRs/commits desde la release anterior (Conventional Commits las hacen legibles)
# opcional: --prerelease si X=0 o el tag lleva sufijo (-rc.1); --draft para revisar antes de publicar

La Release es la ficha pública del tag (notas, assets si el pipeline los sube): no despliega nada. El artefacto de deploy sigue siendo el de la run (upload-artifact), y el deploy sigue siendo /hv:cicd-deploy.

FASE 3 — Cierre

✅ Release vX.Y.Z

   Tag creado y empujado → Build disparado.               <URL de la run>
   Artefacto en construcción (stage/job Build del pipeline).
   GitHub Release: <URL>                                    [solo GitHub]

   El deploy NO es automático. Para desplegar esta versión:
     /cicd-deploy --env dev --tag vX.Y.Z      (Dev)
     /cicd-deploy --env pre --tag vX.Y.Z      (Pre, con confirmación / reviewers)

Actualizar _hilo/ESTADO_PROYECTO.json.estado.version_actual = X.Y.Z.

Si se pasó --deploy <env>: tras confirmar que el Build terminó verde (Azure: poll REST · GitHub: gh run watch <id> --exit-status), invocar el flujo de /hv:cicd-deploy --env <env> --tag vX.Y.Z (con su confirmación para pre/pro). Esto es un atajo explícito, nunca el default.

REGLAS CRÍTICAS

  • NUNCA desplegar por defecto: release solo versiona + dispara build (+ GitHub Release). El deploy es /hv:cicd-deploy.
  • NUNCA liberar con working tree sucio o fuera de la rama base sin confirmar.
  • SIEMPRE tag anotado (-a), nunca lightweight.
  • NO usar /publicar aquí (es del Constructor, no del consumidor).
  • El build sí corre en push (build ≠ deploy); el deploy queda on-demand (Azure R20 · GitHub G1).
  • GitHub: la Release se crea después del push del tag y con --verify-tag; nunca crear el tag desde la Release (--target), porque el tag dejaría de ser anotado y firmado localmente.
