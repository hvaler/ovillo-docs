init

Prepara un repositorio para trabajar con el ecosistema Ovillo instalado como plugin. Crea el layout src/docs/ops, el Hilo, el Patron y la configuracion del proyecto sin pisar lo que ya exista.

Contenido

Solo usuario: lleva disable-model-invocation: true. Se ejecuta con /hv:init en la raiz del repo del proyecto, una vez instalado el plugin (claude plugin install hv@ovillo).

Que hace

El plugin trae el ecosistema (skills, agents, hooks). Lo que un plugin no puede traer es el proyecto: su layout, su memoria, su base de conocimiento y su configuracion. Eso lo escribe esta skill en el repo:

EscribeQue es
src/ docs/ ops/ con sus READMElayout del proyecto
_hilo/memoria del proyecto, vacia de arranque
_patron/base de conocimiento de la organizacion, entera
CLAUDE.md, README.md, INICIO_RAPIDO.md, ecosystem.config.example.jsonficheros de arranque
.claude/CLAUDE_BASE*.md, schemas/, statusline.js, smoke-tests/, rules/lo del ecosistema que no es skill, agent ni hook (las 3 reglas incondicionales incluidas)
.claude/settings.jsonsin hooks (los trae el plugin): statusLine y anuncios
.vscode/solo si --ide vscode o organization.ide lo dice

Nunca sobrescribe un fichero que ya exista: re-ejecutarla es seguro y sirve para completar lo que falte tras una actualizacion del plugin (documentos nuevos del Patron, por ejemplo).

--refresh-memoria (opt-in)

Un proyecto ya inicializado conserva la memoria con la que nacio, asi que no se beneficia solo de actualizar el plugin. Este flag la pone al dia sin tocar lo personalizado:

Con --refresh-memoriaQue hace
.claude/rules/, .claude/CLAUDE_BASE*.md, .claude/CONFIGURACION.mdse reescriben desde el plugin: son del ecosistema y no se personalizan
CLAUDE.md del proyectosolo se retira la linea @.claude/CLAUDE_BASE.md: esos estandares dejaron de estar siempre cargados y los recuerda la regla estandares-base al tocar src/. El resto del fichero (glosario, informacion del proyecto, reglas propias) no se toca
CLAUDE.md.plantillacopia de la plantilla vigente, al lado, para comparar y podar a mano las secciones que ya viven en skills (comandos, workflows, convenciones del Hub). Borrarla al acabar

Ejecutarlo siempre primero con --dry-run, ensenar el resumen y pedir confirmacion. Es idempotente: una segunda pasada dice que no hay nada que cambiar.

Procedimiento

  1. Comprobar que estamos en la raiz de un repositorio (hay .git/ o el usuario lo confirma).
  2. Ejecutar el scaffold. Primero en seco para mostrar que se va a crear:
# $ARGUMENTS puede traer ya --dry-run (el usuario lo escribio): el script lo acepta repetido, pero para no
# ensenar un comando con el flag dos veces, anadirlo solo si no viene en $ARGUMENTS.
node "${CLAUDE_PLUGIN_ROOT}/skills/init/scripts/init.js" --dry-run $ARGUMENTS
  1. Mostrar el resumen al usuario y, si confirma, ejecutar sin --dry-run (si el usuario lo habia pasado, quitarlo de los argumentos):
node "${CLAUDE_PLUGIN_ROOT}/skills/init/scripts/init.js" $ARGUMENTS
  1. Si el usuario paso --refresh-memoria, ensenarle que cambio en su CLAUDE.md y recordarle que compare con CLAUDE.md.plantilla antes de borrarla.
  2. Indicar los dos pasos siguientes: copiar ecosystem.config.example.json a ecosystem.config.json y rellenar organization (incluido ide), y despues /hv:onboarding para contextualizar el proyecto.

Si el proyecto ya tiene codigo en la raiz

Esta skill no mueve codigo. Si hay un .sln o .csproj en la raiz del repo, decirselo al usuario y ofrecer moverlo a src/ con git mv, ensenando los comandos antes de ejecutarlos. Un .sln movido cambia las rutas relativas de sus proyectos: revisar que dotnet build src/<Solucion>.sln compila despues.

Lo que sustituye

Sustituye a los antiguos comandos /setup (instalacion por copia) y /actualizar (refresco por copia): el ecosistema se actualiza con claude plugin update hv@ovillo y el proyecto se completa re-ejecutando /hv:init.
