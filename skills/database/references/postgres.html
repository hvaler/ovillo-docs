Se lee cuando ecosystem.config.json -> database.engine es postgres. El SKILL.md lleva el núcleo (nomenclatura, plantillas, buenas prácticas) escrito en T-SQL; aquí está lo que no se traduce literalmente. Lo que existe desde cada versión vive en capabilities/postgres.json, no en este documento: no se duplica.

1. La trampa que más cuesta: las mayúsculas no se conservan

Un identificador sin comillas se pliega a minúsculas. CREATE TABLE Fichaje crea la tabla fichaje, y SELECT * FROM "Fichaje" no la encuentra. En T-SQL el nombre se conserva tal cual.

Consecuencia directa: la nomenclatura PascalCase de la §1 del SKILL.md no es idiomática aquí. La convención de PostgreSQL es snake_case en minúsculas, sin comillas.

ObjetoT-SQL (núcleo)PostgreSQL
TablaFichajefichaje
Procedimientoacademic.GetStudentacademic.get_student
Vistaacademic.vw_ActiveStudentsacademic.v_active_students o sin prefijo
ColumnaFechaEntradafecha_entrada

Si el proyecto quiere conservar PascalCase, hay que entrecomillar siempre y en todas partes, incluida cada consulta de la aplicación. Se puede, pero es una decisión que se paga en cada línea: déjala escrita en _hilo/DECISIONES.md antes de tomarla.

Los prefijos configurables (naming.functionPrefix, viewPrefix, triggerPrefix) siguen aplicando: solo cambia la caja. En PostgreSQL lo habitual es v_/fn_ en minúscula, o ninguno.

2. Función y procedimiento no son lo mismo

PostgreSQL tiene FUNCTION desde siempre y PROCEDURE desde la 11, y la diferencia importa:

  • PROCEDURE: se llama con CALL, puede hacer COMMIT/ROLLBACK dentro. No devuelve conjunto de filas.
  • FUNCTION: se llama dentro de un SELECT, corre en la transacción del llamante y no puede hacer commit. Para devolver filas: RETURNS TABLE(...) o RETURNS SETOF.

La plantilla de SP del SKILL.md asume T-SQL (SET NOCOUNT ON, TRY...CATCH, RAISERROR). El equivalente aquí es un bloque plpgsql con BEGIN ... EXCEPTION WHEN OTHERS THEN ... END y RAISE EXCEPTION. SET NOCOUNT no existe y no hace falta.

4. Upsert: ON CONFLICT antes que MERGE

MERGE existe desde la 15 y es SQL estándar, pero para el caso corriente —insertar o actualizar por clave— lo idiomático y más barato sigue siendo:

INSERT INTO academic.student (id, email) VALUES ($1, $2)
ON CONFLICT (id) DO UPDATE SET email = EXCLUDED.email
RETURNING id;

RETURNING funciona en INSERT, UPDATE y DELETE, y ahorra el viaje de vuelta que en T-SQL se resuelve con OUTPUT o un SELECT posterior.

5. Concurrencia: no hay WITH (NOLOCK) ni hace falta

PostgreSQL usa MVCC: los lectores no bloquean a los escritores. WITH (NOLOCK) no existe y no tiene traducción, porque el problema que intenta resolver no se da. Para bloqueo explícito: SELECT ... FOR UPDATE o FOR UPDATE SKIP LOCKED (colas de trabajo).

6. Desde la aplicación (.NET)

  • Proveedor: Npgsql.EntityFrameworkCore.PostgreSQL, UseNpgsql(...). No mezclar con Microsoft.EntityFrameworkCore.SqlServer.
  • El parámetro se escribe $1/@p según la API; con EF Core, siempre parametrizado — la regla de no concatenar SQL del núcleo se aplica igual, y el hook sql-injection-guard la vigila igual.
  • timestamptz mapea a DateTime con Kind=Utc: guardar siempre en UTC, como manda el núcleo.

7. Entorno de desarrollo

El docker-compose.yml del andamio trae el servicio postgres tras el perfil postgres. En el .env del proyecto:

COMPOSE_PROFILES=postgres

y database.engine: "postgres" en ecosystem.config.json. Si no coinciden, levantas un motor y generas SQL para el otro — que es exactamente el defecto que corrigió la 1.2.6.
