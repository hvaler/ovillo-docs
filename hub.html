Ovillo.Hub

Centraliza lo que los proyectos aportan al conocimiento común: decisiones, lecciones, salud técnica, pipelines y documentación de agente. Es opcional (opt-in) y todo lo de estas páginas sale de los atributos [Description] del código.

Resources 4

URINombreDescripción
ovillo://decisions/{proyecto}/{codigo}decisionDevuelve el texto completo en Markdown de una ADR (Architecture Decision Record) registrada en el hub: contexto, decision, consecuencias, estado y tags.
ovillo://lessons/{proyecto}/{id}lessonDevuelve el texto completo en Markdown de una leccion aprendida del hub: titulo, categoria, descripcion y severidad. El proyecto en la URI es informativo; el id es el identificador real.
ovillo://snapshots/{proyecto}/{categoria}snapshotDevuelve el snapshot Hilo mas reciente de una categoria (decisiones, lecciones, funcionalidades, dependencias, historial, contexto_tecnico) para un proyecto. Util para que Claude lea el estado actual del proyecto sin tener que cargar cada decision individualmente.
ovillo://projects/{nombre}/statusproject-statusDevuelve la ficha de estado de un proyecto registrado en el hub: heartbeat, version del ecosistema, evolutivos en progreso, ultimas decisiones. Util para retomar contexto de un proyecto desconocido o validar que esta activo.

Prompts 3

PromptDescripción
/audit-securityGenera un prompt de auditoria de seguridad cross-proyecto con los datos vivos del hub: nugets vulnerables, vulnerabilidades criticas y deuda tecnica alta. El modelo debe priorizar acciones y proponer remediacion.
/review-project-decisionsGenera un prompt para revisar las ADRs aceptadas de un proyecto especifico, detectando incoherencias entre decisiones, decisiones que ya no aplican o gaps de documentacion. El modelo debe analizar las ADRs sincronizadas en el hub.
/weekly-status-reportGenera un prompt para producir el informe semanal del ecosistema Ovillo: proyectos activos, evolutivos en curso, decisiones recientes y carga por developer. El modelo redacta un resumen ejecutivo y operativo.

Conectar un proyecto

El consumidor declara el Hub en ecosystem.config.json → hub (opt-in, deshabilitado por defecto) y autentica con la cabecera X-Hub-Api-Key. La skill hub-client es el cliente de referencia; /hv:mcp-register registra el proyecto (nunca en silencio). Despliegue y contratos: Ovillo.Hub.

{
  "hub": {
    "enabled": false,
    "url": "",
    "auth": "apikey",
    "apiKeyHeader": "X-Hub-Api-Key",
    "registerOnInstall": false
  }
}
ClaveTipoDefaultQué hace
hub.enabledbooleanfalse
hub.urlstring""URL base del Hub (ej. http://localhost:8080 con el docker-compose del Hub).
hub.authstring"apikey"
hub.apiKeyHeaderstring"X-Hub-Api-Key"Nombre del header de API key.
hub.registerOnInstallbooleanfalseSi el instalador registra el proyecto en el Hub. SIEMPRE opt-in explicito: ningun instalador ni hook registra en silencio.
