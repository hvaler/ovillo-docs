ADR-015Integración con GitHub, ola 4: cicd-status, cicd-deploy y cicd-release vía gh

Aceptadoestado
2026-09-07fecha
991palabras
3 decisionescita
1citada por
  • Estado: Aceptado · Implementado
  • Fecha: 2026-09-07
  • Contexto: quinta ola del plan de paridad con GitHub (ADR-011 a ADR-014). Tras la ola 3 /cicd-init genera workflows de GitHub Actions, pero los tres comandos que operan el pipeline seguían hablando solo con Azure DevOps: cicd-status consultaba /_apis/build/builds, cicd-deploy encolaba por REST con la variable DeployEnv y cicd-release daba por hecho el trigger de Azure. El Hub describía sus tools en términos de Azure DevOps y mcp-sync.ps1 solo sabía recoger builds y deploys de allí. Un proyecto con cicd.platform = github-actions podía generar su pipeline y no podía desplegarlo ni verlo desde Ovillo.

Decisión

D1 — Mismo comando, misma salida, distinta herramienta por plataforma

Los tres comandos resuelven la plataforma al principio (infraestructura.cicd.plataforma del Hilo, y si falta ecosystem.config.json → cicd.platform) y bifurcan solo en el paso que toca la plataforma. Las fases, los gates (fase ≥ 2 para desplegar, confirmación por entorno, working tree limpio) y el formato de las tablas son comunes. El camino Azure DevOps no cambia.

PasoAzure DevOpsGitHub Actions
Últimos buildsGET /_apis/build/buildsgh run list --workflow <wf> --json … (+ columna Evento: push = solo build, workflow_dispatch = deploy)
Tiempo por stage/jobGET …/builds/{id}/timelinegh run view <id> --json jobs
Último deploy por entornobuilds con DeployEnvgh api repos/{o}/{r}/deployments?environment=<env> + statuses (GitHub los crea al ejecutar un job con environment:)
Pendiente de aprobaciónEnvironment approvalgh run list --status waiting + …/actions/runs/{id}/pending_deployments
Pedir el deployPOST /_apis/build/builds con parameters={DeployEnv}`gh workflow run <wf> --ref <rama\tag> -f environment=<env> y localizar la run (--event workflow_dispatch`)
Seguir la runpoll REST 30 sgh run watch <id> --interval 30 --exit-status
Verificar build verde antes de liberarREST por ramagh run list --workflow ci.yml --branch <base> --limit 1
Releasetag + pushtag + push + gh release create vX.Y.Z --verify-tag --generate-notes (omitible con --no-gh-release)

D2 — El pipelineId de un workflow es el nombre de su fichero

cd-<slug>.yml, no la ruta ni un id numérico: es lo que aceptan gh workflow run y gh run list --workflow, cabe en los 64 caracteres del Hub y se lee en ESTADO_PROYECTO.json. yamlFile conserva la ruta completa. Corregidas las notas de cicd-init (FASE 2.6 y FASE 4) que decían «ruta del workflow».

D3 — Lo que este comando nunca hace en GitHub

  • No aprueba environments. La confirmación de /cicd-deploy es el primer gate; los required reviewers de pre/pro son el segundo y aprueban en la plataforma. El comando muestra quién debe aprobar y la URL.
  • No despacha sobre un SHA. workflow_dispatch solo admite rama o tag: --commit se documenta como solo Azure y en GitHub se pide crear un tag sobre ese commit y usar --tag.
  • No crea el tag desde la Release. La Release se crea después del push del tag y con --verify-tag, para que el tag siga siendo anotado (y firmable) en local.

D4 — El Hub describe ambas plataformas sin tocar el wire

McpCicdTools (register_pipeline, get_cicd_status, list_pipelines), Pipeline, PipelineDeploy y CicdEndpoints cambian solo descriptions y comentarios: pipelineId es «número de definición en Azure DevOps o fichero del workflow en GitHub», stages son «stages o jobs», BuildId de un deploy es «buildId o run id». Ninguna clave JSON ni columna cambia. mcp-sync.ps1 (h7) gana una rama que, si gh está autenticado y el pipelineId termina en .yml, recoge el último build con gh run list y los deploys con la API de deployments (estado normalizado a succeeded/failed/inProgress, buildId = run id extraído de log_url), y envía exactamente el mismo cicd-batch. Los ids numéricos siguen por REST de Azure DevOps.

D5 — Higiene que destapó la ola

  • Cuatro $1 literales dejados por la ola 3 (cicd-init/SKILL.md ×2, fase-1-wizard.md, fases-registro.md, incluido el heading de FASE 2.7) restaurados desde el commit anterior. Causa: la misma de ADR-012, el helper de edición envolvía el reemplazo en una función.
  • Lección nueva: con reemplazo string, replace también interpreta $', $` y $&. Un literal PowerShell '\.ya?ml$' -or insertó el resto del fichero dentro de mcp-sync.ps1 (detectado por el parser de PowerShell, restaurado desde HEAD). Los helpers pasan a split(a).join(b).
  • Residuo del origen mcp__stic_ia_hub__ en cicd-status → mcp__ovillo-hub__ (nombre real del servidor en .mcp.json); _estado/DECISIONES.md → _hilo/DECISIONES.md.
  • cicd-status y cicd-deploy leen la forma canónica infraestructura.cicd = { plataforma, pipelines[] } (la que escribe /cicd-init FASE 4 y lee mcp-sync), con compatibilidad para el array suelto.

Consecuencias

  • Un proyecto en GitHub puede generar, ver, liberar y desplegar su pipeline desde Ovillo con gh como única dependencia adicional (el pre-flight de /cicd-init ya lo comprueba).
  • La guía _patron/08_CICD/GUIA_COMPLETA_CICD.md describe los tres comandos para ambas plataformas y añade dos filas de troubleshooting de GitHub (workflow_dispatch ausente o workflow fuera de la rama por defecto; run en waiting por reviewers).
  • Siguiente ola (5): issue-tracker-sync con GitHub Issues y Projects v2.
