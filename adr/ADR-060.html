ADR-060PowerShell se declara, en vez de portarse

Aceptadoestado
2026-09-19fecha
683palabras
3 decisionescita
1citada por
  • Estado: Aceptado
  • Fecha: 2026-09-19
  • Contexto: la deuda 4 de ADR-010 —«Scripts PowerShell dentro de skills… No todos son opcionales: coverage-gate.ps1 es el gate G7 y security-scan.ps1 el G8»— con criterio de cierre escrito en 1.0.0: «port a Node de los dos que son gate, y declaración explícita de "requiere PowerShell" en el resto». La primera mitad de ese criterio no se sostiene; la segunda señalaba algo peor de lo que decía.

Decisión

D1 — Los dos gates NO se portan, y la evidencia estaba en casa

Portar a Node quitaría una dependencia que las dos plataformas soportadas ya satisfacen:

PlataformaCómo se invocaQué hace falta instalar
Azure DevOpstask: PowerShell@2 en un agente Windowsnada, es nativo
GitHub Actionsshell: pwsh en el runnernada, viene preinstalado

Y no es una suposición: ADR-019 los verificó corriendo sobre un runner Linux, con salida real —G7: cobertura linea=26,9% rama=83,3%—. La única situación que el port mejoraría es un agente self-hosted de Linux sin pwsh, donde se instala con una línea.

A cambio, el port añadiría Node como requisito a los pipelines .NET, que hoy no lo usan —solo el de Vue lo necesita—, más dos reimplementaciones de lógica de gate y una migración para cada consumidor con pipelines ya materializados. Es un movimiento lateral que empeora dos cosas para mejorar una estrecha.

Mismo criterio que ADR-057 aplicó a ado-sp: antes de pagar por una justificación, comprobarla.

D2 — Y la otra mitad del criterio escondía el defecto de verdad

«Declaración explícita en el resto» daba por hecho que los gates sí estaban declarados y el resto no. El barrido dice otra cosa: de las seis skills que llevan .ps1, ninguna lo declaraba.

Cinco lo invocaban (pwsh "…/Sync-QualityRecord.ps1"), que no es lo mismo: una invocación se lee cuando ya estás dentro del procedimiento, y quien no tenga pwsh se entera al fallar. Y api-integration-patterns no lo mencionaba ni una vez, con dos scripts dentro.

Contra eso, el invariante de CLAUDE.md §4 dice «Solo el SDK de .NET es requisito». Era falso para seis skills. La fuente contra sí misma, otra vez.

D3 — Una frase canónica, y una puerta que la exige

Las seis declaran ahora, justo tras el frontmatter, qué necesitan y qué se pierde sin ello —que es la parte útil: en nugets-management se hace a mano y tarda más; en calidad-codigo-sync no se publica el QR; en cicd-architect el requisito es del agente, no del equipo del desarrollador.

build-portal.js --check falla si una skill lleva .ps1 y no contiene **Requiere PowerShell**. La marca es literal a propósito: comprobar «que mencione PowerShell» habría dado por buenas las cinco invocaciones, que es justo lo que no vale.

Un fallo propio por el camino: la primera colocación buscaba el primer título con ^# y cayó dentro de un bloque de código en dos de las seis, porque un # comentario de bash casa igual. La declaración quedó dentro de un ```bash. Se coloca tras el frontmatter, que es el único sitio inequívoco.

D4 — El invariante se corrige, no se borra

§4 pasa a decir que el SDK de .NET es el único requisito para compilar y para los hooks, y que seis skills usan además PowerShell y lo declaran. Sigue siendo una promesa fuerte —ningún IDE, ningún runtime extra para el ciclo normal— y ahora es cierta.

Consecuencias

  • Versión 1.15.4: PATCH.
  • Deuda 4 de ADR-010: CERRADA, y con el criterio de cierre corregido: se declara, no se porta. Quedan dos abiertas.
  • Si algún día aparece un agente self-hosted de Linux sin pwsh, la salida es apt install powershell, escrita en la propia skill.

Verificación

  • La puerta pasa con las seis declaradas y falla al retirar una, nombrando la skill y el invariante.
  • La premisa del port, comprobada contra el repositorio: steps/coverage-gate.yml usa PowerShell@2, las cinco acciones de GitHub usan shell: pwsh, y ADR-019 registra los dos gates corriendo en Linux.
  • El barrido de las seis skills, antes y después: 0 declaraban, 6 declaran.
