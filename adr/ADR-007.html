ADR-007Ovillo.Hub: servidor MCP + REST portátil y opt-in

Aceptadoestado
2026-09-07fecha
1222palabras
6 decisionescita
6citada por
  • Estado: Aceptado
  • Fecha: 2026-09-07
  • Contexto: una organización con varios proyectos quiere compartir entre ellos decisiones, lecciones, estado de pipelines, registros de calidad y documentación de agentes, y verlo agregado. Ese hub tiene que poder levantarse sin infraestructura previa (ni servidor de base de datos ni IIS), ser opcional para el consumidor y no recoger nada sin consentimiento.

Decisión

D1 — Un servicio .NET 10 con dos superficies

hub/Ovillo.Hub.csproj: ASP.NET Core Minimal API sobre .NET 10, SDK MCP oficial (ModelContextProtocol.AspNetCore), EF Core. Versión propia en OvilloVersion.HubVersion (Ovillo.Hub, único literal de versión en el código).

SuperficieDetalle
MCP — POST /mcp, JSON-RPC 2.0 + SSE, sin estado15 tools: ping, get_version, count_projects, list_projects, search_decisions, register_decision, search_lessons, register_lesson, get_health_summary, get_active_workitems, get_cicd_status, list_pipelines, register_pipeline, register_agentdoc, register_ecosystem_feedback · 4 resources: ovillo://decisions/{proyecto}/{codigo}, ovillo://lessons/{proyecto}/{id}, ovillo://snapshots/{proyecto}/{categoria}, ovillo://projects/{nombre}/status · 3 prompts: audit-security, review-project-decisions, weekly-status-report
REST v2/v2/register, /v2/join, /v2/heartbeat, /v2/version, /v2/forget, /v2/leave, /v2/opt-in, /v2/telemetry, /v2/sync/* (batch, f3-batch, cicd-batch, quality-batch, docs-batch, ecosystem-feedback, decision, leccion, snapshot, emit-service-key), /v2/stats/*
Salud, sin authGET / → {"service":"Ovillo.Hub","version":"<OvilloVersion.HubVersion>",…} · GET /v2/version → ecosystem_latest, mcp_server_version

ecosystem_latest se resuelve en cascada: el VERSION.json servido por el portal de distribución (OvilloVersionJsonPath, cache de 5 min) → EcosystemLatest en configuración → constante de último recurso.

D2 — Persistencia multi-provider, SQLite por defecto

DbProvider = Sqlite | SqlServer. SQLite es un fichero único (Data Source=hub.db; /data/hub.db en Docker): copia de seguridad = copiar el fichero. SQL Server queda para parques que ya lo tengan. La capa Data/ es LINQ puro: sin SQL embebido ni procedimientos almacenados, el mismo código sirve a los dos motores. En el arranque, los dos proveedores construyen el esquema con EnsureCreated() desde el mismo modelo (fichero nuevo = hub listo), y la evolución la gobierna el propio Hub con pasos idempotentes y su tabla de estado (Data/SchemaState.cs, Models/HubMetadata.cs), no las EF migrations: ver la enmienda de ADR-026 D5.

D3 — Docker y configuración por entorno

Dockerfile multi-stage (sdk:10.0 → aspnet:10.0), VOLUME /data, puerto 8080, y docker-compose.yml con el volumen hubdata. Configuración por variables de entorno (__ como separador):

ClaveDefaultNotas
DbProviderSqliteo SqlServer
ConnectionStrings__McpDbData Source=hub.db (/data/hub.db en Docker)connection string completa con SQL Server
AllowedHosts*restringir si se expone fuera de la red interna
PrivacyNoticeUrlvacíoaviso de privacidad de la organización
OvilloVersionJsonPath · EcosystemLatest../VERSION.json · vacíoresolución de ecosystem_latest

cd hub && docker compose up -d && curl :8080/v2/version. Sin Docker: dotnet run --project hub. El Hub no lee ecosystem.config.json: ese archivo es del consumidor; hub.url y hub.apiKeyHeader configuran a los clientes.

D4 — Autenticación por API key

Header X-Hub-Api-Key (el nombre es configurable en el cliente vía hub.apiKeyHeader). El servidor persiste solo el hash SHA-256 de la clave. Tres vías: clave per-dev (cada desarrollador la suya), service key per-proyecto para CI (HUB_SERVICE_KEY en el pipeline, emitida por /v2/sync/emit-service-key) y clave de proyecto.

Enmendado por ADR-032 D10: la clave protege las escrituras. Toda la lectura REST (/v2/stats/*, /v2/health/*, /v2/work/*, /v2/team/*, /v2/hilo/stats/*, quality, docs, cicd, feedback) y el endpoint MCP entero responden sin clave: el Hub asume una red de confianza, y quien lo publique fuera de ella pone un proxy con autenticación delante. /v2/version lo declara (read_access). ADR-033 añade la clave de lectura opcional Hub:ReadApiKey: con ella, esa superficie y /mcp exigen X-Hub-Api-Key.

D5 — Registro opt-in, siempre explícito

Enmendado por ADR-032 D9: el alta (/v2/register, /v2/join) sigue sin clave (acceso al repo = autorización), pero acotada: límite por IP (Hub:AltaPorMinuto, 10 por defecto, 429 al superarlo) y, si la organización configura Hub:RegistrationToken, la cabecera X-Hub-Registration-Token (el cliente la toma de HUB_REGISTRATION_TOKEN). /v2/version publica registration_token_required.

hub.enabled: false y hub.registerOnInstall: false por defecto. El punto de entrada es el workflow /mcp-register: registra el proyecto en hub.url, crea los ficheros de identidad (D6), pregunta el opt-in de telemetría de agents con aviso de privacidad (per-dev, revocable) y habilita hub-client. Un segundo desarrollador que clona un repo ya registrado se une con /v2/join. Derecho al olvido: /mcp-forget (el proyecto entero) o /v2/leave (solo el desarrollador). Los instaladores nunca registran en silencio (ADR-006). Sin Hub, los workflows mcp-*, calidad-codigo-sync y docs-agente-sync degradan con un mensaje claro.

D6 — Identidad: per-proyecto y per-dev, en ficheros distintos

FicheroÁmbito¿Se commitea?Contiene
_hilo/.mcp-project.jsonproyectosíprojectId, serverUrl: para que otros se unan vía /v2/join al clonar
_hilo/ESTADO_PROYECTO.json → mcpSyncproyectosíhabilitado, serverUrl, projectId, categorias (decisiones, lecciones, nugets, deuda, evolutivos, equipo, feedback), ultimaSync
_hilo/.mcp-credentials.jsondesarrolladorno (.gitignore)apiKey, devAlias, devEmail, telemetryOptIn

Reglas absolutas: telemetryOptIn, apiKey y devAlias nunca van en ESTADO_PROYECTO.json (un desarrollador cambiaría el consentimiento de todo el equipo); el opt-in se cambia con /mcp-register, que actualiza el fichero local y hace POST /v2/opt-in; el fichero de credenciales no se borra sin desregistrar antes. El cliente MCP se declara en el .mcp.json del repo consumidor (type: http), documentado por la skill hub-client; el hook agent-telemetry y los workflows de sincronización leen hub.* y las credenciales locales.

D7 — Contratos del wire

Los nombres de campo del JSON de REST y de los DTOs son un contrato con los clientes (skills, hooks, instaladores) y no se renombran; un cambio de contrato es versión mayor (ADR-010).

Consecuencias

  • Cualquier organización levanta el Hub con docker compose up y lo respalda copiando un fichero.
  • La privacidad es estructural: lo per-dev no puede acabar en git porque vive en un fichero ignorado.
  • Ovillo.Hub.Tests y la verificación de docker build en una máquina con daemon son deuda declarada (ADR-010).

Verificación

  • dotnet build hub → 0 errores / 0 warnings (TreatWarningsAsErrors).
  • Con el Hub levantado: GET / → service y version, esta última desde OvilloVersion.HubVersion; POST /mcp tools/list → 15; resources/templates/list → 4 URIs ovillo://.
  • POST /v2/register crea un proyecto en SQLite; POST /v2/heartbeat con X-Hub-Api-Key → OK.
  • cat hub/Endpoints/*.cs | grep -c "\[McpServerTool(" → 15.

Enmienda (ADR-024, 2026-09-08)

  • POST /v2/register-silent retirado: era el alta automatica en la primera instalacion, descartada en ADR-006, y no tenia ningun cliente. El alta es siempre POST /v2/register con consentimiento interactivo; el 404 de /v2/join remite a /hv:mcp-register.
  • La telemetria llega con descriptionHash calculado en el cliente; el campo description en claro queda deprecado (se acepta y se hashea en el servidor hasta 2.0.0, nunca se persiste el texto).
  • Retencion implementada (Services/RetentionService.cs): eventos de telemetria 90 dias, heartbeats 365, purga diaria, configurable en Retention:*. PrivacyNoticeUrl apunta a la pagina «Datos y privacidad» del portal.
  • La categoria equipo deja de enviar el nombre completo salvo mcpSync.enviarNombreCompleto: true; mcp-sync exige hub.enabled.

Enmienda (ADR-026, 2026-09-08)

  • D2 corregido: se retira hub/Migrations/. La migración InitialCreate cubría 3 de las 19 tablas del contexto y el aviso de drift de EF Core estaba silenciado en Program.cs, así que con SQL Server el Hub arrancaba con tres tablas y sin decirlo. Ahora EnsureCreated() en los dos proveedores, la versión de esquema en HubMetadata y los upgrades como pasos idempotentes numerados en Data/SchemaState.cs. La supresión del aviso desaparece porque ya nadie llama a Migrate().
  • GET /v2/version publica schema_version (la de la base) y schema_expected (la del binario): si no coinciden, falta aplicar un upgrade.
  • La primera pasada de retención va en seco sobre cada base: cuenta cuánto borraría, lo registra con un aviso, deja la marca retention.firstPassAt y no borra. Borra desde la segunda. Retention:DryRun: true fuerza el modo seco indefinidamente.
