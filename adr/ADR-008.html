ADR-008Solo Git; IDE condicional con organization.ide

Aceptadoestado
2026-09-07fecha
668palabras
1 decisionescita
5citada por
  • Estado: Aceptado
  • Fecha: 2026-09-07
  • Contexto: dos supuestos de entorno atraviesan skills, hooks e instaladores y hay que fijarlos: qué control de versiones se asume y qué herramienta de desarrollo se da por presente. Cada camino alternativo que se mantenga es código, documentación y evals que hay que sostener; cada integración impuesta es un paso que falla en el equipo que no la usa.

Decisión

D1 — El ecosistema asume Git y no mantiene un segundo camino de VCS

Los workflows commit, git-sync, nuevo-evolutivo, testing-patterns y git-best-practices hablan Git (git status/diff/add/commit/pull/push, ramas, conventional commits) y nada más. vcs.type admite git y other: con other el ecosistema degrada a instrucciones manuales (dice qué habría que hacer y no lo ejecuta), sin pretender conocer otro sistema. Lo configurable es dónde vive Git y cómo se ramifica: vcs.platform (github | gitlab | azure-devops | bitbucket | other), vcs.defaultBranch, vcs.branchNamingConvention y vcs.branchingStrategy con 13 estrategias (github-flow por defecto, trunk-based, gitflow, release-flow, oneflow, gitlab-flow, developer-branch, ship-show-ask, stacked-prs, environment-branching…). La estrategia efectiva del proyecto vive en ESTADO_PROYECTO.json → configuracion.branching.estrategia y gana a la de la organización; la regla incondicional developer-branch se autogatea leyendo ese valor (ADR-003 D4). Los helpers de git de los hooks (gitReadOnly, gitWithRetry, clearStaleGitLock) son la única capa de acceso a Git en el harness.

D2 — El único requisito de herramientas es el SDK de .NET

Todo lo que toca la solución lo hace con dotnet build, dotnet test, dotnet restore y dotnet format, buscando un .sln / .slnx bajo src/. Funciona igual desde Visual Studio, VS Code con la extensión de C#, Rider o una terminal. Los hooks solo conocen el IDE de forma pasiva: auto-format invoca dotnet format y bash-guard tolera los .lock huérfanos que deja Visual Studio. Ningún hook ni skill impone un IDE.

D3 — organization.ide: none | visual-studio | vscode | rider, con none por defecto

ValorQué hace el ecosistema
nonesolo el SDK; ninguna integración adicional
visual-studio/hv:init copia integracion-vs.ps1 a .claude/scripts/; los workflows que la mencionan (analizar, onboarding, nuevo-evolutivo, documentacion-tecnica) la proponen "si el equipo usa Visual Studio", nunca como paso obligatorio
vscode/hv:init escribe .vscode/: settings.json (dotnet.defaultSolution: src, exclusiones de búsqueda para _patron/ y _hilo/specs/, formatOnSave), extensions.json (C#, C# Dev Kit, EditorConfig, markdownlint, Claude Code) y tasks.json (build, test con el coverlet.runsettings de ops/testing/, entorno docker)
ridersolo el SDK; sin ficheros propios (valor reservado)

El campo está en el schema, en ecosystem.config.example.json y en los DEFAULTS de hooks/lib/config.js.

D4 — La integración con Visual Studio: cosmética, condicional y reversible

integracion-vs.ps1 añade Solution Folders al .sln / .slnx para ver la documentación del proyecto desde el explorador de soluciones. Al arrancar lee organization.ide y, si no vale visual-studio, sale limpio con un [SKIP] explicativo (-Force lo salta). Marca el .sln con # Ovillo-Integracion v<n>, hace copia de seguridad antes de tocarlo y no se reaplica si ya está (salvo -Force). Estructura:

Solución.sln
├── src/…                 ← los proyectos .NET, como siempre
└── Ovillo/
    ├── Raiz              ← CLAUDE.md, README.md, INICIO_RAPIDO.md, ecosystem.config.json, VERSION.json
    ├── _hilo             ← memoria del proyecto
    ├── _patron           ← base de conocimiento
    ├── docs              ← lo que se lee
    └── ops               ← lo que se ejecuta, más azure-pipelines.yml

Sin skills ni hooks como carpetas de solución: son cientos de ficheros del ecosistema que ni siquiera viven en el repo del consumidor cuando se usa el plugin. El contenedor se llama Ovillo (sin guion bajo: en una carpeta virtual no hay orden de disco que forzar) y sin número de versión (ya está en VERSION.json, visible en Raiz).

Consecuencias

  • Menos superficie: un solo flujo de commit, sincronización y ramificación; los evals de git-best-practices cubren cambios entre estrategias de ramificación, no entre sistemas de control de versiones.
  • El ecosistema funciona en VS Code sin ningún paso adicional; el soporte propio (.vscode/) es opcional.
  • Añadir soporte a otro IDE es un valor más en el enum y lo que init.js deba escribir; nunca un paso obligatorio en un workflow.

Verificación

  • Schema: organization.ide con enum de 4 valores; DEFAULTS.organization.ide === 'none' en hooks/lib/config.js.
  • Con ide: none, pwsh .claude/scripts/integracion-vs.ps1 → [SKIP] organization.ide = 'none'.
  • grep -rn "vspscc\|tf branch\|TFVC" ovillo/ → nada: no hay camino de ejecución para otro VCS.
  • ls ovillo/.vscode/ → extensions.json settings.json tasks.json, presentes también en plugin/hv/scaffold/.vscode/.
