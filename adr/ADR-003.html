ADR-003La skill es la única primitiva: conocimiento, workflow y regla por ruta

Aceptadoestado
2026-09-07fecha
1184palabras
5 decisionescita
10citada por
  • Estado: Aceptado
  • Fecha: 2026-09-07
  • Contexto: Claude Code ofrece una primitiva, la skill (.claude/skills/<nombre>/SKILL.md con frontmatter, más references/ y scripts/ bajo demanda), que cubre los tres modos de uso que Ovillo necesita: conocimiento que el modelo aplica solo cuando toca, procedimientos con efectos que solo el usuario debe lanzar, y convenciones que se activan al editar ciertos ficheros. Mantener además .claude/commands/*.md duplicaría contenedores, metadatos y evals, y un plugin no distribuye rules/. Ovillo usa solo skills: 67, y ningún comando.

Decisión

D1 — Tres clases operativas, declaradas en el frontmatter

ClaseFrontmatter¿La invoca el modelo?¿Su description entra en contexto?Cuántas
Conocimientometadata.kind: knowledge; description larga con cláusulas USE FOR: / DO NOT USE FOR:sí, por disparo semánticosí20
Workflowmetadata.kind: workflow + disable-model-invocation: true; description de una línea; argument-hint y allowed-tools cuando aplicanno: solo el usuario, con /hv:nombreno (0 tokens)35
Regla por rutametadata.kind: rule + paths: (globs) + user-invocable: falsese carga sola al trabajar con ficheros que casanno aparece en el listado ni en el menú12
  • kind viaja bajo metadata: porque es el campo libre del estándar Agent Skills: el frontmatter de primer nivel queda solo con campos que el runtime reconoce y la skill sobrevive fuera de Claude Code.
  • kind es declarativo y se verifica (ADR-022): toma exactamente uno de los tres valores y debe coincidir con lo que implican los flags (disable-model-invocation: true → workflow; paths: → rule; ninguno → knowledge). generate-inventory.js --check y build-plugin.js fallan si no coincide; el hook skill-guard (SessionStart, informa) lo revisa en el plugin instalado. Todas las skills lo declaran; la inferencia solo existe como red de seguridad.
  • Una skill de conocimiento puede traer además una sección ## Workflow (solo si se invoca /hv:nombre o se pide ejecutar/generar): el saber se aplica solo; el procedimiento, no. Sigue siendo knowledge (antes se etiquetaba hybrid; esa etiqueta se retiró porque no cambiaba el comportamiento y confundía el inventario).
  • Las 12 por ruta son las convenciones por capa: api, application, domain, infrastructure, database, tests, webapp, blazor, console, domain-api-docs, mcp-config, cicd-runtime.
  • Los workflows llevan nombres cortos en español (commit, analizar, cicd-init, pausar, sos, init); las de conocimiento se nombran por dominio (testing-patterns, cicd-architect, hub-client).

D2 — Progressive disclosure

SKILL.md no pasa de 400 líneas. Un procedimiento largo vive en references/ (por ejemplo cicd-init/references/ con un fichero por fase, o analizar/references/fases-analisis.md) y se lee solo cuando el workflow lo necesita. Una hybrid mantiene el conocimiento en SKILL.md y el procedimiento en references/workflow-<nombre>.md, de modo que preguntar no carga el procedimiento.

D3 — paths: es el único campo de scoping por ruta

Vale para .claude/rules/*.md y para skills. Comprobado con unidades señuelo en un repo consumidor real:

Frontmatter¿Carga al arrancar?
sin frontmatter, o sin paths:sí (incondicional)
paths: con patronesno; se activa al tocar un fichero que casa
paths: []sí: una lista vacía equivale a no tener el campo
globs: con o sin patronessí: el campo es inerte y la unidad se carga entera en cada sesión

Nunca usar globs:. Si hace falta una unidad que no cargue jamás, el idioma es un paths: con un patrón que no case con nada, comentado en el fichero. El BOM no impide parsear el frontmatter, pero el estándar es UTF-8 sin BOM.

D4 — Solo tres reglas incondicionales

.claude/rules/ contiene únicamente lo que debe cargar en toda sesión y no es expresable por ruta: context-optimization (dieta de tokens), developer-branch (se autogatea leyendo configuracion.branching.estrategia en ESTADO_PROYECTO.json) y devops-awareness (se autogatea por vcs.platform / cicd.platform). El plugin no las carga desde su paquete: las escribe /hv:init en el repo del consumidor (ADR-006).

D5 — Presupuesto de contexto

El runtime capa el listado de skills al 1 % de la ventana y trunca cada description a 1.536 caracteres; por encima, recorta en silencio y puede perder las palabras que disparan la skill. De ahí que solo las 20 de conocimiento paguen contexto, que sus descripciones tengan que caber en el cap, y que el techo objetivo de contexto siempre-cargado sea 14k tokens, medido con scripts/measure-context.js (ADR-009).

D6 — Subagente solo para lectura sin diálogo

context: fork + agent: (y background: false para recibir el informe en el mismo turno) se reserva a workflows que leen mucho y no conversan: analizar (general-purpose, background: false), git-best-practices (Explore) y security-audit (general-purpose). Los asistentes interactivos (cicd-init, nuevo-proyecto, onboarding, nuevo-evolutivo) no van en subagente: el diálogo con el usuario no sobrevive al aislamiento.

D7 — Lo que la taxonomía garantiza y lo que no

Garantiza que un workflow con efectos (commit, deploy, olvido en el Hub) nunca se alcanza por accidente: el modelo no ve commit en su listado, y una pregunta de conocimiento ("¿qué es un conventional commit?") se responde sin invocar herramienta alguna. No garantiza que una petición en lenguaje natural ("ejecuta los tests") alcance el procedimiento de una hybrid: el procedimiento se alcanza por invocación explícita, y así se documenta, sin prometer disparo semántico del workflow.

Consecuencias

  • Toda unidad tiene frontmatter completo y clase; hay una sola forma de metadatos, de evals y de publicación.
  • Los evals de disparo solo aplican a las de conocimiento; las workflow no son auto-invocables (ADR-009).
  • Los hooks que reaccionan a la invocación de un workflow casan por nombre corto con prefijo opcional hv: (ADR-004).
  • En modo plugin la invocación es /hv:<nombre>; en el fallback en-repo, /<nombre>.

Verificación

  • grep -l "kind: workflow" ovillo/.claude/skills/*/SKILL.md | wc -l → 35 = grep -l "disable-model-invocation: true" … | wc -l.
  • grep -l "kind: rule" … | wc -l = grep -l "^paths:" … | wc -l = las que llevan user-invocable: false; grep -l "kind: knowledge" … | wc -l → 20; grep -l "kind: hybrid" … → nada.
  • node scripts/generate-inventory.js --check y node scripts/build-plugin.js --check fallan con una skill cuyo kind no coincida con sus flags (node -e "require('./scripts/lib/skills-meta').verifySkillsDir('ovillo/.claude/skills')" → 0 problemas).
  • grep -rl "^globs:" ovillo/.claude/rules ovillo/.claude/skills → nada.
  • node scripts/measure-context.js → listado publicado de 20 unidades; las user-only y las que cargan por ruta, a 0 caracteres.

Enmienda (ADR-025, 2026-09-08)

El presupuesto de contexto de esta decisión deja de ser una aspiración y pasa a medirse y bloquear:

  • Techo: 14.000 tokens de contexto siempre cargado, medidos con node scripts/measure-context.js. --check --max 14000 es la quinta puerta de release y falla la publicación si se supera.
  • Los estándares de la organización dejan de estar siempre cargados: .claude/CLAUDE_BASE.md sale de los @imports del CLAUDE.md del consumidor y lo recuerda una regla nueva por ruta, estandares-base (src/**, *.csproj, *.sln). Sigue habiendo una sola fuente de ese estándar: la regla apunta, no copia.
  • Tope de 350 ch por description de agent y ninguna description de skill por encima del cap de 1.536, para que el listado que se publica al modelo no se trunque.
  • Un proyecto ya inicializado conserva su memoria: la pone al día /hv:init --refresh-memoria (opt-in).

Medida tras la enmienda: 13.029 tokens. Detalle y verificación en ADR-025.
