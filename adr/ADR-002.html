ADR-002Configuración de organización: ecosystem.config.json

Aceptadoestado
2026-09-07fecha
836palabras
4 decisionescita
2citada por
  • Estado: Aceptado
  • Fecha: 2026-09-07
  • Contexto: las convenciones que Ovillo aplica dependen de quién lo usa: prefijo de namespace, proveedor de identidad, cloud, motor y nomenclatura de base de datos, plataforma de CI/CD, tema visual, Hub. Si esa identidad viviera dentro de las skills y los hooks, cada organización tendría que editar cientos de ficheros y perdería la actualización centralizada. El principio rector es configuración sobre código: todo lo que es de la organización vive en un único archivo, y sin ese archivo el ecosistema sigue funcionando.

Decisión

D1 — Un archivo JSON en la raíz del proyecto consumidor

ecosystem.config.json, junto a CLAUDE.md. Se distribuyen ecosystem.config.example.json (todos los defaults, comentados con claves _doc), .claude/schemas/ecosystem.config.schema.json (JSON Schema draft-07) y .claude/scripts/validate-config.js, un validador Node sin dependencias que implementa el subconjunto de draft-07 que usa el schema (type, enum, const, pattern, required, properties, patternProperties, additionalProperties, items, minimum/maximum, minLength/maxLength). Exit 0 si es válido o si el archivo no existe (con aviso: la configuración es opcional por diseño); exit 1 si es inválido. JSON y no YAML: coherente con ESTADO_PROYECTO.json y parseable desde un hook sin instalar nada. Las claves que empiezan por _ son comentarios y el lector las ignora.

D2 — Tres niveles de precedencia

_hilo/ESTADO_PROYECTO.json   (proyecto)      decisiones del equipo: branching efectivo, entornos, dominiosExternos
        ↓ sobrescribe a
ecosystem.config.json         (organización)  identidad: prefijo, IdP, cloud, plataforma CI/CD, tema, Hub
        ↓ sobrescribe a
defaults neutrales            (código)        un repo vacío SIN config funciona

Cuando una clave existe en los dos primeros niveles (vcs.branchingStrategy frente a configuracion.branching.estrategia, cicd.environments frente a infraestructura.entornos, integrations[] frente a dominiosExternos[]) gana siempre el proyecto. El lector de referencia es .claude/hooks/lib/config.js: load() fusiona el archivo del usuario sobre DEFAULTS (espejo del schema) con deepMerge, cachea por proceso y nunca lanza: archivo ausente o ilegible ⇒ defaults.

database.engine es sqlserver por defecto porque es el motor con más cobertura en el núcleo de conocimiento (reglas, plantillas SQL, testing con Testcontainers); no impone ninguna versión.

D4 — Nomenclatura SQL configurable (database.naming)

storedProcedurePattern: "{schema}.{Verb}{Entity}", prefijos fn_ / fnt_ / vw_ / tr_, schemaCase: lowercase, allowedVerbs: [] (vacío = cualquier verbo), forbiddenPrefixes: [usp_, sp_, pr_, proc_, pa_], forbiddenSuffixes: [], legacySchemas: [], legacyPrefixes: [] y legacyBaselineFile (.claude/sql-legacy-baseline.txt) para el parque existente que el guard debe tolerar. El gating de features SQL por versión solo se aplica si database.version está fijada. Estas claves las leen sql-nomenclatura-guard.js y la utilidad sql-baseline-generate.js (ADR-004).

D5 — Lo que NO es configurable, y quién lee qué

El layout del proyecto (src/ docs/ ops/ _hilo/ _patron/) no está en este archivo a propósito: son identificadores (ADR-005). El Hub no lee este archivo, que es del consumidor: se configura por variables de entorno (ADR-007); hub.url y hub.apiKeyHeader alimentan a los clientes (hooks, skill hub-client, .mcp.json). Skills y agents siguen el patrón "leer la clave si existe → si no, default; nunca fallar ni preguntar por su ausencia", escrito en .claude/CLAUDE_BASE.md §0.

Alternativas descartadas

  • YAML: más cómodo para humanos, pero exige un parser (dependencia) en hooks y scripts.
  • Dentro de ESTADO_PROYECTO.json: mezcla el ámbito de organización (estable, compartible entre proyectos) con el de proyecto (mutable) y rompe la actualización no destructiva.
  • Varios archivos por área (identity.json, cicd.json…): más fricción de descubrimiento para ~120 líneas.
  • "Ovillo" como organización por defecto: Ovillo es el nombre del ecosistema, no de quien lo usa.

Consecuencias

  • Añadir una clave es tocar a la vez el schema, ecosystem.config.example.json y DEFAULTS en config.js.
  • /hv:init deja ecosystem.config.example.json en el repo y pide copiarlo y rellenar organization; los instaladores en-repo validan el archivo si existe y respetan hub.registerOnInstall (ADR-006).
  • Un consumidor puede compartir su ecosystem.config.json entre todos sus proyectos: no contiene nada de un proyecto concreto.

Verificación

  • node ovillo/.claude/scripts/validate-config.js ovillo/ecosystem.config.example.json → exit 0.
  • Sin archivo: exit 0 con el aviso de defaults neutrales.
  • DEFAULTS de ovillo/.claude/hooks/lib/config.js y ecosystem.config.example.json coinciden clave a clave; vcs.branchingStrategy tiene 13 valores en el schema y organization.ide 4.
