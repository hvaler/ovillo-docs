ADR-009Artefactos generados y puertas de release

Aceptadoestado
2026-09-07fecha
1119palabras
7 decisionescita
9citada por
  • Estado: Aceptado
  • Fecha: 2026-09-07
  • Contexto: Ovillo publica varias vistas de sí mismo: las cifras del inventario, un portal de documentación, el plugin, el zip y sus hashes. Mantener cualquiera de ellas a mano garantiza que se desincronice del filesystem. También necesita medir dos cosas que no se ven en un diff: si las descripciones de las skills disparan bien y cuánto contexto paga cada sesión del consumidor.

Decisión

D1 — Todo lo publicado se deriva del filesystem y tiene --check

ArtefactoScriptFuenteQué valida --check
publicacion/docs/recursos/data/inventory.jsonscripts/generate-inventory.jsovillo/.claude/**, hub/Endpoints/*.cs, adr/, publicacion/VERSION.jsondrift del inventario y cuadre de las páginas del portal por familia (Skills, Agents, Reglas, Hooks; Comandos = 0)
Portal publicacion/docs/ (entero)scripts/build-portal.jsinventory.json, cada SKILL.md, cada agent, las 3 reglas, settings.json + política leída del código de los hooks, adr/*.md, _patron/** y guías .mdlo generado difiere de lo commiteado
plugin/hv/ + .claude-plugin/marketplace.jsonscripts/build-plugin.jsovillo/.claude/ (+ el andamio para scaffold/)ídem (ADR-006), por huella de contenido con el EOL normalizado (ADR-030 D1)
Plantillas de generador-crudscripts/check-crud-templates.jslas 23 plantillas renderizadas con valores de ejemplocompilan juntas: 0 errores, 0 diagnósticos de Mapperly, sin placeholders sin sustituir (ADR-031 D6)
publicacion/ovillo-template.zipscripts/build-zip.jslos blobs de HEAD bajo ovillo/ (git archive, EOL LF, fecha de release, UTC; se niega si hay cambios sin commit o si la versión ya está etiquetada sin _hotfixes[]; ADR-030 D2)cada entrada frente a su blob de HEAD con el EOL normalizado, sin sobras ni faltas, entradas de texto en LF, zipSha256/zipSizeBytes de VERSION.json iguales a los del zip y su estructura: raíz única ovillo/, ficheros del contrato de los instaladores, carpetas del manifiesto estructura-plantilla.json, y nada de bin/ obj/ node_modules/ .vs/ TestResults/ ni credenciales
zipSha256, installPs1Sha256, installShSha256, zipSizeBytes en VERSION.jsonscripts/compute-hashes.ps1 (+ build-zip.js)los tres ficheros publicadoslos instaladores documentan cómo verificarlos antes de ejecutar

Criterios de conteo del inventario, explícitos en el script: skill = directorio con SKILL.md; hook = script cableado en settings.json (un script puede vigilar dos eventos; las entradas se cuentan aparte como hooks_entradas, ADR-032 D2); comando = .md en commands/; agent = .md en agents/; regla = .md en rules/ (incondicional si no tiene paths:); tool MCP = [McpServerTool(Name=…)] en hub/Endpoints; ADR = adr/ADR-*.md. El mecanismo de deuda del cuadre (DEUDA_PORTAL) existe y está vacío: cualquier descuadre es drift y rompe la puerta.

D2 — El portal es una vista, no un sitio editado

build-portal.js regenera publicacion/docs/ completo en cada ejecución: index.html (cifras del inventario + versión), una página por skill (67) con su frontmatter como ficha técnica y su cuerpo íntegro, una por agent (18), una por regla (3), hooks.html (evento, matcher y si bloquea, avisa o informa, leído de intrinsicBlock / resolvePolicy), hub.html (tools del inventario), patron.html, decisiones.html y una página por ADR, guias/ a partir de markdown vivo y buscar.html con índice embebido. Una sola hoja recursos/portal.css (tokens, tema claro/oscuro por prefers-color-scheme, un color por clase de skill), sin frameworks ni librerías embebidas; estático puro, servible desde cualquier servidor de ficheros. Si algo falta o está mal en el portal, se arregla en la fuente.

D3 — Flujo de release

editar ovillo/ → commit →
node scripts/generate-inventory.js && node scripts/build-portal.js && node scripts/build-plugin.js &&
claude plugin validate ./plugin/hv --strict && node scripts/build-zip.js && pwsh scripts/compute-hashes.ps1
→ commit

Cuatro puertas --check (inventario, portal, plugin, zip) más el validador de la CLI; todas en verde antes de publicar. Enmendado por ADR-025, ADR-030 D8 y ADR-031 D6: son seis puertas (más measure-context.js --check y check-crud-templates.js), y .github/workflows/publish-portal.yml las ejecuta todas, con el validador, la regresión de evals y los tests, en dos clones con core.autocrlf true y false en cada push a main. «En verde» significa en verde en los dos, no en la máquina del mantenedor.

D4 — Evals de disparo derivados de las descripciones reales

scripts/run_eval.py evalúa, para cada skill de conocimiento con eval-set.json (20), si sus queries positivas y adversariales la seleccionan. El vocabulario se deriva de la description del SKILL.md: la cláusula USE FOR: aporta los términos positivos (con doble peso), DO NOT USE FOR: los negativos, y son exclusivos los tokens que solo una skill usa. Query y descripción pasan por el mismo extractor (minúsculas, sin acentos, sin palabras vacías, con bigramas); el mapa de sinónimos es un puente ES↔EN, no una puerta; la puntuación base divide por los tokens discriminantes de la query (los que alguna descripción usa), para no penalizar preguntas largas. Las kind: workflow no se evalúan: no son auto-invocables.

Baseline: F1 0,8953 · 20 skills · 210 queries. No se baja. Una descripción incompleta se ve: si la skill cubre algo que su description no nombra, sus queries fallan y la nota lo dice. scripts/eval-regression/check-regression.py compara el último run con el anterior por skill (history.jsonl, umbral 0,05 de F1). Los quality-evals (run_quality_eval.py, scripts/quality-evals/) y los smoke tests del consumidor (.claude/smoke-tests/, tres suites: activación, compilación, convenciones) completan el cuadro.

D5 — Contexto siempre-cargado: medido, con techo

scripts/measure-context.js suma lo que entra en cada sesión del consumidor: CLAUDE.md con sus @imports (hasta 4 saltos), las reglas sin paths:, el listado publicado al modelo (nombre + description, sin las user-only ni las por ruta, que aportan 0) y las description de los agents. Caracteres exactos, tokens estimados a 4 caracteres/token.

ComponenteMedida
CLAUDE.md + 3 @imports (ESTADO_PROYECTO.json, SESION_ACTUAL.md, CLAUDE_BASE.md)41.596 ch · ~10,4k tok
3 reglas incondicionales14.193 ch · ~3,5k tok
Listado publicado (20 unidades)16.403 ch · ~4,1k tok
description de los agents12.376 ch · ~3,1k tok
Total84.568 ch · ~21,1k tok

Techo objetivo: 14k tokens. El listado se capa al 1 % de la ventana: cabe en 1M y excede en 200k (~8.000 ch), y dos description superan por sí solas el cap de 1.536 ch (cicd-architect 3.631, hub-client 1.937). Las tres cosas son deuda declarada (ADR-010).

Consecuencias

  • Ninguna cifra del README, del portal o del plugin se escribe a mano: si difiere del filesystem, una puerta lo detecta.
  • Reescribir una description mueve el F1: es la señal buscada, no un efecto secundario.
  • El coste de contexto de cada unidad nueva se mide antes de aceptarla.

Verificación

  • node scripts/generate-inventory.js --check && node scripts/build-portal.js --check && node scripts/build-plugin.js --check && node scripts/build-zip.js --check → exit 0.
  • node scripts/measure-context.js → total, desglose y las dos descripciones que exceden el cap.
  • python scripts/run_eval.py → F1 global ≥ 0,8953, 20 skills, 210 queries.

Enmienda (ADR-025, 2026-09-08)

A las cuatro puertas --check de D1 se suma una quinta, sobre la medida de contexto que esta decisión ya exigía tomar:

node scripts/measure-context.js --check --max 14000

Falla si el contexto siempre cargado del consumidor supera el techo de ADR-003, y entra en el flujo de release y en el workflow de publicación junto a las otras cuatro. El techo por defecto es el declarado; --max sirve para apretarlo, nunca para relajarlo sin ADR.
