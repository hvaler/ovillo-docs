ADR-017Integración con GitHub, ola 6: calidad, seguridad opt-in y guías

Aceptadoestado
2026-09-07fecha
937palabras
2 decisionescita
1citada por
  • Estado: Aceptado · Implementado · Cierra el plan de paridad con GitHub (ADR-011 a ADR-016)
  • Fecha: 2026-09-07
  • Contexto: tras las olas 0-5 un proyecto en GitHub genera, opera y audita su pipeline y lleva su backlog desde Ovillo, pero tres piezas seguían escritas solo para Azure DevOps: el cableado de calidad (la service-key del QR se aprovisionaba en un Variable Group; docs-agente-sync citaba un step de Azure y una variable con nombre del origen), la seguridad del repositorio (el ejemplo de GitHub Actions de security-audit usaba @v4 y @master, contra G16, y nada decía qué funciones nativas activar ni qué exige licencia), las guías del Patrón (todas en términos de pool, agentes y Variable Groups) y eval-gap, que solo sabía abrir work items en Azure DevOps.

Decisión

D1 — Calidad: la service-key del QR viaja a un secret de GitHub por stdin

Nuevo cicd-architect/templates/Provision-QualityCiKey.github.ps1.template (homólogo del de Azure): resuelve la apiKey per-dev, pide al Hub que emita o rote la service-key (POST /v2/sync/emit-service-key), y la guarda con gh secret set HUB_SERVICE_KEY leyendo de stdin, nunca con --body ni impresa; publica HUB_PROJECT_ID con gh variable set. Mismos códigos de salida que el de Azure (3 sin apiKey, 4/5 Hub, 6 gh sin sesión o sin permiso), -Env <environment> para secret de environment, -Rotate, -WhatIf. No hay «autorizar el VG»: los secrets de repositorio los lee cualquier workflow. calidad-codigo-sync/references/ci-wiring.md gana la sección 4-gh (equivalencias, zero-touch y manual) y cicd-init FASE 2.7 el bloque GitHub. docs-agente-sync documenta el job de GitHub equivalente y su variable pasa a llamarse HubProjectId.

D2 — Seguridad nativa de GitHub: opt-in con degradación, nunca bloqueante

FunciónCosteCómoSin licencia
Dependabot alerts / security updatesgratisPUT /repos/{o}/{r}/vulnerability-alerts · /automated-security-fixes—
Dependency review en PRsgratis (Dependency graph)job dependency-review de security.yml—
Secret scanning + push protectiongratis en públicos, GHAS en privadosPATCH /repos/{o}/{r} con security_and_analysishook secret-scanner + G5
Code scanning (CodeQL)gratis en públicos, GHAS en privadossecurity.yml (advanced setup) o PATCH …/code-scanning/default-setupgate G8 + job Security de ci.yml

Nuevo templates/github/security.yml.template (sello github-security): CodeQL con build-mode: none para C#, queries: security-extended, security-events: write solo en su job; dependency review con fail-on-severity: high; permissions: contents: read en la raíz, concurrency, todas las acciones por SHA (codeql-action@486fec2a… bundle v2.26.4, dependency-review-action@a1d282b3… v5.0.0). /cicd-init FASE 2.5-gh pregunta, intenta activar por API y, ante 403/422 («Advanced Security must be enabled»), no materializa el workflow, lo anota en ops/cicd/SEGURIDAD_PIPELINE.md y continúa. security-audit/tools/sast-integration.md sustituye su ejemplo con tags flotantes por el extracto pinneado y la tabla de funciones nativas.

D3 — Guías del Patrón para ambas plataformas

_patron/08_CICD/GUIA_GITHUB_ACTIONS.md (nuevo): fases y lo que exigen en GitHub, lo que genera /cicd-init, los tres comandos, modelos de deploy y rollback, G15-G19, seguridad opt-in, calidad, troubleshooting. README.md del Patrón neutro y con la guía en el índice; GUIA_FASES_ADOPCION.md con puntero y tabla de equivalencias (pool → runner, agentes → OIDC/self-hosted, aprobadores → reviewers, Variable Group → secrets, registro de definición → no existe); PERMISOS_CICD.md § GitHub (admin de repo, owner de org, scopes de gh, runners, OIDC, plan); RUNBOOK_TEMPLATE.md § equivalencias; runbooks de deploy manual y de actualización neutros.

D4 — eval-gap abre el item donde vive el ecosistema

El item «Eval gap» se abre en la plataforma del ecosistema, no la del proyecto consumidor. Azure: como hasta ahora. GitHub: gh issue create -R <owner/repo> con labels eval-gap, smoke-*, skill:*, priority:P*, area:calidad; duplicados con gh issue list --label. El destino se lee del nuevo campo ecosistema.repositorio de ESTADO_PROYECTO.json (null si el ecosistema vive en Azure DevOps).

D5 — Estado del plan de paridad

Las siete olas están hechas (0 vocabulario · 1 git-best-practices · 2 G15-G19 y auditor · 3 templates y wizard · 4 operación vía gh · 5 Issues y Projects · 6 calidad, seguridad y guías). Lo que sigue solo en Azure Pipelines es deliberado y está documentado: stacks netfx y Console/Worker con tarea programada, y el registro de definición (que en GitHub no existe).

Consecuencias

  • Paridad funcional Azure DevOps ↔ GitHub en configuración, conocimiento, generación, operación, backlog, calidad y seguridad; toda la bifurcación cuelga de cicd.platform / vcs.platform y el camino Azure no cambió.
  • Deuda que queda abierta (ya listada en CLAUDE.md): R18 cita mira summary; BUILDAGENT01 hardcodeado en los templates Azure y el wizard; y la verificación en vivo de todo lo de GitHub, que exige un repo sandbox (workflows despachados, environments con reviewers, rulesets, sub-issues, Projects, gh secret set por stdin, la activación de security_and_analysis y CodeQL en un repo con licencia).
