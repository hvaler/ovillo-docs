ADR-006Distribución: plugin hv en el marketplace ovillo, /hv:init y fallback en-repo

Aceptadoestado
2026-09-07fecha
958palabras
6 decisionescita
12citada por
  • Estado: Aceptado
  • Fecha: 2026-09-07
  • Contexto: Claude Code distribuye skills, agents y hooks como plugins instalados desde un marketplace (un repositorio git con .claude-plugin/marketplace.json) y los actualiza con un comando. Eso separa limpiamente el ecosistema (que se actualiza centralmente) del proyecto (su layout, su memoria, su base de conocimiento y su configuración, que viven en el repo del consumidor y nadie debe pisar). Un plugin, sin embargo, no puede llevar todo: ni rules/, ni el settings.json del consumidor, ni una URL de Hub que es de cada organización.

Decisión

D1 — Nombres: plugin hv, marketplace ovillo

El namespace de plugin es obligatorio en Claude Code (/plugin:skill, plugin:agent), así que el nombre del plugin es lo que se teclea a diario: se elige corto, hv. La marca Ovillo queda en el marketplace, el repositorio, el displayName y el portal.

AcciónComando
Instalarclaude plugin marketplace add hvaler/ovillo && claude plugin install hv@ovillo (--scope project deja enabledPlugins: {"hv@ovillo": true} en el repo)
Preparar el repo/hv:init
Invocar/hv:<skill> (/hv:commit, /hv:cicd-init, /hv:testing-patterns); agents hv:<agent>
Actualizarclaude plugin update hv@ovillo, y /hv:init de nuevo para completar lo nuevo

Los hooks no llevan namespace: se identifican por la etiqueta [hv] en su salida (ADR-004). El repositorio es privado: marketplace add usa las credenciales git ya presentes en la máquina.

D2 — El repositorio es el marketplace, y el plugin es una vista generada

.claude-plugin/marketplace.json en la raíz (name: ovillo, plugins[0] = { name: hv, source: ./plugin/hv }) y plugin/hv/.claude-plugin/plugin.json (name: hv, displayName: Ovillo, version; sin clave hooks: Claude Code carga hooks/hooks.json por convención y declararlo además en el manifiesto hacía que el plugin entero fallara al cargar, ADR-034 D10). plugin/hv/ y marketplace.json los genera scripts/build-plugin.js desde ovillo/.claude/; nadie los edita a mano, y --check detecta cualquier desviación respecto a la fuente (ADR-009).

Dentro del pluginPor qué
skills/ (67), agents/ (18)el ecosistema: lo que un plugin distribuye
hooks/ (21 cableados + lib/ + la utilidad) y hooks/hooks.jsonla sección hooks de settings.json con las rutas reapuntadas a ${CLAUDE_PLUGIN_ROOT}/hooks/
rules/ (las 3 incondicionales)como referencia: el runtime no carga rules/ desde un plugin; las escribe /hv:init
scaffold/el andamio del proyecto consumidor: todo ovillo/ salvo skills, agents, hooks y los eval-set.json; de aquí copia init.js
Fuera del pluginPor qué
settings.json del consumidorun plugin solo admite agent y subagentStatusLine; statusLine y anuncios los escribe init
.mcp.json del Hubhub.url es de cada organización; una URL fija sería inventarla. Lo configura la skill hub-client en el repo consumidor
eval-set.json, OVERLAP_MAP.mdinstrumentos del constructor del ecosistema, no del consumidor

D3 — /hv:init escribe lo que el plugin no puede llevar

Skill workflow (solo usuario) que ejecuta skills/init/scripts/init.js, un script Node determinista que copia desde ${CLAUDE_PLUGIN_ROOT}/scaffold/:

EscribeDetalle
src/ docs/ ops/ con sus READMElayout (ADR-005), según el manifiesto estructura-plantilla.json
_hilo/memoria vacía de arranque
_patron/base de conocimiento entera
CLAUDE.md, README.md, INICIO_RAPIDO.md, ecosystem.config.example.json, VERSION.json, .gitignore, .gitattributesficheros de arranque
.claude/CLAUDE_BASE*.md, CONFIGURACION.md, schemas/, scripts/, statusline.js, smoke-tests/, estructura-*.json, user-config.template.jsonlo del ecosistema que no es skill, agent ni hook
.claude/rules/las 3 reglas incondicionales
.claude/settings.jsonsin hooks (los trae el plugin): statusLine y anuncios
.vscode/ · .claude/scripts/integracion-vs.ps1solo si organization.ide (o --ide) es vscode · visual-studio (ADR-008)

Idempotente: nunca sobrescribe lo que existe (--force solo sobre ficheros concretos), así que re-ejecutarla tras plugin update completa lo nuevo y respeta lo adaptado. --dry-run muestra el plan y la skill lo enseña antes de ejecutar de verdad. No mueve código: si detecta un .sln/.csproj en la raíz, ofrece los git mv a src/ y recuerda revisar las rutas relativas de la solución.

D4 — Fallback en-repo: zip + instaladores no destructivos

Para quien no pueda usar plugins: publicacion/ovillo-template.zip (raíz ovillo/, generado de lo versionado, ADR-009) con install.ps1 / install.sh.

  • Fuente: -Source / --source = URL base (<base>/ovillo-template.zip) o ruta local; sin él, lee distribution.baseUrl del ecosystem.config.json destino.
  • No destructivo: la instalación respeta ficheros preexistentes; el update (detectado por la existencia de .claude/) refresca solo el núcleo .claude/* y conserva settings.json, settings.local.json, user-config.json, sql-legacy-baseline.txt, _hilo/**, CLAUDE.md, ecosystem.config.json, src/, docs/, ops/; en _patron/ añade sin pisar (ADR-005 D7).
  • Sin registro silencioso: registra en el Hub solo si hub.enabled, hub.registerOnInstall y hub.url están configurados, siempre con consentimiento interactivo (con -NoInput / --no-input nunca registra) y con telemetría OFF; el camino normal es /mcp-register (ADR-007).
  • Comprueba Node ≥ 18, valida la configuración con validate-config.js y añade al .gitignore las entradas de identidad local. VERSION.json publica zipSha256, installPs1Sha256 e installShSha256 para verificar los tres ficheros antes de ejecutar.

D5 — El validador de la CLI entra en el flujo de release

claude plugin validate ./plugin/hv --strict se ejecuta tras build-plugin.js: detecta frontmatter YAML inválido que el runtime descartaría en silencio (una description con : sin escapar deja un agent sin descripción ni modelo).

Consecuencias

  • El ecosistema se instala con dos comandos y se actualiza con uno; el proyecto se completa con /hv:init.
  • "Actualizar sin pisar personalizaciones" deja de ser un problema del instalador: lo del ecosistema vive en el plugin y lo del proyecto en el repo.
  • ovillo/ en el repositorio contiene las dos cosas (el ecosistema en .claude/ y el andamio del consumidor) y es la única fuente de la que se generan plugin, zip y portal.

Verificación

  • node scripts/build-plugin.js --check → sin desviaciones (503 ficheros); claude plugin validate ./plugin/hv --strict → pasa.
  • E2E en un repo vacío: marketplace add + install --scope project + /hv:init → raíz src docs ops _hilo _patron más ficheros de arranque; el modelo ve hv:testing-patterns y no ve hv:commit.
  • node plugin/hv/skills/init/scripts/init.js --dry-run en un repo ya inicializado → 0 ficheros escritos, todo "conservado".
