ADR-014Integración con GitHub, ola 3: generación de workflows desde /cicd-init

Aceptadoestado
2026-09-07fecha
1227palabras
3 decisionescita
1citada por
  • Estado: Aceptado · Implementado
  • Fecha: 2026-09-07
  • Contexto: cuarta ola del plan de paridad con GitHub (ADR-011, ADR-012, ADR-013). Tras las olas anteriores el ecosistema sabía juzgar un workflow de GitHub Actions (G15-G19, github-actions-reviewer, lint_github_workflow.py) pero no sabía producirlo: /cicd-init solo generaba azure-pipelines.yml a partir de los siete templates de Azure Pipelines, el sello de plantilla y el self-check de completitud entendían únicamente displayName:/ArtifactName:/- template:, y el wizard preguntaba por pools, Variable Groups y ManualValidation@0 aunque cicd.platform fuese github-actions. Esta ola cierra la generación sin tocar la ejecución (ola 4) ni el issue tracking (ola 5).

Decisión

D1 — Un juego de templates GitHub paralelo al de Azure, no una traducción línea a línea

ovillo/.claude/skills/cicd-architect/templates/github/:

TemplateSe materializa enCuándo
ci.fase1.dotnet.yml.template.github/workflows/ci.ymlFase 1 .NET (queda para PRs en Fase 2, sin push)
cd.fase2.dotnet.yml.template.github/workflows/cd-<slug>.ymlFase 2 .NET, uno por entrypoint (R25)
_reusable-dotnet-build.yml.template.github/workflows/_reusable-dotnet-build.ymlFase 2 .NET, una vez por repo
cd.fase2.vue.yml.template.github/workflows/cd-<slug>.ymlVue 3 + Vite (Fase 1: solo el job build)
ci.nettool.yml.template.github/workflows/publish-nuget.yml.NET-tool / librería (push del paquete solo en tags v*)
actions/security-scan/action.yml.template.github/actions/security-scan/action.ymlFase 2 (G8, verdict-file)
actions/security-gate/action.yml.template.github/actions/security-gate/action.ymlFase 2 (G8, warn en dev, block en pre/pro)
actions/quality-sync/action.yml.template.github/actions/quality-sync/action.ymlFase 2 .NET con Hub

Lo que en Azure eran steps/*.yml reutilizados por - template: son aquí un reusable workflow (build + test + cobertura + scan + publish) y tres composite actions. Los templates son YAML válido antes de sustituir (placeholders entre comillas o en comentarios; {{TRIGGER_BRANCHES_EXTRA}} y {{DEPLOY_STEP}} son marcadores de línea que /cicd-init reemplaza) para poder validarlos con PyYAML o actionlint en ambos estados. Cumplen G15-G19 de fábrica: permissions: contents: read en la raíz, todas las acciones pinneadas por SHA con la versión en comentario, concurrency (con cancel-in-progress: false en los CD), id-token: write solo en los jobs de deploy, ninguna entrada interpolada en run:.

No se portan netfx (MSBuild + IIS) ni Console/Worker con tarea programada: exigen runners Windows self-hosted y un modelo de despliegue que no se ha pilotado en GitHub. Siguen solo en Azure Pipelines.

D2 — G1 en GitHub = workflow_dispatch + environment:; el push solo construye

El modelo por defecto es on-demand: el push a la rama base ejecuta solo build; el deploy se lanza desde Actions → Run workflow o con gh workflow run cd-<slug>.yml -f environment=<dev|pre|pro>, y pre/pro llevan además required reviewers en su environment (FASE 2.5-gh): doble gate, equivalente a DeployEnv + ManualValidation@0/Environment approval en Azure. Los modelos auto (dev en cada push) y branch-gated (gitlab-flow/gitflow, github.ref por entorno) se documentan en la cabecera de cd.fase2.dotnet como cambios de if: y de on.push.branches. El rollback (G9) tiene tres capas: backup en el step Deploy, re-ejecución con --ref <sha_anterior>, y el runbook.

D3 — Los scripts que CI ejecuta se materializan en el repo: CI no puede leer el plugin

En la era del plugin hv@ovillo la skill vive fuera del repositorio del consumidor, así que .claude/skills/<skill>/scripts/x.ps1 no existe ni en el agente de CI ni en el repo. Regla:

  • Uso interactivo (Claude ejecuta el script durante el wizard): ${CLAUDE_PLUGIN_ROOT}/skills/<skill>/…, la misma convención que /hv:init.
  • Uso en CI: /cicd-init copia el script a ops/cicd/scripts/ (security-scan.ps1, Sync-QualityRecord.ps1, Sync-AgentDoc.ps1) y el workflow o pipeline lo invoca desde ahí.

Se corrigieron 16 referencias que asumían el layout en-repo (cicd-init, cicd-status, calidad-codigo-sync, docs-agente-sync, analisis-arquitectura, git-best-practices, github-actions-reviewer) y el steps/quality-sync.yml de Azure, que además arrastraba hosts del origen.

D4 — Sello y self-check con modo GitHub, sin duplicar el mapa de stacks

Get-TemplateStamp.ps1 gana los tokens github-dotnet-fase1 | github-dotnet | github-vue | github-nettool | github-reusable en el único mapa stack → fichero, y un fallback a $PSScriptRoot cuando la ruta relativa .claude/skills/cicd-architect/templates no existe (modo plugin). validate-pipeline-complete.ps1 -GitHub deriva los markers de name: (jobs y steps, con el guion opcional del step) y uses: (acciones) en vez de displayName:/ArtifactName:/- template:; el resto (bloques # CUSTOM:, -Allow, salida) es común. Los templates Azure no cambian ni un marker.

D5 — Wizard cicd-init bifurcado por cicd.platform, con un solo tronco

La detección (FASE 0), la elección de fase y de stack son comunes. Se bifurca donde la plataforma manda: 0.4-gh (pre-flight gh, tabla G1-G7 en GitHub, idempotencia 0.5), P2 (modelo de deploy en términos de if:), P2-bis (modelos), P3-gh (runner hosted/self-hosted y destino del deploy: azure-webapp, iis-selfhosted, container, custom → {{DEPLOY_STEP}}), P4-gh (secrets por environment vs repo, OIDC vs credenciales), FASE 2 (ficheros, ramas condicionales, sello, self-check -GitHub), FASE 2.5-gh (gh api PUT /repos/{o}/{r}/environments/{env} con reviewers, gh secret set, gh variable set), 2.6/2.7 (registro en ESTADO_PROYECTO.json con el mismo payload) y checklist de cierre. El hook pre-cicd-init añade, solo con github-actions, un pre-flight gh auth status WARN-first: sin gh o sin sesión avisa y deja pasar (el wizard puede generar los workflows igual; solo pierde la creación de environments por API).

D6 — Evals: las consultas sobre GitHub Actions dejan de ser adversariales

Las cuatro consultas de cicd-architect/eval-set.json que hasta ahora debían no activar la skill (workflows de GitHub Actions) pasan a positivas y se añaden dos más; la description gana el vocabulario de GitHub (workflow_dispatch, environments, reusable workflow, composite action, permisos). Se ajustó la frase «composite actions de seguridad» → «security-scan y quality-sync» porque la palabra genérica robaba una consulta a security-audit (0,75 → 0,57 → 0,75).

D7 — Higiene que destapó la ola

  • Hosts y agentes del origen que sobrevivieron a las purgas de 1.0.0 (nombres de servidores de build, demo y aplicaciones, colección de Azure DevOps): ~100 sustituciones por nombres neutros (BUILDAGENT01, dev01/demo01/app01, fileserver.example.org, MyCollection), con las cajas ASCII realineadas. Los templates Azure solo cambian en esas líneas.
  • Linter: G19 (concurrency) no aplica a un reusable workflow (solo workflow_call): la concurrencia la fija el caller.

Consecuencias

  • /cicd-init genera GitHub Actions o Azure Pipelines según cicd.platform; la ruta Azure no cambia.
  • Aparecen dos deudas que esta ola no resuelve (ver CLAUDE.md §2): el gate de cobertura R18 cita mira summary, herramienta interna del origen que Ovillo no distribuye; y el nombre del agente de build está hardcodeado (BUILDAGENT01) en templates y wizard de Azure en vez de preguntarse.
  • Siguiente ola (4): cicd-status/cicd-deploy/cicd-release vía gh, descriptions neutras en McpCicdTools.cs.
