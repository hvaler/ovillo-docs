ADR-012Integración con GitHub, ola 1: git-best-practices cubre la higiene completa del repositorio

Aceptadoestado
2026-09-07fecha
896palabras
1 decisionescita
4citada por
  • Estado: Aceptado · Implementado
  • Fecha: 2026-09-07
  • Contexto: segunda ola del plan de paridad con GitHub (ADR-011). git-best-practices era el único punto del ecosistema con conocimiento real de GitHub: un workflow de Actions, un ruleset básico y patrones de reusable workflows. Le faltaba lo que un repositorio de GitHub bien gobernado lleva puesto: CODEOWNERS, plantillas de PR e issues, Dependabot, merge queue, protección de tags, y un workflow que no regale permisos. Es la ola de mejor relación valor y esfuerzo: todo es conocimiento y plantillas, sin tocar ejecución ni el camino Azure DevOps.

Decisión

D1 — Siete plantillas nuevas, una skill

PlantillaQué fija
templates/CODEOWNERS.templateOwners por carpeta para el layout Ovillo: src/ (backend, frontend, datos, tests), ops/ y CI (DevOps), docs/ y _hilo/ (plataforma), _patron/, CLAUDE.md y ecosystem.config.json (arquitectura), autenticación y secretos (seguridad). Placeholders {{ORG}} y {{EQUIPO_*}}
templates/pull_request_template.md.templateTítulo en Conventional Commits (con squash es el commit final), tipo de cambio, cómo se probó, checklist que incluye el Hilo (FUNCIONALIDADES, DEPENDENCIAS, HISTORIAL_CAMBIOS, DECISIONES) y /hv:revision
templates/ISSUE_TEMPLATE/bug_report.yml.template · feature_request.yml.template · config.yml.templateIssue forms con campos obligatorios (versión, entorno, severidad; problema, propuesta, capa, impacto) y selector sin issues en blanco
templates/dependabot.yml.templateNuGet semanal desde /src agrupado (Microsoft/System aparte del resto, majors uno a uno) y las acciones de los workflows, ambos con prefijo Conventional Commits
templates/tag-ruleset.json.templateTags v*: ni borrar ni mover, creación solo por bypass, firmados. Protege lo que empuja /hv:cicd-release

D2 — El workflow CI no regala permisos

templates/github-workflow.yml.template pasa a: permissions: contents: read en la raíz; las nueve acciones pinneadas por SHA de commit con la versión en comentario (actions/checkout v7.0.1, setup-dotnet v6.0.0, cache v6.1.0, upload-artifact v7.0.1; las @v4 que traía llevaban dos majors de retraso); trigger merge_group para que la merge queue ejecute los checks; jobs Build y Security cuyo name: es el contexto que exige el ruleset; el job de seguridad falla si el audit de NuGet encuentra Critical o High; y un job deploy-staging real con environment, id-token: write para OIDC y un paso de despliegue que falla a propósito hasta que la organización lo sustituya por el suyo.

D3 — Rulesets completos

templates/branch-ruleset.json.template: ~DEFAULT_BRANCH, historial lineal, firmas, PR con require_code_owner_review, require_last_push_approval, hilos resueltos y solo squash, checks Build y Security estrictos, y merge queue (SQUASH, ALLGREEN, 5 entradas). El bypass de admins es solo vía PR. Cada regla lleva _description y el fichero un _ajustes con qué quitar según plan (Free sin merge queue, equipo sin firmas). Las claves _ se eliminan al aplicar.

D4 — Los rulesets se aplican por API, versionados en el repo

tools/github-rulesets.md: los JSON viven en .github/rulesets/, se aplican con gh api -X POST repos/{org}/{repo}/rulesets tras filtrar las claves _ (Node o jq), se listan, actualizan y borran; se verifica lo que aplica de verdad a una rama (/rules/branches/main) y la validez de CODEOWNERS (/codeowners/errors); rulesets de organización con repository_name; y una tabla de lo que rompe si se ignora (contexto = name: del job, merge_group obligatorio, bypass_mode: always solo en tags, evaluate solo Enterprise, protección antigua y rulesets se suman).

D5 — La skill lo sabe y los evals lo miden

Descripción con las capacidades nuevas en las dos lenguas; activación y tablas de recursos al día; checklists/repository-setup.md, patterns/monorepo-patterns.md y el workflow-nugets.md de nugets-management remiten a las plantillas en vez de repetir fragmentos. Eval-set 16 → 20 queries (CODEOWNERS, plantillas de PR e issues, Dependabot, merge queue). La consulta de CODEOWNERS se redactó en términos de GitHub porque, con «equipo», «revise» y «main», el motor léxico la enviaba a cicd-architect.

Además: un defecto de las purgas anteriores, reparado

Las reescrituras de la sesión 1.0.0 usaron replace(regex, () => '…$1…'): con función, $1 no se interpola. Quedaron literales *$1 1.0.0* (70 pies de página), $1$2 (35), *Skill $1 · kind: $2* (33) y tres ($1). Se repararon reproduciendo cada regla sobre la versión original de cada fichero (commit 4e0d601) y sustituyendo la línea defectuosa por lo que la regla quería producir; los 33 pies de skill se reconstruyeron desde el nombre de la carpeta y metadata.kind. Cero restos; los $1 que quedan son shell y PowerShell legítimos.

Consecuencias

  • Un proyecto en GitHub puede montar hoy su gobierno de repositorio entero desde la skill: copiar siete ficheros, sustituir placeholders, aplicar dos rulesets por API.
  • Las acciones pinneadas obligan a tener Dependabot activo (la plantilla lo trae) o los SHA envejecen.
  • Siguiente ola (2): invariantes G15-G19 en cicd-runtime (permisos mínimos, pin por SHA, pull_request_target, OIDC, concurrency) y el agent github-actions-reviewer, hermano de cicd-pipeline-reviewer, con fixtures bueno y malo.
