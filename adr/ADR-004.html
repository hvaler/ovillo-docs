ADR-004Hooks en Node con política WARN-first

Aceptadoestado
2026-09-07fecha
1064palabras
6 decisionescita
9citada por
  • Estado: Aceptado
  • Fecha: 2026-09-07
  • Contexto: los hooks son el contrato de Ovillo con el harness de Claude Code: se ejecutan en eventos del ciclo (inicio de sesión, antes y después de cada herramienta, cada prompt, parada) y son lo único del ecosistema que corre sin que el modelo decida. Tienen que funcionar en Windows, macOS y Linux sin exigir PowerShell, y tienen que avisar sin estorbar: un guard que bloquea por defecto acaba desactivado.

Decisión

D1 — 100 % Node ≥ 18, sin dependencias

Node ya es requisito del ecosistema (scripts de inventario y statusline.js), así que los hooks son .js puros. Protocolo: JSON por stdin (tool_name, tool_input, tool_output), y exit 0 = permitir · 1 = WARN (avisa, no bloquea) · 2 = BLOCK (solo en PreToolUse). Canal de salida (enmendado por ADR-030 D4): stdout solo es contexto para el modelo en SessionStart y UserPromptSubmit; en el resto de eventos Claude Code lo descarta, y con exit 1 y 2 lo que muestra es stderr. Los hallazgos y el motivo de un bloqueo van siempre por console.error; scripts/test-hooks.js lo comprueba para todos los hooks cableados. Enmendado por ADR-032 D1/D2: bash-guard trabaja sobre el comando en claro y tokeniza los flags cortos (rm -r -f, git push -fu, find -delete cuentan como la forma canónica), y hilo-json-guard vigila también PreToolUse · Write|Edit validando el JSON que quedaría en disco. La tabla siguiente es la de la fecha de este ADR; la vigente la publica el portal. Los Hooks cableados en .claude/settings.json (el inventario lleva la cuenta):

Evento · matcherHooks (cableado de 1.1.1; la tabla viva es la página Hooks del portal, derivada de settings.json)
SessionStart · *banner, mcp-check, skill-guard
PreToolUse · Bashbash-guard, antipattern-guard, hilo-json-guard
PreToolUse · `Write\Edit`protect-files, secret-scanner, auth-config-guard, cert-expiry-reminder, sql-injection-guard, token-validation-guard, sql-nomenclatura-guard, hilo-json-guard
PostToolUse · `Write\Edit`auto-format, multi-rol-coordination
PostToolUse · Bashpost-build-check, quality-alert
PostToolUse · Taskagent-telemetry
Stop · *session-checkpoint, hilo-checkpoint
UserPromptSubmit · *hilo-freshness, pre-cicd-init

Además, una utilidad CLI no cableada (sql-baseline-generate.js) y statusline.js. Los hooks degradan con gracia: git ausente, configuración ilegible o Hub apagado nunca rompen la sesión.

D2 — WARN-first: solo tres bloquean siempre

hooks.policy: "warn" | "block" y hooks.blockList: [...] en ecosystem.config.json. La función resolvePolicy(cfg, hookName, { intrinsicBlock }) de hooks/lib/config.js decide:

CasoResultado
intrinsicBlock: trueblock, siempre; ninguna configuración lo degrada
hooks.policy = "block"block para todos los guards configurables
el hook figura en hooks.blockListblock para ese hook
restowarn (exit 1)
CategoríaHooks
Bloqueo intrínseco (exit 2 siempre)bash-guard (comandos destructivos: git push --force, borrados recursivos…), hilo-json-guard (impide escribir JSON inválido en _hilo/), protect-files en su parte de certificados y claves (la de configuraciones de producción es WARN configurable)
WARN configurable (exit 1, elevable a 2)antipattern-guard, auth-config-guard, cert-expiry-reminder, secret-scanner, sql-injection-guard, sql-nomenclatura-guard, token-validation-guard
Informativos (exit 0)banner, mcp-check, auto-format, multi-rol-coordination, post-build-check, quality-alert, agent-telemetry, session-checkpoint, hilo-checkpoint, hilo-freshness, pre-cicd-init

Lo irrenunciable es lo destructivo y la integridad del Hilo; todo lo demás es criterio de la organización y se eleva por configuración.

D3 — Infraestructura común en hooks/lib/

  • helpers.js: readHookInput (stdin JSON con fallback a variables de entorno), getToolInput / getFilePath / getNewContent, projectDir; gitReadOnly (GIT_OPTIONAL_LOCKS=0, no crea locks), gitWithRetry (backoff exponencial ante index.lock), clearStaleGitLock (solo locks huérfanos > 30 s); y writeHiloJson, el único serializador de JSON del Hilo: valida antes de tocar el destino, escribe a .tmp, revalida y renombra (atómico), UTF-8 sin BOM. Ningún hook escribe JSON del Hilo de otra forma.
  • config.js: load() (defaults neutrales + deepMerge, cache por proceso), get(cfg, 'a.b.c', fallback), resolvePolicy y DEFAULTS.layout (ADR-005).

D4 — Etiqueta [hv] en un solo punto

Al cargarse, helpers.js envuelve console.log/error/warn y antepone [hv] a la primera línea de cada mensaje (respeta líneas vacías y no re-etiqueta). Los 22 cableados lo importan, así que la trazabilidad de 144 mensajes se resuelve sin tocar ninguno; la utilidad CLI no lo importa y no lo necesita.

D5 — Los hooks leen la configuración, nunca la exigen

sql-nomenclatura-guard ← database.naming.*, gating por database.version solo si está fijada, y la carpeta de código de layout.src; banner ← distribution.baseUrl / updateCheck (vacío = sin comprobación); mcp-check ← mcp.context7Url (vacío = servicio público); agent-telemetry ← hub.enabled/url/apiKeyHeader más el opt-in per-dev (Hub apagado = silencio); pre-cicd-init ← cicd.* y ESTADO_PROYECTO.json.

D6 — pre-cicd-init.js casa por nombre, con namespace opcional

Regex /\/(?:hv:)?cicd-init\b/: dispara con /cicd-init (fallback en-repo) y con /hv:cicd-init (plugin); no casa /cicd-initial. Es el motivo por el que el workflow conserva ese nombre corto.

D7 — Dos cableados, un mismo código

En-repo: settings.json con node "${CLAUDE_PROJECT_DIR}/.claude/hooks/<hook>.js". Plugin: hooks/hooks.json generado con ${CLAUDE_PLUGIN_ROOT}/hooks/<hook>.js (ADR-006). Los hooks de un plugin no llevan namespace: por eso la etiqueta [hv] en la salida.

Consecuencias

  • Requisito de runtime: Node ≥ 18 en la máquina del desarrollador; los instaladores lo comprueban.
  • Los scripts PowerShell que existen viven dentro de skills como herramientas opcionales, no cableadas; su port a Node es deuda declarada (ADR-010).
  • Cambiar un exit code o un mensaje es cambiar el contrato: cada hook se verifica por stdin simulado con al menos un caso de disparo y uno benigno, y la escalada a block se prueba con hooks.policy.

Verificación

  • grep -n "intrinsicBlock: true" ovillo/.claude/hooks/*.js → bash-guard, hilo-json-guard, protect-files.
  • grep -c CLAUDE_PLUGIN_ROOT plugin/hv/hooks/hooks.json coincide con los hooks cableados del inventario, y grep -c CLAUDE_PROJECT_DIR ovillo/.claude/settings.json con esa cifra más uno (la statusline).
  • echo '{"tool_name":"Bash","tool_input":{"command":"git push --force origin main"}}' | node ovillo/.claude/hooks/bash-guard.js → exit 2.
  • echo '{"prompt":"/hv:cicd-init"}' | node ovillo/.claude/hooks/pre-cicd-init.js → emite el pre-flight; con /cicd-initial → silencio.

Enmienda (ADR-026, 2026-09-08)

Regla nueva, explicita porque su ausencia produjo el defecto: un hook cuyo contrato admite exit 2 se cablea en PreToolUse. En PostToolUse el fichero ya esta escrito, asi que un exit 2 no impide nada: informa. Solo van ahi los hooks que formatean o avisan.

sql-injection-guard, sql-nomenclatura-guard y token-validation-guard documentaban «Exit 2 = BLOCK (politica block)» desde PostToolUse[Write|Edit]: una organizacion con hooks.policy: "block" creia impedir SQL inseguro y recibia un aviso con el codigo en disco. Pasan a PreToolUse[Write|Edit], el mismo evento que secret-scanner. Su codigo no cambia de logica: ya leian del payload de la herramienta.

Y dejan de aplicar sus patrones sobre el tool_input serializado: una interpolacion real llegaba como $\" y ningun patron escrito contra la comilla sin escapar la veia. Usan getFilePath y getNewContent de hooks/lib/helpers.js, que ya des-escapan.
