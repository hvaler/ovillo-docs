Cómo se mide

Dos cifras de consultas conviven en esta página y ambas son correctas: el baseline se fijó con 210 consultas (Ovillo 1.0.0, 2026-09-07) y el último run mide 220, porque los eval-sets han crecido desde entonces. Lo que sigue reproduce BASELINE.md.

check-regression.py compara siempre el ultimo run vs el anterior por skill en history.jsonl (append-only). Este archivo declara cual es el baseline vigente y por que cambio, para que "F1 >= X" en auditorias apunte a la cifra correcta.

Motorrun_eval.py deriva el vocabulario de la description real de cada SKILL.md (USE FOR / DO NOT USE FOR / tokens exclusivos)

El baseline es el de este motor. Las cifras de motores anteriores (que puntuaban un mapa de palabras clave escrito a mano y no podian suspender) no son comparables y no se conservan.

Como se actualiza

  1. python scripts/run_eval.py tras cualquier cambio de description.
  2. pwsh scripts/eval-regression/append-run.ps1 anade una entrada por skill a history.jsonl.
  3. python scripts/eval-regression/check-regression.py falla si una skill cae mas de los umbrales.
  4. Si el baseline cambia a proposito, documentar aqui el motivo y la cifra nueva.

Pendiente

  • history.jsonl conserva las entradas del run ovillo-v1.0.0 (2026-07-27, 16 skills, motor anterior) solo como historial: sus cifras no son comparables con este motor. El primer append-run del motor actual crea el baseline comparable con un run_id nuevo: append-run.ps1 genera ovillo-v<version>-<yyyyMMdd> por defecto y rechaza cualquier run_id ya presente en el fichero (append-only: nunca se reutiliza un identificador).
  • eval-results-latest.json lleva version (la del ecosistema, de VERSION.json) y engine (el motor de evals); el portal muestra ambas.
  • Quality-evals: el corpus de fixtures esta por crear para Ovillo; append-run.ps1 salta esa fase si run_quality_eval.py no existe.
