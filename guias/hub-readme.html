Hub central del ecosistema Ovillo — protocolo MCP real (15 tools, 4 resources ovillo://, 3 prompts) + REST v2 (registro/heartbeat, sync Hilo/F3/CI-CD, calidad QR, docs de agente, feedback del ecosistema).

v1.0.0: ASP.NET Core Minimal API .NET 10 + EF Core multi-provider — SQLite por defecto (fichero único) o SQL Server. Sin IIS, sin stored procedures, sin infraestructura previa: docker compose up.

Quickstart (Docker)

cd hub
docker compose up -d
curl http://localhost:8080/            # {"service":"Ovillo.Hub","version":"1.0.0",...}
curl http://localhost:8080/v2/version  # {"ecosystem_latest":"...","mcp_server_version":"1.0.0",...}

O en una línea, sin compose:

docker build -t ovillo-hub . && docker run -d -p 8080:8080 -v hubdata:/data ovillo-hub

Backup = copiar el volumen (/data/hub.db). Restaurar = reponer el fichero y reiniciar.

Quickstart (local, sin Docker)

dotnet run --project hub          # SQLite en ./hub.db por defecto

Esquema: EnsureCreated() en los dos proveedores desde el mismo modelo EF, y la evolucion en pasos idempotentes registrados en la tabla HubMetadata (Data/SchemaState.cs). GET /v2/version publica schema_version y schema_expected: si difieren, falta aplicar un upgrade. No se usan EF migrations (ADR-026 D5). Respaldo de SQLite: copiar el fichero. fichero nuevo = hub listo.

  • SqlServer: mismo modelo y mismo arranque que SQLite: EnsureCreated() y verificación tabla a tabla en el arranque (ADR-026, ADR-030); no hay EF migrations.

Contrato con los consumidores

  • Auth de las escrituras: header X-Hub-Api-Key (API key opaca; solo se persiste el hash SHA-256). 3 vías: key per-dev (ProyectoDevs), service-key per-proyecto para CI ( HUB_SERVICE_KEY en el pipeline), y key legacy per-proyecto.
  • Lectura anónima por defecto, acotable: los GET de /v2/stats, /v2/health, /v2/work, /v2/team, /v2/hilo/stats, quality, docs, cicd y feedback, y el endpoint MCP (/mcp) no exigen clave si Hub:ReadApiKey está vacía (read_access: "anonymous" en GET /v2/version). Con Hub:ReadApiKey configurada, todos ellos exigen X-Hub-Api-Key con esa clave o con una clave de escritura válida (per-dev, service key, legacy: quien puede escribir puede leer, y los scripts de CI no cambian); 401 con WWW-Authenticate si falta; GET / y GET /v2/version siguen públicos y read_access pasa a "key". Los clientes la toman de HUB_READ_API_KEY (.mcp.json la envía como cabecera). Si el Hub se publica fuera de una red de confianza y no se configura la clave, ponga un proxy con autenticación delante (AllowedHosts filtra la cabecera Host, no la red). ADR-032 D10, ADR-033.
  • Alta acotada: POST /v2/register y POST /v2/join no exigen clave (acceso al repo = autorización), pero llevan límite por IP (Hub:AltaPorMinuto, 10 por defecto; 429 al superarlo) y, si se configura Hub:RegistrationToken, exigen la cabecera X-Hub-Registration-Token (401 sin ella). El cliente la toma de la variable de entorno HUB_REGISTRATION_TOKEN. GET /v2/version publica registration_token_required. ADR-032 D9.
  • Politica de datos: retencion automatica (Retention:*: eventos de telemetria 90 dias, heartbeats 365; purga diaria) y borrado total con /v2/forget. PrivacyNoticeUrl apunta a la pagina «Datos y privacidad» del portal, que deriva del codigo de este servidor lo que sube cada categoria. La telemetria llega con el prompt ya hasheado en el cliente (ADR-024).
  • MCP (POST /mcp, JSON-RPC 2.0 + SSE, stateless): 15 tools (ping, get_version, search_decisions, register_decision, register_pipeline, register_agentdoc, register_ecosystem_feedback…), 4 resources (ovillo://decisions/…, ovillo://lessons/…, ovillo://snapshots/…, ovillo://projects/…/status), 3 prompts (/audit-security, /review-project-decisions, /weekly-status-report).
  • REST v2: /v2/register (opt-in via /hv:mcp-register), /v2/join, /v2/heartbeat, /v2/telemetry, /v2/version, /v2/forget, /v2/leave, /v2/opt-in, /v2/sync/* (Hilo, F3, cicd-batch, quality-batch, docs-batch, ecosystem-feedback, emit-service-key), /v2/stats/*.
  • Cliente de referencia: skill hub-client de la plantilla; config del consumidor en ecosystem.config.json → hub (enabled, url, apiKeyHeader).

Contenedor

docker compose up -d construye desde Dockerfile (imágenes base fijadas por digest, proceso como usuario app sin root, volumen /data propiedad de ese usuario) y declara un HEALTHCHECK que ejecuta dotnet Ovillo.Hub.dll --health (el binario consulta GET / y sale 0/1, porque la imagen runtime no trae curl). Para subir la imagen base, cambiar la etiqueta y el digest a la vez: curl -sI -H 'Accept: application/vnd.oci.image.index.v1+json' https://mcr.microsoft.com/v2/dotnet/aspnet/manifests/10.0 devuelve el digest vigente en Docker-Content-Digest. El Dockerfile está revisado, no ejecutado con daemon (deuda 1 de ADR-010).

Tests

dotnet test hub/Ovillo.Hub.Tests        # xUnit + WebApplicationFactory sobre SQLite (fichero temporal por test)

Cubren el arranque del esquema (ADR-030): una base nueva arranca con todas las tablas del modelo; una base parcial (tres tablas de una version anterior) se completa en el arranque con el DDL del propio modelo; y GET /v2/version publica schema_tables_expected, schema_tables_found y schema_tables_missing ademas de schema_version/schema_expected. Si tras intentar crearlas sigue faltando una tabla, el Hub no arranca y dice cual.

Smoke test manual

REG=$(curl -s -X POST http://localhost:8080/v2/register -H 'Content-Type: application/json' \
  -d '{"nombreProyecto":"Demo","ecosystemVersion":"1.0.0","ownerAlias":"yo","stack":".NET 10"}')
KEY=$(echo $REG | jq -r .apiKey); PID=$(echo $REG | jq -r .projectId)
curl -s -X POST http://localhost:8080/v2/heartbeat -H "X-Hub-Api-Key: $KEY" \
  -H 'Content-Type: application/json' \
  -d "{\"projectId\":\"$PID\",\"ecosystemVersion\":\"1.0.0\",\"agentsDisponibles\":18,\"skillsDisponibles\":53}"
