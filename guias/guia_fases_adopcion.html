Guia de adopcion CI/CD — Fases 0, 1 y 2

8 minlectura
1678palabras
9secciones
2026-09-08última edición
9cambios

Audiencia: desarrolladores + jefes de proyecto. Propósito: elegir el nivel correcto de CI/CD para tu proyecto antes de invocar /hv:cicd-init. Origen: modelo de doble barrera Ovillo local + Pipeline remoto (ver analisis-integracion-cicd.html en el portal docs).

Repositorio en GitHub? Las fases son las mismas; lo que necesitas y lo que se genera cambia. Lee GUIA_GITHUB_ACTIONS.md (§ 2 y § 3) y usa esta guia para el modelo de fases.

TL;DR — Cual elegir

FaseEstado del proyectoEsfuerzo inicialLo que ganasLo que NO obtienes
Fase 0Cero infraestructura Azure DevOps, deploy manual0 horas (solo Ovillo local)/hv:verify 7 fases pre-push, recordatorios disciplinaBuild remoto, CI verde/rojo, deploy automatico
Fase 1Tienes acceso a Azure DevOps + agente de build online~2 horasBuild validation branch policy, dotnet build + dotnet test en cada PRDeploy automatico, rollback, gates manuales
Fase 2Tienes el pool configurado + agentes <ENV>_DEPLOY + grupo aprobadores~6 horasPipeline completo Build → DEV (auto) → DEMO (gate manual) → PROD (gate environment, 2 servers rolling, triple rollback)— (este es el techo)

Regla rapida: empieza por la fase mas baja que puedas mantener. Subir de fase es facil; bajar duele.

Fase 0 — Solo Ovillo local

Cuando aplica

  • Proyecto nuevo o sin pipeline previa.
  • Sistemas de la organización aun no ha autorizado el pool configurado al proyecto.
  • Equipo pequeno (1 dev) sin necesidad de validacion remota.
  • Deploys puntuales (cada varias semanas), no diarios.

Que genera /hv:cicd-init en Fase 0

  1. RUNBOOK_DEPLOY_MANUAL.md adaptado al proyecto: RDP a server, copy DLLs, recycle app pool, smoke manual.
  2. Recordatorios pre-push en _hilo/CLAUDE.md (sección "Pre-commit"): obliga a ejecutar /hv:verify antes de cada git push.
  3. Entrada en _hilo/ESTADO_PROYECTO.json.infraestructura.cicd[] con { fase: 0, ... }.

Que NO genera

  • ❌ azure-pipelines.yml (no hay pipeline)
  • ❌ Llamada a Hub MCP (register_pipeline omitida)
  • ❌ Agentes ni grupos Azure DevOps

Como promocionar a Fase 1

Cuando el equipo de infraestructura autorice el pool configurado al proyecto + agente de build (cicd.buildAgent) disponible:

claude /cicd-init  # detecta Fase 0 + reescribe a Fase 1 (modo edicion FASE 0.5 idempotente)

Fase 1 — Build validation branch policy

Cuando aplica

  • Tienes acceso a Azure DevOps + el pool configurado autorizado.
  • Agente de build (cicd.buildAgent) online (el equipo de infraestructura confirma).
  • Quieres bloquear merges con build/tests rojos pero el deploy sigue manual.
  • Equipo de 2+ devs (PRs requieren protección).

Que genera /hv:cicd-init en Fase 1

  1. azure-pipelines.yml minimal: stage unico Build con dotnet restore/build/test y dotnet publish → artefacto drop. Sin CD, sin Deployment Groups.
  2. Registro pipeline en Azure DevOps vía _apis/build/definitions (FASE 2.5 del comando).
  3. Branch policy de build validation sugerida (manual via la UI de Azure DevOps o _apis/policy/configurations).
  4. Registro en Hub MCP: tool register_pipeline con fase=1.
  5. Entrada en _hilo/ESTADO_PROYECTO.json.infraestructura.cicd[] con { fase: 1, pipelineId, url, stages: ['Build'] }.

Que NO genera

  • ❌ Stages DeployDev/Demo/Prod
  • ❌ Variable Groups para secretos
  • ❌ Backup/rollback automatico
  • ❌ Runbook (deploy manual desde el artefacto)

Como promocionar a Fase 2

Cuando el equipo de infraestructura instale agentes <SERVER>_DEPLOY con capability DeployTarget=<env>-<app|svc> (R1/R25: un agente por entorno×tipo — Aplicaciones y Servicios; ver PERMISOS_CICD.md §3) en cada server destino:

claude /cicd-init  # detecta Fase 1 + reescribe a Fase 2 anadiendo stages CD (modo edicion FASE 0.5)

Fase 2 — Pipeline completo CD

Cuando aplica

  • Tienes Fase 1 funcionando estable >= 4 semanas.
  • el equipo de infraestructura confirma agentes online en DEV, DEMO y PROD (cada server con su agente <SERVER>_DEPLOY).
  • Grupo Azure DevOps de aprobadores creado y poblado (≥2 miembros para PROD).
  • Stack soportado: .NET ASP.NET Core (in-process) o Vue 3 + Vite + TS (SPA estatica).

Que genera /hv:cicd-init en Fase 2

  1. azure-pipelines.yml completo: stages Build → DeployDev (auto) → DeployDemo (gate ManualValidation@0) → DeployProd (Environment + group approval + 2 servers rolling).
  2. Triple rollback PROD: backup pre-deploy + MSDeploy enableRule:DoNotDeleteRule + condition: failed() step de restauracion.
  3. Variable Group <PIPELINE_NAME>-secrets creado vía _apis/distributedtask/variablegroups con fail-fast pre-build (valida que los secretos tienen valor).
  4. Retention rules: master 30d/5 builds, otras 7d/1 build.
  5. Coverage gate: avisa (WARN-first) o bloquea si la cobertura de lineas/branches baja del umbral (coverage-gate.ps1, script propio; -Mode block para bloquear; no calcula CRAP).
  6. RUNBOOK.md del proyecto: 6 secciones (build falla / deploy DEMO falla / deploy PROD falla / app caida tras deploy verde / contactos / backups), ≤1 pagina cada una.
  7. Registro Hub MCP: tool register_pipeline con fase=2.

Limitaciones a respetar

Antes de editar el YAML manualmente, comprueba las restricciones de tu plataforma (cicd.platform + cicd.variant). En la variante server-2020 aplican:

  • ❌ NUNCA Cache@2 (servicio Pipeline Caching no existe en Azure DevOps Server 2020)
  • ❌ NUNCA IISWebAppDeployment@1 (preview deprecada) → usar IISWebAppDeploymentOnMachineGroup@0
  • ❌ NUNCA deploymentGroup: keyword (schema rechaza)
  • ❌ NUNCA DownloadBuildArtifacts@0 / DownloadPipelineArtifact@2 (bug SSL Node.js contra devops.example.org) → usar REST API + PowerShell
  • ❌ NUNCA TLS 1.0/1.1 en scripts PowerShell (PS 5.1 default es 1.0; forzar 1.2+)

Detalle, comandos y seguridad opt-in: GUIA_GITHUB_ACTIONS.md.

Anti-patrones (lo que NO hacer)

  • ❌ Saltar de Fase 0 a Fase 2 directamente: el modo edicion FASE 0.5 del comando lo permite, pero perderse la fase intermedia significa que el primer fallo PROD sera catastrofico (sin practica con Fase 1).
  • ❌ Pedir Fase 2 sin tener agentes <ENV>_DEPLOY: el wizard lo detectara en FASE 0.4 pre-flight y abortara con mensaje claro.
  • ❌ Tratar Fase 0 como "no se hace CI/CD": Fase 0 SI es CI/CD — la primera barrera (Ovillo local con /hv:verify 7 fases) es lo que evita bugs reales en deploys manuales.
  • ❌ Editar azure-pipelines.yml ignorando G1-G19: el agent cicd-pipeline-reviewer te avisara, pero la disciplina humana es mas barata.

Cuando dudes

Sigue este arbol:

¿Tienes acceso a Azure DevOps y el pool configurado autorizado?
├── NO  → Fase 0
└── SI  → ¿Tienes agentes <ENV>_DEPLOY online en todos los servers destino?
         ├── NO  → Fase 1
         └── SI  → ¿Existe grupo aprobadores de Azure DevOps con ≥2 miembros?
                  ├── NO  → Fase 1 (y crear grupo en paralelo)
                  └── SI  → Fase 2

Si no estas seguro, empieza por Fase 0 y promociona cuando este claro el siguiente paso. El comando /hv:cicd-init es idempotente — re-invocarlo en modo edicion no rompe nada.

Actualizar el pipeline tras nuevas versiones de Ovillo

Hay dos capas y actualizar una NO actualiza la otra:

CapaQue esComo se actualiza
Plantilla Ovillo (.claude/)Las herramientas: comandos, reglas, skill cicd-architect, agent cicd-pipeline-reviewer, hooks, templates`irm <distribution.baseUrl>/install.ps1 \iex`
Tu azure-pipelines.ymlEl artefacto generado: vive en tu repo y corre en Azure DevOps/hv:cicd-init (re-ejecutado) o edicion manual

Clave: irm actualiza las herramientas, pero nunca toca tu YAML. El pipeline es tuyo; las mejoras de reglas no se imponen sobre el sin que tu lo decidas.

Comando vs skill vs agent — como invocar cada cosa

  • Comandos (/hv:cicd-init, /hv:cicd-status, /hv:cicd-deploy, /hv:cicd-release): se escriben con /.
  • Skill cicd-architect: auto-invocacion (se activa solo al editar azure-pipelines.yml).
  • Agent cicd-pipeline-reviewer: NO es un /comando (por eso no lo ves en la lista de slash commands). Se lo pides a Claude — ej. "audita mi azure-pipelines.yml con el agent cicd-pipeline-reviewer" o "revisa mi pipeline y dame un reporte de severidad" — y lo lanza como subagente.

Flujo recomendado al actualizar

  1. Actualiza la plantilla: irm … | iex (trae reglas/templates nuevos).
  2. Audita tu YAML contra las reglas vigentes: pide a Claude que pase el agent cicd-pipeline-reviewer. Te da el "diff de conformidad" (que reglas nuevas no cumple tu pipeline). Si sale limpio, no hay nada que hacer.
  3. Si hay hallazgos que quieres aplicar: re-ejecuta /hv:cicd-init. Su FASE 0.5 (modo edicion, regla R14 idempotencia):
    • hace backup automatico (.azure-pipelines.bak.<fecha>.yml),
    • muestra el diff antes de tocar nada,
    • ofrece 5 opciones: anadir stage / modificar stage / regenerar docs / actualizar YAML completo / salir,
    • preserva tus bloques # CUSTOM: ... # /CUSTOM y variables propias.
  4. Commit + push del YAML en tu repo → el push dispara el build y valida que sigue verde. La definicion en Azure DevOps no se re-registra (ya existe).
  5. Cambio de fase (0→1→2): el mismo /hv:cicd-init anade los stages nuevos (Deploy on-demand con DeployEnv R20, gate de seguridad R22, rollback…).

Que obliga a tocar el YAML (y que no)

Tipo de mejora en Ovillo¿Tocar el YAML?
Solo auditoria (el reviewer detecta mas cosas)No, salvo que quieras corregir un hallazgo
Cambio en el template (nuevo paso canonico)/hv:cicd-init opcion "actualizar YAML" lo incorpora (preservando tus customs)
Nueva fase / CD/hv:cicd-init anade stages
Cambios solo en hooks / comandos / skillNo afecta al YAML

Garantia: re-ejecutar /hv:cicd-init nunca pisa tu trabajo (backup + diff + confirmacion + preserva # CUSTOM). Es seguro hacerlo en cada actualizacion para re-sincronizar el pipeline con las reglas vigentes.

Ejemplo (proyecto en Fase 1 que solo refresca herramientas): si las novedades de la version son de Fase 2 (deploy) o de otro stack, tu YAML Fase 1 no necesita cambios — basta irm … | iex. Solo re-ejecutas /hv:cicd-init cuando quieras promocionar de fase o aplicar un cambio de template.
