Guía CI/CD con GitHub Actions — Fases 0, 1 y 2, comandos y seguridad

6 minlectura
1243palabras
8secciones
2026-09-08última edición
4cambios

Audiencia: devs y JPs de proyectos cuyo repositorio vive en GitHub (ecosystem.config.json → cicd.platform: github-actions). Es la lectura equivalente a GUIA_COMPLETA_CICD.md + GUIA_FASES_ADOPCION.md, que siguen el caso Azure DevOps. Las fases, los comandos y los invariantes son los mismos; cambia lo que necesitas de la plataforma y la forma de los ficheros. Generado por Ovillo.

1. Idea general

Ovillo genera con /hv:cicd-init un pipeline por entrypoint desplegable (R25) en .github/workflows/, con el modelo on-demand (G1): el push a la rama base construye y prueba; el deploy a dev/pre/pro se pide con /hv:cicd-deploy (o Actions → Run workflow). «Liberar» (/hv:cicd-release) es marcar un tag semver, construirlo y crear la GitHub Release; no despliega.

ComandoQué hace en GitHubCuándo
/hv:cicd-initGenera ci.yml (Fase 1) o cd-<slug>.yml + reusable workflow + composite actions (Fase 2); crea environments y secretos con gh; registra en el Hilo y en el HubAl adoptar CI/CD o al promocionar de fase
/hv:cicd-statusRuns (gh run list/view), tiempo por job, último deploy por environment, runs esperando aprobación, drift de plantillaPara ver cómo va el pipeline
/hv:cicd-releaseTag anotado + push (dispara build) + gh release create --generate-notesAl marcar una versión
/hv:cicd-deploy`gh workflow run cd-<slug>.yml --ref <rama\tag> -f environment=<env>` y sigue la runAl promover un artefacto a un entorno

Todos los workflows llevan sello # Ovillo cicd-architect github-<stack> @ …; /hv:cicd-status avisa de drift cuando la plantilla cambia, y /hv:cicd-init Opción 4 re-renderiza.

4. Modelo de deploy y rollback

  • On-demand (default): deploy-<env> solo corre con workflow_dispatch y inputs.environment == '<env>'.
  • Auto: deploy-dev con if: github.event_name == 'push'; pre/pro siguen on-demand.
  • Branch-gated (gitlab-flow/gitflow): además github.ref == 'refs/heads/<rama del entorno>'.
  • Doble gate en pre/pro: la confirmación de /hv:cicd-deploy y los required reviewers del environment. Nadie aprueba su propio environment desde Ovillo: se aprueba en Actions → Review deployments.
  • Rollback (G9): (1) backup previo en el step Deploy; (2) re-desplegar la versión anterior: /hv:cicd-deploy --env <env> --tag <anterior> (= gh workflow run cd-<slug>.yml --ref <tag> -f environment=<env>); (3) manual según ops/cicd/RUNBOOK.md.

Regla: /hv:cicd-init prueba la llamada; ante 403/422 («Advanced Security must be enabled») no materializa security.yml, lo anota en ops/cicd/SEGURIDAD_PIPELINE.md y sigue. Nunca bloquea la adopción por licencia.

7. Calidad: publicar el QR al Hub

El job quality de cd-<slug>.yml (composite quality-sync) publica el Registro de Calidad de cada build en el Hub Ovillo. Necesita el secret HUB_SERVICE_KEY (service-key del proyecto, no la apiKey del dev) y la variable HUB_PROJECT_ID. Dos vías:

  • Zero-touch: /hv:cicd-init FASE 2.7 materializa y ejecuta ops/cicd/provision-quality-ci-key.ps1 (desde Provision-QualityCiKey.github.ps1.template): pide al Hub la key y la guarda con gh secret set por stdin. La key nunca se imprime.
  • Manual: el admin la emite (EXEC mcp.EmitirServiceKey @Label='ci-quality') y gh secret set HUB_SERVICE_KEY < key.txt.

Sin key, el job avisa y sale en verde: la calidad no gatea el build.
