Auditing your CI/CD pipeline (cicd-pipeline-reviewer · github-actions-reviewer)

3 minlectura
757palabras
7secciones
2026-09-22última edición
1cambios

Two agents, one way of working: cicd-pipeline-reviewer audits azure-pipelines.yml and github-actions-reviewer audits .github/workflows/*.yml. Same report (🔴 HARD / 🟡 SOFT / 🔵 INFO), same G1-G19 invariants from cicd-runtime; this document follows the Azure DevOps case, and the GitHub one is identical with a different file and agent name.

Guide for developers: how to audit your azure-pipelines.yml against Ovillo's G1-G19 invariants and the limitations of Azure DevOps Server 2020, before registering the pipeline or after editing it by hand.

What it is

The cicd-pipeline-reviewer agent is a batch, read-only auditor (only Read/Grep/Glob, it changes nothing) that:

  1. Reads your whole azure-pipelines.yml.
  2. Checks it against .claude/skills/cicd-runtime/SKILL.md (the G1-G19 invariants) and against the constraints of the platform declared in ecosystem.config.json (cicd.platform + cicd.variant).
  3. Produces a structured report with a severity per finding plus the corrective action.

Severities:

Meaning
🔴 HARDA feature forbidden on Azure DevOps Server 2020 (it breaks the pipeline) or a secret in code. Fix it before registering.
🟡 SOFTInconsistent behaviour, known debt, or a deviation from the ecosystem's convention. Review it.
🔵 INFOA check that lives outside the YAML (agent account, retention in the definition, RUNBOOK), or a note.

When to audit

  • After editing azure-pipelines.yml by hand (before pushing).
  • Before registering a new pipeline or promoting a phase.
  • Periodically, to catch drift (someone added a Cache@2, a deploymentGroup:, and so on).
  • It runs automatically inside /hv:verify (the consumer's 7-phase pipeline).

When NOT to use it

  • To create a pipeline from scratch → use /hv:cicd-init.
  • To edit the YAML with inline suggestions → use the cicd-architect skill (interactive).
  • To apply the fixes → the agent does NOT modify anything; fix it yourself or delegate to cicd-architect.

How to launch it

Agents are not slash commands: you invoke them by describing the task to Claude inside a Claude Code session in your project.

cd C:\path\to\YourProject
claude

And in the session, type (any of these fires the agent — its USE FOR is "audit my pipeline"):

Audit azure-pipelines.yml with the cicd-pipeline-reviewer agent and give me the G1-G19 report with severities.

or simply:

audit my pipeline

Alternative route: /hv:verify also runs it (inside its 7-phase pipeline), but that is broader; for a focused audit use the prompt above.

Requirement: your project must have .claude/skills/cicd-runtime/SKILL.md (G1-G19) — it comes with Ovillo. If you are on an older version, run claude plugin update hv@ovillo first.

What it returns

  1. Inventory of the pipeline: detected stack, deployment model (auto / on-demand R20 / branch-gated R24), stages, adoption phase.
  2. Findings by severity (🔴/🟡/🔵), each with the rule broken, why, and the fix.
  3. Verdict: fit / with debt / blocking.

A real example — auditing MyCompany.ExchangeManager (netfx, branch-gated)

Pipeline: .NET Framework 4.8, branch-gated R24 model (develop→Dev/Demo, main→Prod), 4 stages.

Result: FIT — 0 🔴 findings, G1-G19 compliant. Known and managed brownfield debt:

SevRuleFindingAction
🟡R16Hardcoded secrets in Web.config (15+), no variable group and no fail-fastMove them to a variable group with isSecret + fail-fast; then raise R22 to block. See SECRETOS.md.
🟡R180% coverage (the .sln has no test projects) → VSTest and the gate are skippedAdd a test project and re-enable R18 when feasible
🔵R22Security gate in mode: warn in all three environments (not block in PRE/PROD)Correct while it is brownfield (GI#6). Raise it to block once Web.config is clean
🔵R6/R17/R19The agent account, retentionRules (in the definition) and RUNBOOK.md cannot be checked from the YAMLVerify them separately

It complies without deviation on: R1 (the configured pool + capability), R3 (REST download), R4 (canonical tasks), R5 (no Cache@2), R7 (double path pattern), R8 (checkout:none), R10 (TakeAppOffline netfx), R15 (PRE/PROD rollback), R20 (DeployEnv on-demand), R21 (gitlab-flow trigger), R23 (build per environment) and R24 (correct DeployEnv + Build.SourceBranch conditions: Prod only from main). No features forbidden on Azure DevOps Server 2020 (tables A/B clean; PROD uses regular jobs, avoiding TEC-006).

How to read it: a pipeline that is "FIT with 🟡" is deployable. The 🟡 findings are planned debt (recorded in DEUDA_TECNICA.md / SECRETOS.md), not blockers. Only the 🔴 ones force a fix before registering.
