CI/CD guide with GitHub Actions — phases 0, 1 and 2, commands and security

6 minlectura
1290palabras
8secciones
2026-09-22última edición
1cambios

Audience: developers and project managers whose repository lives on GitHub (ecosystem.config.json → cicd.platform: github-actions). This is the equivalent reading to GUIA_COMPLETA_CICD.md + GUIA_FASES_ADOPCION.md, which follow the Azure DevOps case. The phases, the commands and the invariants are the same; what changes is what you need from the platform and the shape of the files. Generated by Ovillo.

1. The general idea

With /hv:cicd-init, Ovillo generates one pipeline per deployable entrypoint (R25) under .github/workflows/, with the on-demand model (G1): a push to the base branch builds and tests; the deployment to dev/pre/pro is requested with /hv:cicd-deploy (or Actions → Run workflow). "Releasing" (/hv:cicd-release) means tagging a semver version, building it and creating the GitHub Release; it does not deploy.

CommandWhat it does on GitHubWhen
/hv:cicd-initGenerates ci.yml (phase 1) or cd-<slug>.yml + a reusable workflow + composite actions (phase 2); creates environments and secrets with gh; records it in the Hilo and in the HubWhen adopting CI/CD or promoting a phase
/hv:cicd-statusRuns (gh run list/view), time per job, last deployment per environment, runs waiting for approval, template driftTo see how the pipeline is doing
/hv:cicd-releaseAnnotated tag + push (triggers build) + gh release create --generate-notesWhen marking a version
/hv:cicd-deploy`gh workflow run cd-<slug>.yml --ref <branch\tag> -f environment=<env>` and follows the runWhen promoting an artifact to an environment

There is no pool to authorize and no agents to install (unless self-hosted): what on Azure was a handoff to the infrastructure team is here admin permission on the repository (environments, secrets, rulesets) and, for Projects v2 and organization runners, organization owner (see PERMISOS_CICD.md § GitHub).

Every workflow carries the stamp # Ovillo cicd-architect github-<stack> @ …; /hv:cicd-status warns about drift when the template changes, and /hv:cicd-init option 4 re-renders it.

4. Deployment model and rollback

  • On-demand (default): deploy-<env> only runs with workflow_dispatch and inputs.environment == '<env>'.
  • Auto: deploy-dev with if: github.event_name == 'push'; pre/pro stay on-demand.
  • Branch-gated (gitlab-flow/gitflow): plus github.ref == 'refs/heads/<the environment's branch>'.
  • Double gate on pre/pro: the confirmation in /hv:cicd-deploy and the environment's required reviewers. Nobody approves their own environment from Ovillo: approval happens in Actions → Review deployments.
  • Rollback (G9): (1) the backup taken in the Deploy step; (2) redeploy the previous version: /hv:cicd-deploy --env <env> --tag <previous> (= gh workflow run cd-<slug>.yml --ref <tag> -f environment=<env>); (3) by hand, following ops/cicd/RUNBOOK.md.

G16Actions pinned by SHAuses: owner/action@<sha40> # vX.Y.Z; Dependabot keeps them current (git-best-practices/templates/dependabot.yml.template)
G17No pull_request_target with a checkout of the fork, and no ${{ github.event.* }} inside run:inputs through env: and "$VAR"
G18OIDCid-token: write + azure/login/configure-aws-credentials with a federated credential
G19concurrencycancel-in-progress: true in CI, false in CD

Audit it with the github-actions-reviewer agent (see AUDITAR_PIPELINE.md); the ecosystem team maintains a linter with the same criteria.

The rule: /hv:cicd-init tries the call; on a 403/422 ("Advanced Security must be enabled") it does not materialize security.yml, records it in ops/cicd/SEGURIDAD_PIPELINE.md and carries on. It never blocks adoption over a licence.

7. Quality: publishing the quality record to the Hub

The quality job of cd-<slug>.yml (the quality-sync composite) publishes each build's quality record to the Ovillo Hub. It needs the secret HUB_SERVICE_KEY (the project's service key, not a developer's apiKey) and the variable HUB_PROJECT_ID. Two ways:

  • Zero-touch: /hv:cicd-init PHASE 2.7 materializes and runs ops/cicd/provision-quality-ci-key.ps1 (from Provision-QualityCiKey.github.ps1.template): it asks the Hub for the key and stores it with gh secret set over stdin. The key is never printed.
  • By hand: the admin issues it (EXEC mcp.EmitirServiceKey @Label='ci-quality') and gh secret set HUB_SERVICE_KEY < key.txt.

Without the key, the job warns and exits green: quality does not gate the build.
