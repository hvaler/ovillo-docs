Intelligent Context System for Claude Code

This document explains how the project scaffolding's context system works and how Claude navigates through it according to each project situation.

System Overview

The project scaffolding includes an intelligent context system that allows Claude Code to:

  1. Remember project state between sessions
  2. Understand existing functionalities, dependencies, and decisions
  3. Ask proactively to avoid errors
  4. Execute standardized commands for common tasks

System Architecture

CLAUDE.md                    ← Entry point (automatically read)
    │
    ├── _hilo/           ← Dynamic project memory
    │   ├── ESTADO_PROYECTO.json   ← Current state, phase, mode
    │   ├── FUNCIONALIDADES.md     ← What the application does
    │   ├── DEPENDENCIAS.md        ← What can break
    │   ├── DECISIONES.md          ← Why it was done this way
    │   ├── HISTORIAL_CAMBIOS.md   ← Changelog
    │   └── reuniones/             ← Meeting agreements
    │
    ├── .claude/commands/    ← Custom commands
    │   ├── onboarding.md    ← /onboarding
    │   ├── commit.md        ← /commit
    │   ├── prepara-entrega.md ← /prepara-entrega
    │   ├── revision.md      ← /revision
    │   ├── estado.md        ← /estado

        ├── 01_Estructura_Tecnica/

Operation Modes

The system has 4 main modes defined in ESTADO_PROYECTO.json:

1. Mode: puesta_a_punto (Setup)

When: Existing project newly incorporated into the template

Claude's behavior:

1. Detects "puesta_a_punto" mode in ESTADO_PROYECTO.json
2. Does NOT make code changes
3. Invites to execute /onboarding
4. Asks battery of questions to contextualize
5. Documents in _hilo/
6. Upon completion, switches to "desarrollo" mode

Flow:

┌─────────────────┐     ┌──────────────┐     ┌─────────────────┐
│ New project     │ ──► │ /onboarding  │ ──► │ Development     │
│ (puesta_a_punto)│     │ (questions)  │     │ mode (ready to  │
│                 │     │              │     │  work)          │
└─────────────────┘     └──────────────┘     └─────────────────┘

2. Mode: desarrollo (Development)

When: Active project development

Claude's behavior:

1. Reads complete context at startup
2. Asks proactive questions according to task type
3. Verifies dependencies before modifying
4. Updates _hilo/ with important changes
5. Uses commands for standard operations

Proactive questions:

SituationClaude asks
New functionality"Which module does it go in? Does it follow existing pattern?"
Modification"I've detected dependencies with [X]. Should I review impact?"
Bug fix"Steps to reproduce? Severity?"
Before coding"Do I understand the requirement correctly?"

3. Mode: mantenimiento (Maintenance)

When: Stable project, only minor corrections

Claude's behavior:

1. Conservative mode: minimal changes
2. Emphasis on not breaking existing functionality
3. Always verifies tests before changes
4. Documents all changes in HISTORIAL_CAMBIOS.md

4. Mode: soporte_uap (UAP Support)

When: Project in production supported by UAP

Claude's behavior:

1. Consults runbooks before acting
2. Prioritizes quick resolution
3. Documents incident according to template
4. Notifies about SLA impact

Available Commands

/onboarding

Purpose: Contextualize existing project When to use: When incorporating project into template What it does:

  • Asks battery of questions about the project
  • Documents in _hilo/
  • Switches mode to "desarrollo" upon completion

/commit

Purpose: Commit with verifications When to use: Before each commit What it does:

  • Verifies test coverage >= 70%
  • Verifies code format
  • Verifies no secrets present
  • Generates message according to commit policy
  • Updates HISTORIAL_CAMBIOS.md

/prepara-entrega

Purpose: Prepare version for delivery When to use: Before delivering to client/production What it does:

  • Verifies all tests pass
  • Generates/updates documentation
  • Updates FUNCIONALIDADES.md
  • Increments version
  • Generates delivery summary

/revision

Purpose: Analyze change impact When to use: Before modifying critical code What it does:

  • Analyzes modified files
  • Cross-references with dependency map
  • Identifies affected modules
  • Suggests tests to execute

/estado

Purpose: View current project state When to use: To know current situation What it does:

  • Shows mode, phase, version
  • Lists modules in development
  • Shows active alerts
  • Summarizes metrics

/sync

Purpose: Update project context When to use: After important changes What it does:

  • Analyzes current code
  • Updates FUNCIONALIDADES.md
  • Updates DEPENDENCIAS.md
  • Synchronizes ESTADO_PROYECTO.json

Context budget: windows, thresholds and anti-patterns

The unconditional rule .claude/rules/context-optimization.md states what to do. This section holds the why and the figures, which go stale sooner than the rules.

Window per model family

FamilyModelsWindowMax outputThinking
Claude 5Fable 5.1 (claude-fable-5-1) - Opus 5 (claude-opus-5) - Sonnet 5 (claude-sonnet-5)1M tokens128Kadaptive
Claude 4.5Haiku 4.5 (claude-haiku-4-5)200K tokens64Kextended

Source: platform.claude.com/docs/en/models/overview. Models 4.6 to 4.8 and Fable 5 are legacy and share the 1M window. Review this table whenever the Claude Code default model changes; the rule itself speaks of window classes (1M / 200K) rather than models, so it does not go stale.

1M is a lot, yet an intense session burns 200-400K over 50-100 tool calls, and with adaptive thinking the model's own reasoning also takes window on long tasks. Optimising context is not thrift for its own sake: it buys longer sessions and better answers.

Thresholds for suggesting /compact

Metric1M window200K window
Tool calls in the session> 80> 30
Whole files read> 25> 10
Unrelated tasks completed> 4> 2
Consecutive build errors> 3 (stop and replan)> 3 (stop and replan)

Consumption anti-patterns

Anti-patternInstead
Reading a whole file to find one lineGrep with the pattern
Unbounded git diffgit diff --stat, then the specific file
Unbounded git loggit log --oneline -10
dotnet build with full outputdotnet build -v quiet
Reading every file in a directoryGlob + Grep to filter first
Several Grep calls in a rowone with the combined regex
Re-reading CLAUDE.md every turnit is already in context

What is always loaded and what is not

Always: CLAUDE.md with its two @imports (project state and current session), the unconditional rules in .claude/rules/, the skill listing published to the model and the agents' description. On demand: the organization standards (.claude/CLAUDE_BASE.md, which the estandares-base rule brings up when touching src/), the layer rules (activated by file path), the guides in this knowledge base and the Hilo files that are not state (DEPENDENCIAS.md, FUNCIONALIDADES.md, specs/). That separation is what keeps the start-up context inside its budget.
